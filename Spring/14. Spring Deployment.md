
## Spring boot build file (.jar) using maven ?

#### First understand the lifecycle

Suppose your project is

```
itemset-service/

├── src
│   ├── main
│   │     ├── java
│   │     └── resources
│   └── test
│         └── java
│
├── pom.xml
│
└── target/
```

Initially,

```
target/
```

doesn't exist.

---

### Step 1 — Maven reads pom.xml

Command

```java
mvn clean install
```

First thing Maven does

```
Read pom.xml
```

It understands

- Java version
- Spring Boot version
- Dependencies
- Plugins
- Packaging type

Example

```
<dependencies>

spring-boot-starter-web

spring-boot-starter-data-jpa

postgresql

junit

mockito

</dependencies>
```

Maven now knows everything required to build your application.

---

### Step 2 — Download dependencies in ~/.m2/repository

#### Why do we need ~/.m2/repository?

`~/.m2/repository` is **Maven's local repository**. It stores downloaded dependencies and locally built Maven artifacts.

**Why is it needed?**

Suppose your project depends on:

- Spring Boot
- Hibernate
- PostgreSQL Driver
- JUnit

The first time you run:

```
mvn clean install
```

Maven downloads these libraries from remote repositories (like Maven Central) and stores them in:

```
~/.m2/repository
```

The next time you build, Maven **reuses the local copies** instead of downloading them again.

**Benefits:**

- ✅ Faster builds
- ✅ Saves internet bandwidth
- ✅ Works offline if dependencies are already downloaded

---

#### Another use case

If you run:

```
mvn install
```

your project's JAR is also copied into `~/.m2/repository`.

Now another local Maven project can use your library as a dependency without publishing it to a remote repository.

---

#### Interview answer (30 seconds)

> "`~/.m2/repository` is Maven's local repository. It stores downloaded dependencies like Spring Boot and Hibernate so Maven doesn't download them every time, making builds faster and allowing offline builds. It also stores artifacts created by `mvn install`, so other local Maven projects can use them as dependencies."

### Step 3 — Clean

Because command is

```
mvn clean install
```

first

```
clean
```

runs.

It deletes

```
target/
```

Why?

To remove

- old class files
- old jar
- old reports

Fresh build starts.

---

### Step 4 — Validate

Maven checks

- pom.xml syntax
- dependency conflicts
- required plugins

If pom.xml is broken

Build stops.

---

### Step 5 — Compile

Now Maven compiles Java.

```
.java

↓

javac

↓

.class
```

Example

```
ItemController.java

↓

ItemController.class
```

Every Java file becomes bytecode.

Output

```
target/classes/
```

---

### Step 6 — Copy Resources

Everything inside

```
src/main/resources
```

gets copied.

Example

```
application.yml

logback.xml

messages.properties
```

goes into

```
target/classes
```

---

### Step 7 — Compile Test Code

Now

```
src/test/java
```

also compiles.

Example

```
ItemServiceTest.java

↓

.class
```

---

### Step 8 — Run Unit Tests

This is very important.

JUnit executes.

Example

```
ItemServiceTest

CatalogServiceTest

ProductControllerTest
```

If

```
1 test fails
```

Build fails.

No JAR is created (with the standard lifecycle).

Example

```
Tests Failed

↓

BUILD FAILED
```

This is why unit tests are important in CI.

---

### Step 9 — Package

Now Maven packages everything.

Spring Boot plugin creates

```
itemset-service.jar
```

Inside JAR

```
Classes

+

Dependencies

+

Embedded Tomcat

+

Resources
```

This is called a **Fat JAR** (or Executable JAR). You don't need to install Tomcat separately.

---

### Step 10 — Install

Because command is

```
mvn install
```

Maven also copies

```
itemset-service.jar
```

into

```
~/.m2/repository
```

This is called the **local Maven repository**.

It allows other local Maven projects to use this artifact if needed.

---

### What happens inside Spring Boot packaging?

Without Spring Boot

```
Java Classes

↓

WAR

↓

External Tomcat
```

With Spring Boot

```
Java Classes

↓

Embedded Tomcat

↓

Dependencies

↓

Executable JAR
```

That's why we simply run

```
java -jar itemset-service.jar
```

### Which command is used in production?

In modern CI/CD pipelines, **`mvn clean verify`** or **`mvn clean package`** is commonly used because the artifact is usually consumed immediately by Docker or another deployment step. Installing it into the Jenkins agent's local Maven repository often provides no benefit since build agents are frequently ephemeral.

Typical flow:

```
mvn clean package
```

↓

```
itemset-service.jar
```

↓

```
Docker Image
```

↓

```
Deploy
```

If a team has multiple Maven modules that depend on one another within the same build environment, `mvn clean install` may still be used, but for many single-service Spring Boot applications in CI/CD, `package` or `verify` is sufficient.

---

### Interview answer (2 minutes)

> "When I build a Spring Boot application using Maven, Maven first reads the `pom.xml` to identify the project configuration, dependencies, plugins, and Java version. It downloads any missing dependencies into the local Maven repository, then the `clean` phase removes the old `target` directory. Maven compiles the application source code into bytecode, copies the resources, compiles the test code, and executes all unit tests. If the tests pass, the Spring Boot Maven plugin packages the application as an executable fat JAR containing the application classes, dependencies, resources, and embedded Tomcat. Depending on the build goal, Maven may also install the artifact into the local Maven repository. That JAR is then ready to be run with `java -jar` or packaged into a Docker image for deployment."

This explanation demonstrates that you understand both **the Maven lifecycle** and **how Spring Boot produces a deployable application**, which is exactly what interviewers are usually looking for.

### Diference b/w JAR and WAR ?

| **JAR**                                                                                     | **WAR**                                                     |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **JAR (Java Archive)**                                                                      | **WAR (Web Application Archive)**                           |
| Used for standalone Java/Spring Boot applications                                           | Used for traditional Java web applications                  |
| Contains application classes, dependencies, and **embedded server** (Tomcat/Jetty/Undertow) | Contains application code but **does not include a server** |
| Preferred for Spring Boot microservices                                                     | Common in older Spring MVC/Java EE applications             |
