

# Access Token, Refresh Token

## What is JWT?

JWT is just a token format.

JWT (JSON Web Token) is a compact, self-contained token that contains user claims and is digitally signed. It is commonly used for stateless authentication.

### JWT Structure

```
Header.Payload.Signature
```

Explain:

```
Header
{
  "alg":"HS256",
  "typ":"JWT"
}
```

```
Payload
{
  "sub":"prashant",
  "role":"USER"
}
```

```
Signature
Hash(header + payload + secret)
```

---

## What is Access Token?

Access Token = Token used to access APIs.

Often the Access Token is a JWT.

Example:

```
Access Token = JWT = eyJhbGciOiJIUzI1NiIs...
```

Purpose:

```
Call APIs
Prove identity
Authorize requests
```

Example:

```
GET /api/profile
```

Server asks:

> "Who are you?"

You send Access Token.

Server verifies it.

Request allowed.

---

## What is Bearer Token?

This is where most beginners get confused.

Consider this request:

```
GET /api/profile
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

The word:

```
Bearer
```

is NOT the token.

The actual token is:

```
eyJhbGciOiJIUzI1NiIs...
```

"Bearer" simply tells the server:

> "I am sending a token."

---

### Example

Suppose:

```
Access Token = ABC123
```

Request becomes:

```
Authorization: Bearer ABC123
```

Here:

|Part|Meaning|
|---|---|
|Bearer|Authentication scheme|
|ABC123|Actual token|


> A Bearer token is an access token sent through the Authorization header.

---

### Real Life Analogy

Imagine entering a cinema.

Security says:

> Show your ticket.

You show:

```
Ticket #A12345
```

Security doesn't ask:

- Your name
- Your password
- Your email

Whoever possesses the ticket can enter.

This is why it's called:

```
Bearer Token
```

Meaning:

> Whoever bears (holds) the token gets access.

---

### [ Why Access Token Expires ]

Suppose Access Token lives forever.

```
Valid for 1 year
```

Hacker steals it.

Now hacker can use your account for one year.

Bad.

So we make it short:

```
15 minutes
```

After 15 minutes:

```
401 Unauthorized
```

because token expired.

---

### [ Then Why Refresh Token ? ]

Without Refresh Token:

```
Access Token expires
↓
User enters password again
```

Very annoying.

Instead:

```
Access Token = 15 min
Refresh Token = 7 days
```

###  Access Token Expires

After 15 minutes:

```

```


### Refresh Flow

Frontend automatically sends:

```
POST /auth/refresh
```

with Refresh Token.

Server checks:

```
Refresh token valid?
Exists in DB?
Not revoked?
```

If valid:

Creates new Access Token:

```
JWT789
```

Returns:

```
{
  "accessToken":"JWT789"
}
```

User doesn't notice anything.

No login screen.

No password.

---

### Why Refresh Token Stored in DB?

Access Token usually isn't stored in DB.

Because JWT is self-contained.

But Refresh Token is stored.

Example table:

```
refresh_tokens

id
user_id
token
expiry_date
```

Why?

Because logout requires revocation.

---

### Logout

User clicks Logout.

```
POST /logout
```

Server:

```
DELETE FROM refresh_tokens
WHERE user_id = 101;
```

Now Refresh Token is useless.

Even if Access Token exists:

```
Expires in few minutes
```

After that:

```
User completely logged out
```

## Interview Understanding

### JWT

> A JWT is a self-contained token containing user claims and a digital signature.

### Access Token

> A short-lived token used to access protected APIs.

### Refresh Token

> A long-lived token used to obtain new access tokens without requiring the user to log in again.

### Bearer Token

> A Bearer token is an access token sent in the HTTP Authorization header using the Bearer scheme.

---

### The Most Important Relationship

```
JWT
│
├── Token Format
│
└── Often used as Access Token


Access Token
│
├── Used for API calls
├── Usually JWT
└── Sent as Bearer Token


Bearer Token
│
└── Way of sending token
   Authorization: Bearer <token>


Refresh Token
│
└── Used only to generate
   new Access Tokens
```

### Interview Answer (2 Minutes)

**What is a Filter?**

> A Filter is a servlet component that intercepts HTTP requests and responses before they reach the controller. It is commonly used for logging, authentication, authorization, JWT validation, CORS, and request modification.

**What is SecurityFilterChain?**

> SecurityFilterChain is an ordered chain of Spring Security filters that process incoming requests. It performs authentication, authorization, session management, CSRF protection, JWT validation, and other security-related tasks before the request reaches the controller.

**Why was WebSecurityConfigurerAdapter removed?**

> WebSecurityConfigurerAdapter was removed because Spring Security moved from inheritance-based configuration to bean-based configuration. The new SecurityFilterChain approach is more flexible, readable, testable, and follows the modern Spring principle of composition over inheritance.



## 5. Why Custom JWT Filter ( OncePerRequestFilter ) ? What is UserDetails ? What is UserDetailsService ? why it needed ?

### Why Custom JWT Filter (`OncePerRequestFilter`)?


When a request comes:

Spring Security doesn't automatically know how to validate **your JWT token**.

You need a custom filter to:

1. Extract JWT from header
2. Validate JWT
3. Get user details from token
4. Set authenticated user in Spring Security Context

---

### Why `OncePerRequestFilter`?

Because we want JWT validation to happen **exactly once per request**.

```
public class JwtAuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(...) {
        // validate token
    }
}
```

Without it, a filter might execute multiple times during request forwarding.

### Interview Answer

> We create a custom JWT filter to intercept every request, validate the JWT token, and set authentication in SecurityContext. We extend OncePerRequestFilter to ensure the filter executes only once per request.

---

## 5. What is BCryptPasswordEncoder?

**BCryptPasswordEncoder** is a Spring Security class that converts a plain password into a secure one-way hash before storing it in the database.

```
PasswordEncoder encoder =  new BCryptPasswordEncoder();
```

---

#### Registration Flow

User enters:

```
admin123
```

Code:

```
String encoded = encoder.encode("admin123");
```

Result:

```
$2a$10$Q8fJ9h2j.....
```

Store in DB.

---

#### Login Flow

User enters:

```
admin123
```

Spring does:

```
encoder.matches("admin123", storedHash);
```

Returns:

```
true
```

User authenticated.


---

### How BCrypt Works (Theory)

Imagine password:

```
admin123
```

BCrypt performs:

#### Step 1: Generate Salt

Example:

```
X7Y9Z123ABC
```

#### Step 2: Mix Password + Salt

```
admin123 + X7Y9Z123ABC
```

#### Step 3: Run BCrypt Algorithm

Multiple rounds of computation.

```
Hash(admin123 + Salt)
```

Result:

```
$2a$10$Q8fJ9h2j.....
```

Store this in DB.

---

### [ What is Salt? ]

This is one of the most asked interview questions.

---

#### Problem Without Salt

Two users choose:

```
password123
```

Hash:

```
Hash(password123)
```

Result:

```
ABC123
```

DB:

```
User1 -> ABC123
User2 -> ABC123
```

Attacker immediately knows both users have same password.

---

#### With Salt

User1:

```
password123 + SALT1
```

Result:

```
XYZ111
```

User2:

```
password123 + SALT2
```

Result:

```
PQR999
```

DB:

```
User1 -> XYZ111
User2 -> PQR999
```

Same password.

Different hashes.

Much safer.

#### BCrypt Example

```
PasswordEncoder encoder =
        new BCryptPasswordEncoder();

System.out.println(
    encoder.encode("admin123")
);

System.out.println(
    encoder.encode("admin123")
);
```

Output:

```
$2a$10$abcxyz.....$2a$10$pqrlmn.....
```

Different every time.

Because BCrypt generates a new Salt each time.

This is a favorite interview question.

```
   |

   |

   |
```

```
Two Way

     |

     |

```

```
 |

```

---

### Interview Answer

#### What is BCryptPasswordEncoder?

> BCryptPasswordEncoder is a Spring Security implementation of PasswordEncoder that hashes passwords using the BCrypt algorithm before storing them in the database. It automatically generates a unique salt and performs secure password verification using the matches() method.

#### What is Salt?

> Salt is a random value added to a password before hashing. It ensures that even if two users have the same password, their stored hashes will be different, protecting against rainbow table attacks.




## 7. Why Disable CSRF in JWT APIs?

This is a favorite interview question.

---

### Session Based Authentication

```
Browser
  |
Cookie
  |
Server Session
```

Cookies are automatically sent.

CSRF possible.

Need protection.

---

### JWT Authentication

```
Authorization: Bearer eyJhbGci...
```

Browser does NOT automatically attach JWT.

Frontend must explicitly send:

```
headers: {
   Authorization: "Bearer token"
}
```

Attacker's website cannot force the browser to attach your JWT.

So:

```
CSRF attack not possible
```

(or greatly reduced).

---

Therefore in JWT APIs:

```
http.csrf(csrf -> csrf.disable());
```

because:

```
No Session
No Cookie Authentication
No CSRF Risk
```

---

### Interview Answer

**Why disable CSRF in JWT-based APIs?**

> CSRF attacks rely on browser cookies being automatically sent with requests. JWT authentication usually sends tokens in the Authorization header, which browsers do not attach automatically. Therefore CSRF protection is generally unnecessary for stateless JWT APIs and is usually disabled.

#### Security Flow is Different


---

### AuthenticationException vs AccessDeniedException

Let's understand carefully.

---

### AuthenticationException

```
WHO ARE YOU?

status - 401 Unauthorized
```

**`AuthenticationException`** means the system cannot verify your identity because you provided invalid or missing credentials.

- No JWT - no token provided
- Expired JWT
- Invalid JWT Signature
- Wrong Username Password

---

### AccessDeniedException

```
I KNOW WHO YOU AREBUT YOU ARE NOT ALLOWED

status - 403 Forbidden
```

User authenticated successfully.

But lacks permission.

**`AccessDeniedException`** means the system knows exactly who you are, but you do not possess the required permissions or roles to view the requested resource.


### Most Important Interview Question

#### Why doesn't @ControllerAdvice handle AuthenticationException?

Answer:

> AuthenticationException and AccessDeniedException occur inside the Spring Security filter chain before the request reaches the controller. Since @ControllerAdvice only handles exceptions thrown during controller execution, Spring Security provides AuthenticationEntryPoint and AccessDeniedHandler for handling security-related exceptions.

---
### Production Rule


#### `@ControllerAdvice`

For:

```
Business Exceptions
Validation Exceptions
Database Exceptions
Service Layer Exceptions
```

Examples:

```
UserNotFoundException
OrderNotFoundException
MethodArgumentNotValidException
```

---

#### `AuthenticationEntryPoint`

For:

```
401 Unauthorized
AuthenticationException
JWT Issues
```

---

#### `AccessDeniedHandler`

For:

```
403 Forbidden
Role/Permission Issues
AccessDeniedException
```

This separation is exactly how production-grade Spring Security applications handle authentication and authorization errors.

## Example Security Configuration

```
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http)
            throws Exception {

        return http
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**")
                .permitAll()
                .requestMatchers("/admin/**")
                .hasRole("ADMIN")
                .anyRequest()
                .authenticated()
            )
            .build();
    }
}
```

## Interview Answer (2-Min Version)

**Spring Security is a framework that provides authentication and authorization for Spring applications. Internally, every request first passes through the SecurityFilterChain. Authentication filters extract credentials and delegate them to AuthenticationManager, which uses AuthenticationProvider and UserDetailsService to validate users. On successful authentication, an Authentication object is stored inside SecurityContextHolder (ThreadLocal). Authorization filters then verify roles and permissions before allowing access to controllers.**
