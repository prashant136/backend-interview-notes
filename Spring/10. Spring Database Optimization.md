
`To Overcome N+1 problem --->  JOIN FETCH, Entity Graphs, DTO projections, batch fetching, or optimized custom queries so related entities are loaded in a single query.`



# ==what is projection in spring boot ? How does Spring Data JPA work with native queries and projections ?==

## What is Projection in Spring Data JPA?

**Projection means: fetch only selected columns from database instead of full entity.**

Example: Your `users` table has:

```
id, name, email, password, phone, address, created_at
```

But for user list API, frontend only needs:

```
name, email
```

Without projection:

```
SELECT * FROM users;
```

With projection:

```
SELECT name, email FROM users;
```

So projection is mainly used for:

**Performance + security + cleaner API response.**

Spring Data JPA officially supports interface-based projections and DTO/class-based projections. Interface projections are backed by proxy objects, while DTO projections create actual DTO objects.

---

## Real-world intuition

Imagine this API:

```
GET /api/users
```

For listing users, should we return full entity?

```
{
  "id": 1,
  "name": "Prashant",
  "email": "p@gmail.com",
  "password": "encrypted-password",
  "address": "Bangalore",
  "phone": "9999999999"
}
```

Bad idea.

You only need:

```
{
  "name": "Prashant",
  "email": "p@gmail.com"
}
```

That is projection.

---

### Suppose we have Entity Class for example

```
package com.example.demo.entity;

import jakarta.persistence.*;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    private String password;
    private String phone;
    private String city;

    public User() {}

    public User(String name, String email, String password, String phone, String city) {
        this.name = name;
        this.email = email;
        this.password = password;
        this.phone = phone;
        this.city = city;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public String getEmail() { return email; }
    public String getPassword() { return password; }
    public String getPhone() { return phone; }
    public String getCity() { return city; }
}
```

## Interface-based Projection

### Projection Interface

```
package com.example.demo.projection;

public interface UserSummaryProjection {
    String getName();
    String getEmail();
}
```

Important: method names must match entity fields:

```
getName()  -> name
getEmail() -> email
```

### Repository

```
package com.example.demo.repository;

import com.example.demo.entity.User;
import com.example.demo.projection.UserSummaryProjection;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;

public interface UserRepository extends JpaRepository<User, Long> {

    List<UserSummaryProjection> findByCity(String city);
}
```

Spring Data JPA understands:

```
findByCity(String city)
```

and internally creates query like:

```
SELECT name, email F
ROM users 
WHERE city = ?;
```

### Controller

```
package com.example.demo.controller;

import com.example.demo.projection.UserSummaryProjection;
import com.example.demo.repository.UserRepository;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserRepository userRepository;

    public UserController(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @GetMapping("/summary")
    public List<UserSummaryProjection> getUserSummary(@RequestParam String city) {
        return userRepository.findByCity(city);
    }
}
```

### API

```
GET /api/users/summary?city=Bangalore
```

Response:

```
[
  {
    "name": "Prashant",
    "email": "p@gmail.com"
  }
]
```

##  DTO/Class-based Projection

Use this when you want a proper DTO object.

### DTO

```
package com.example.demo.dto;

public class UserSummaryDto {

    private String name;
    private String email;

    public UserSummaryDto(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public String getName() { return name; }
    public String getEmail() { return email; }
}
```

### Repository with JPQL

```
package com.example.demo.repository;

import com.example.demo.dto.UserSummaryDto;
import com.example.demo.entity.User;
import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;

import java.util.List;

public interface UserRepository extends JpaRepository<User, Long> {

    @Query("""
           SELECT new com.example.demo.dto.UserSummaryDto(u.name, u.email)
           FROM User u
           WHERE u.city = :city
           """)
    List<UserSummaryDto> findUserSummaryDtoByCity(@Param("city") String city);
}
```

Important:

```
SELECT new packageName.DtoName(...)
```

This is called **constructor expression**.

---

## ==Native Query with Projection==

Native query means writing real SQL:

```
SELECT name, email FROM users WHERE city = 'Bangalore';
```

Spring Data JPA supports native queries using `@Query(nativeQuery = true)`. For interface projections with native queries, column aliases must match getter names.

### Interface Projection for Native Query

```
package com.example.demo.projection;

public interface UserNativeProjection {
    String getName();
    String getEmail();
}
```

### Repository

```
@Query(
    value = """
            SELECT 
                u.name AS name,
                u.email AS email
            FROM users u
            WHERE u.city = :city
            """,
    nativeQuery = true
)
List<UserNativeProjection> findNativeUserSummaryByCity(@Param("city") String city);
```

This works because:

```
u.name AS name   -> getName()
u.email AS email -> getEmail()
```

If your DB column is snake_case:

```
SELECT 
    u.full_name AS name,
    u.email_address AS email
FROM users u;
```

Then also it works because alias matches projection method.

---

## ==Native Query with DTO Class==

This is more tricky.

This may not work directly:

```
@Query(value = "SELECT name, email FROM users", nativeQuery = true)
List<UserSummaryDto> findUsers();
```

Because Spring may not know how to convert native SQL result into your DTO constructor automatically. For native queries, interface projection is usually easier. For class-based DTO with native SQL, you often need `@SqlResultSetMapping` or manual mapping.

Best beginner-friendly approach:

```
@Query(
    value = """
            SELECT 
                u.name AS name,
                u.email AS email
            FROM users u
            WHERE u.city = :city
            """,
    nativeQuery = true
)
List<UserNativeProjection> findNativeUserSummaryByCity(@Param("city") String city);
```

Then convert to DTO in service if needed.

---

### Service Layer Example

```
package com.example.demo.service;

import com.example.demo.dto.UserSummaryDto;
import com.example.demo.projection.UserNativeProjection;
import com.example.demo.repository.UserRepository;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public List<UserSummaryDto> getUsersByCity(String city) {
        List<UserNativeProjection> users =
                userRepository.findNativeUserSummaryByCity(city);

        return users.stream()
                .map(u -> new UserSummaryDto(u.getName(), u.getEmail()))
                .toList();
    }
}
```

---

## Final Interview Explanation

You can say:

> Projection in Spring Data JPA is used to fetch only required fields from the database instead of loading the complete entity. It improves performance, reduces network payload, and prevents exposing sensitive fields like passwords. Spring Data JPA supports interface-based projections, DTO/class-based projections, and projections with JPQL or native queries. In native queries, interface projection works well if SQL column aliases match projection getter names.

---

### When to Use What?

| Use case                   | Best option                |
| -------------------------- | -------------------------- |
| Simple selected fields     | Interface projection       |
| API response DTO           | DTO projection             |
| Custom JPQL query          | DTO constructor expression |
| Native SQL query           | Interface projection       |
| Complex native DTO mapping | `@SqlResultSetMapping`     |
| Need to update entity      | Fetch full entity          |

---

Main rule:

```
Entity = when you want full object and maybe update it.
Projection = when you only want read-only selected fields.
```

# what is JOIN FETCH ?

## Interview Definition

> `JOIN FETCH` is a JPQL feature used to load an entity and its associated entities in a single database query. It helps avoid the N+1 query problem and improves performance by reducing the number of SQL queries executed.

### Simple Rule

```
Need related data immediately?
→ Use JOIN FETCH

Need entity only?
→ Keep LAZY

Need different fetch plans for different APIs?
→ Use Entity Graph
```

So the relationship is:

```
LAZY = Default choice
JOIN FETCH = Load relationship for one specific query
@EntityGraph = Load relationship for one specific repository method in a cleaner way
```

That's why people often say:

> "Entity Graph is a cleaner alternative to JOIN FETCH for many use cases."


## difference b/w JOINS and FETCH JOINS ?

This is exactly where most developers get confused.

You are thinking:

> "Both JOIN and JOIN FETCH generate JOIN SQL. Then what's the difference?"

The difference is **not in SQL syntax**.

The difference is:

> **What Hibernate does with the joined data after getting it from the database.**

Let's build intuition.

---

### Imagine these entities

```
User
   |
   | OneToMany
   ↓
Order
```

```
@Entity
class User {

    Long id;
    String name;

    @OneToMany(mappedBy="user", fetch=LAZY)
    List<Order> orders;
}
```

---

## Case 1: Normal JOIN

JPQL:

```
@Query("""
    SELECT u
    FROM User u
    JOIN u.orders o
    WHERE o.productName = 'Laptop'
""")
List<User> findUsers();
```

Notice:

```
JOIN u.orders o
```

NOT

```
JOIN FETCH
```

---

### What Hibernate's goal is?

Goal:

```
Find users who purchased Laptop
```

Hibernate uses Orders table ONLY for filtering.

---

### SQL

```
select u.*
from users u
join orders o
  on u.id = o.user_id
where o.product_name = 'Laptop';
```

Database returns:

```
User(1, Prashant)
```

Hibernate creates:

```
User
```

But:

```
user.orders
```

is still NOT loaded.

Because you never asked Hibernate to load orders.

---

### Later

```
user.getOrders()
```

Hibernate says:

```
Oops...
Orders are LAZY.
Need another query.
```

Runs:

```
select *
from orders
where user_id = 1;
```

Extra query.

---

## Case 2: JOIN FETCH

JPQL:

```
@Query("""
    SELECT u
    FROM User u
    JOIN FETCH u.orders
""")
List<User> findUsers();
```

---

Now Hibernate's goal is different.

Goal:

```
Load User
AND
Load Orders also
```

---

### SQL

Looks very similar:

```
select u.*, o.*
from users u
join orders o
  on u.id = o.user_id;
```

You look at SQL and think:

```
Same SQL !!
```

Yes.

The database doesn't know what "FETCH" means.

**FETCH is a Hibernate/JPA instruction, not a SQL instruction.**

---

### What happens after SQL returns?

Database returns:

```
User1 + Order101
User1 + Order102
```

Hibernate sees:

```
Ah!Developer used JOIN FETCH.
```

So it builds:

```
User {
   id = 1,
   orders = [
      Order101,
      Order102
   ]
}
```

Orders are already populated.

No extra query later.

JOIN - `Use relationship for filtering Does not Solve N+1 problem.`

FETCH JOIN - `Load relationship data eagerly in this query. Solve N+1 problem.`
