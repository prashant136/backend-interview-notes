## What is projection in spring boot ? How does Spring Data JPA work with native queries and projections ?

### Native Query

Normally, JPA uses **JPQL**.

JPQL

```java
@Query("SELECT p FROM Product p WHERE p.price > :price")
```

Here, `Product` is the **Entity**, not the table.

---

Sometimes JPQL cannot do what we want.

For example,

- Database-specific functions
- Complex JOINs
- CTE (WITH clause)
- Window functions
- Performance tuning

Then we use **Native SQL**.

```java
@Query(
    value = "SELECT * FROM product WHERE price > :price",
    nativeQuery = true
)
List<Product> findProducts(int price);
```

Here, we're writing actual SQL.

---

### What is Projection?

Suppose Product table

|id|name|price|description|category|
|---|---|---|---|---|

Your UI only needs
- name
- price

Why fetch everything?

fetch

```

price
```

This is called **Projection**.

Result

```

```

Only two columns are fetched.

```

-------

name
price

```

Interface

```java

    String getName();

    Integer getPrice();
}
```

Repository


## What is entity graph in spring ? How do you use Entity Graphs for optimizing queries ?

This is an **interview favorite** because it is one of the solutions to the **N+1 Query Problem**.

---

> **An Entity Graph tells JPA exactly which related entities should be fetched in a particular query.**

Instead of changing the relationship to `EAGER`, you can **keep it `LAZY`** and fetch related entities **only when needed**.

---

#### Real-world Analogy

Imagine you're ordering food.

Normally (`LAZY`):

```
Burger
```

Later you realize you need fries.

```
Burger
↓
Go back
↓
Order Fries
```

Extra trip (extra SQL query).

With **Entity Graph**, you tell the waiter beforehand:

```
Burger + Fries
```

Everything comes together in **one trip (one SQL query).**

---

#### Example

Suppose:

```
Customer
      |
      | OneToMany
      |
    Orders
```

By default:

```java
@Entity
public class Customer {

    @OneToMany(mappedBy = "customer", fetch = FetchType.LAZY)
    private List<Order> orders;
}
```

We keep it **LAZY** (recommended).

---

#### Without Entity Graph

```java
List<Customer> customers = repository.findAll();

for(Customer c : customers){
    System.out.println(c.getOrders().size());
}
```

SQL:

```sql
SELECT * FROM customer;

SELECT * FROM orders WHERE customer_id = 1;

SELECT * FROM orders WHERE customer_id = 2;

SELECT * FROM orders WHERE customer_id = 3;
```

This is **N+1**.

---

#### With Entity Graph

Repository

```java
public interface CustomerRepository extends JpaRepository<Customer, Long> {

    @EntityGraph(attributePaths = "orders")
    List<Customer> findAll();
}
```

Now,

```java
List<Customer> customers = repository.findAll();
```

JPA automatically fetches:

```sql
SELECT *
FROM customer c
LEFT JOIN orders o
ON c.id = o.customer_id;
```

Only **one query**.

---

#### Multiple Relationships

Suppose:

```
Customer
    |
    +------ Orders
    |
    +------ Address
```

You can fetch both.

```java
@EntityGraph(attributePaths = {
    "orders",
    "address"
})
List<Customer> findAll();
```

JPA fetches both relationships in one query (or an optimized set of queries depending on the provider).

---

#### Interview Answer (30 seconds)

> **Entity Graph is a JPA feature that allows us to specify which related entities should be fetched for a particular query. It helps optimize performance by keeping relationships `LAZY` by default while fetching only the required associations when needed. This reduces unnecessary database queries and is commonly used to avoid the N+1 query problem without changing the fetch type to `EAGER`.**

---

### One-line memory aid

> **`@EntityGraph` = "Keep entities LAZY, but fetch the required relationships in one query for this method."**


### 📝 Refined Question

I am building a product catalog system with the following database tables and relationships:

- **`brands`**: Stores company/user information.
- **`catalog`**: Has 10 fields, including `catalog_id`, `brand_id`, `catalog_name`, `status`, etc.
- **`product_set`**: Represents groups of items. It has a **Many-to-One** relationship with `catalog` via `catalog_id`. (One Catalog can have \(N\) Product Sets).

**Frontend Workflow:**

1. The user visits the page and fetches all catalogs (`GET /catalogs`) to populate a select dropdown menu.
2. The user selects a specific catalog from the dropdown.
3. Based on that `catalog_id`, the frontend makes a second API call to fetch only the related product sets for that specific catalog.

**My Questions:**

1. **System Design & Architecture:** Given my frontend workflow (Step 1 fetches only Catalogs, Step 2 fetches Product Sets separately via a specific `catalog_id`), **do I actually need an Entity Graph here?** Or is Entity Graph designed for a completely different use case?
2. **How `@EntityGraph` Works:** I am confused about what `@EntityGraph(attributePaths = ...)` actually fetches from the database. When I specify an attribute path, what is Hibernate doing behind the scenes, and what data gets loaded into memory?

This is exactly where many developers get confused. The key point is:

> **`@EntityGraph` is NOT for calling multiple APIs. It is for optimizing how a _single JPA query_ loads related entities from the database.**

Let's use your example.

---

### Your Database

#### Catalog

```
catalog
----------------------------
catalog_id (PK)
brand_id
catalog_name
catalog_rules
last_exported_at
status
node_mapping
node_available
...
```

#### Product Set

```
product_set
----------------------------
product_set_id (PK)
catalog_id (FK)
filters
product_set_name
product_set_image_link
```

Relationship

```
Catalog
   |
   | One
   |
   |-------> Many ProductSets
```

Entity

```java
@Entity
class Catalog {

    @Id
    private Long catalogId;

    private String catalogName;

    @OneToMany(mappedBy = "catalog", fetch = FetchType.LAZY)
    private List<ProductSet> productSets;
}
```

---

### Your Frontend Flow

```
GET /catalogs
      ↓
Dropdown shows catalogs
      ↓
User selects Catalog 101
      ↓
GET /catalogs/101/product-sets
      ↓
Display Product Sets
```

### Do we need EntityGraph here?

**No.**

Why?

Because the second API only needs ProductSets.

Repository can simply do

```java
List<ProductSet> findByCatalogId(Long catalogId);
```

SQL

```sql
SELECT *
FROM product_set
WHERE catalog_id = 101;
```

Only one query.

No N+1.

No EntityGraph.

This is already optimal.

---

### When would EntityGraph be useful?

Suppose your UI changes.

Instead of only showing catalog names, the UI shows:

```
Catalog Name      Product Set Count

Electronics             25
Fashion                 18
Shoes                   42
```

Now your service does

```java
List<Catalog> catalogs = catalogRepository.findAll();

for (Catalog catalog : catalogs) {

    System.out.println(
        catalog.getProductSets().size()
    );
}
```

Because ProductSets are LAZY,

JPA executes

```sql
SELECT * FROM catalog;

SELECT * FROM product_set WHERE catalog_id=1;

SELECT * FROM product_set WHERE catalog_id=2;

SELECT * FROM product_set WHERE catalog_id=3;

...
```

This is N+1.

---

Now use EntityGraph.

```java
@EntityGraph(attributePaths = "productSets")
List<Catalog> findAll();
```

JPA fetches

```
Catalog
+
ProductSets
```

in one optimized query.

No N+1.

-----

The `attributePaths` parameter tells JPA exactly **which related tables to JOIN and fetch immediately** in a single database hit, overriding the default `FetchType.LAZY` setting.

Whatever field name you put inside `attributePaths` will be pulled into memory right away instead of being queried later.

## What is JOIN FETCH ?

### Interview Definition

> `JOIN FETCH` is a JPQL feature used to eagerly load associated entities in a single SQL query. It helps eliminate the N+1 Query Problem by fetching the parent entity and its related entities together using a SQL JOIN.

### Simple Rule

```
Need related data immediately?
→ Use JOIN FETCH

Need entity only?
→ Keep LAZY

Need different fetch plans for different APIs?
→ Use Entity Graph
```

So the relationship is:

```
LAZY = Default choice
JOIN FETCH = Load relationship for one specific query
@EntityGraph = Load relationship for one specific repository method in a cleaner way
```

### Memory Trick

```
Without JOIN FETCH

Customer
   ↓
Orders
   ↓
Orders
   ↓
Orders

1 + N Queries ❌
```

```
With JOIN FETCH

Customer JOIN Orders

↓

1 Query ✅
```

### One-line interview summary

> **`JOIN FETCH` = Fetch related entities in a single query to avoid the N+1 Query Problem.**

## How do you define a Named Query using @NamedQuery annotation? What is the difference between @NamedQuery and @NamedNativeQuery ?

### What is a Named Query?

> **A Named Query is a JPQL query defined once (usually in the entity) and reused multiple times by its name.**

Instead of writing the query every time, you give it a name.


```java
@Entity
@NamedQuery(
    name = "Product.findByName",
    query = "SELECT p FROM Product p WHERE p.name = :name"
)
public class Product {

    @Id
    private Long id;

    private String name;
}
```

---

### What is `@NamedNativeQuery`?

> **A Named Native Query is a reusable SQL query written using the database's native SQL syntax.**


```java
@Entity
@NamedNativeQuery(
    name = "Product.findByNameNative",
    query = "SELECT * FROM product WHERE name = :name",
    resultClass = Product.class
)
public class Product {

    @Id
    private Long id;

    private String name;
}
```


---

### Difference

| `@NamedQuery`                 | `@NamedNativeQuery`                     |
| ----------------------------- | --------------------------------------- |
| Uses **JPQL**                 | Uses **Native SQL**                     |
| Refers to **Entity & fields** | Refers to **Database tables & columns** |
| Database independent          | Database specific                       |
| More portable                 | Can use DB-specific SQL features        |

### Which one should you prefer?

- ✅ Use **`@NamedQuery`** for most cases because it's portable and works across databases.
- ✅ Use **`@NamedNativeQuery`** only when you need database-specific SQL, complex joins, CTEs, window functions, or other features JPQL doesn't support.

---

# Interview Answer (30 seconds)

> **`@NamedQuery` defines a reusable JPQL query identified by a name. It works with entity names and entity fields, making it database-independent. `@NamedNativeQuery` defines a reusable native SQL query using actual table and column names. It is useful when JPQL is not sufficient or when database-specific SQL features are required.**

### Modern Spring Boot Reality

In most modern Spring Boot projects:

```
Derived Queries
(findByEmail)

+
@Query

+
EntityGraph

+
Specifications
```

are used far more frequently.

`@NamedQuery` and `@NamedNativeQuery` are still supported and useful, but you will see them less often than `@Query` in many modern codebases. They are worth knowing for interviews because they demonstrate understanding of JPA query management and startup-time validation.

## How does Spring Data JPA resolve Named Queries internally ?

This is actually a very good senior-level interview question because it tests whether you understand what happens **behind the repository method call**.

### Interview Answer (30 seconds)

> **When Spring Data JPA starts, it scans all entities for `@NamedQuery` and `@NamedNativeQuery` annotations. If a repository method matches a Named Query's name, Spring executes that Named Query instead of generating a query from the method name. If no Named Query is found, Spring tries to derive the query from the repository method name.**

---

### Internal Flow

Suppose you have:

```java
@Entity
@NamedQuery(
    name = "Product.findByName",
    query = "SELECT p FROM Product p WHERE p.name = :name"
)
public class Product {
}
```

Repository:

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    List<Product> findByName(String name);
}
```

---

Spring Boot starts.

↓

JPA scans all entities.

↓

It registers

```
Product.findByName
```

inside the `EntityManagerFactory`.

↓

You call

```
repository.findByName("iPhone");
```

↓

Spring checks:

```
Is there a Named Query called

Product.findByName ?

Yes
```

↓


Execute that JPQL.

Spring **doesn't derive a query from the method name**.

---

### What if no Named Query exists?

Suppose

```java
List<Product> findByPrice(int price);
```

No

```java
@NamedQuery(name="Product.findByPrice")
```

exists.

Spring automatically generates

```sql
SELECT p
FROM Product p
WHERE p.price = ?
```

This is called **Query Derivation**.

---

### Search Order [ (Important for Interview) ] 

```
	Repository Method
	       │
	       ▼
	Named Query exists?
	        │
	   Yes  ▼    No
   Execute     Derive query from method name
  NamedQuery
```


This **"Named Query first, Query Derivation second"** rule is the key point interviewers usually want to hear.

## What is the precedence between Named Queries and @Query annotation in Spring Data JPA? How do you override a Named Query defined in an entity?

### Precedence Order

Spring Data JPA follows this order:

```
1. @Query          ✅ Highest Priority
2. @NamedQuery
3. Query Derivation (Method Name)
```

---

### Example

#### Entity

```java
@Entity
@NamedQuery(
    name = "Product.findByName",
    query = "SELECT p FROM Product p WHERE p.name = :name"
)
public class Product {
}
```

---

#### Repository

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Query("SELECT p FROM Product p WHERE p.name = :name AND p.price > 1000")
    List<Product> findByName(String name);
}
```

---

### What happens?

When you call:

```java
repository.findByName("iPhone");
```

Spring sees:

- ✅ `@Query` exists
- ❌ Ignores the `@NamedQuery`
- Executes the `@Query`

---

### How do you override a Named Query?

Simply add an `@Query` annotation to the repository method.

```java
@Query("SELECT p FROM Product p WHERE p.price > :price")
List<Product> findByName(int price);
```

Even if a `@NamedQuery` with the same method name exists, Spring will use the `@Query` because it has higher precedence.

---

### What if there is no `@Query`?

Spring checks for a matching `@NamedQuery`.

If found:

```
Execute NamedQuery
```

---

### What if neither exists?

Spring derives the query from the method name.

```java
List<Product> findByPrice(int price);
```

becomes something like:

```sql
SELECT p
FROM Product p
WHERE p.price = ?
```

---

### Interview Answer (20 seconds)

> **`@Query` has the highest precedence in Spring Data JPA. If a repository method is annotated with `@Query`, Spring executes it and ignores any matching `@NamedQuery`. If no `@Query` is present, Spring looks for a `@NamedQuery`. If neither exists, it derives the query from the repository method name. To override a Named Query, simply define an `@Query` on the repository method.**

## How do you define an index in JPA using annotations?

### How to define an Index in JPA?

Use the `@Table` annotation with `indexes`.


```java
@Entity
@Table(
    name = "product",
    indexes = {
        @Index(
            name = "idx_product_name",
            columnList = "name"
        )
    }
)
public class Product {

    @Id
    private Long id;

    private String name;

    private double price;
}
```

JPA generates SQL similar to:

```sql
CREATE INDEX idx_product_name
ON product(name);
```

---

### Composite Index (Multiple Columns)

```java
@Entity
@Table(
    indexes = {
        @Index(
            name = "idx_name_price",
            columnList = "name, price"
        )
    }
)
public class Product {
}
```

SQL:

```sql
CREATE INDEX idx_name_price
ON product(name, price);
```

### Memory Trick

```
@Table
   |
   +-- indexes
         |
         +-- @Index(name="...", columnList="...")
```
