## 1. JDBC (Java Database Connectivity)

### What is JDBC?

JDBC is a Java API that allows Java applications to communicate with databases.

It is provided by Java.

Think:

```
Java App

   |

### Problems with JDBC

Lots of boilerplate code.

```

Huge effort.

### What is ORM?

Before Hibernate understand ORM.

ORM = Object Relational Mapping

Problem:

```

Columns

Java uses:

```

Example:

### What is Hibernate?

Hibernate is an ORM Framework.
==**Hibernate** serves as the default object-relational mapping (ORM) framework implementation provided out of the box by the **Spring Data JPA** starter dependency==. Instead of writing manual SQL, you write Java code, and Hibernate translates your objects into relational database tables automatically.

It automates:

```

Table -> Object
```

## Interview Answer (2 Minutes)

**What is JDBC?**

> JDBC is a Java API used to connect Java applications with databases. It provides classes like Connection, PreparedStatement, and ResultSet. It requires writing SQL manually.

**What is Hibernate?**

> Hibernate is an ORM framework that maps Java objects to database tables and reduces JDBC boilerplate code. It internally uses JDBC.

**What is JPA?**

> JPA is a specification for ORM in Java. It defines standards like Entity, EntityManager, and relationships. Hibernate is the most popular implementation of JPA.

**What is MyBatis/iBatis?**

> MyBatis is a SQL mapping framework where developers write SQL manually and MyBatis maps the result to Java objects. It provides more SQL control than Hibernate.

**What is Spring Data JPA?**

> Spring Data JPA sits on top of JPA and Hibernate and automatically generates repository implementations. By extending JpaRepository, we get CRUD operations without writing implementation code.

# ==Use of transient Keyword?==

The `transient` keyword tells Java:

> "Do not serialize this field."

Serialization means converting an object into a byte stream so that it can be stored in a file, sent over a network, cached in Redis, etc.

Serialization and Deserialization are important Java mechanisms used to convert objects into a byte stream and reconstruct them back into objects. Together, they enable object persistence, data transfer, and communication between different systems while preserving an object's state.

- Serialization converts an object into a byte stream for storage or transmission.
- Deserialization converts the byte stream back into the original Java object.

---


```
import java.io.Serializable;

public class Employee implements Serializable {

    private int id;
    private String name;

    transient String password; // won't be serialized

    public Employee(int id, String name, String password) {
        this.id = id;
        this.name = name;
        this.password = password;
    }
}
```

---

### Without transient

```
Employee emp = new Employee(1, "Prashant", "secret123");
```

Serialized data:

```
id=1
name=Prashant
password=secret123
```

Password also gets stored.

---

### With transient

```
transient String password;
```

Serialized data:

```
id=1
name=Prashant
```

Password is ignored.

---

## Real-world Example

### User Entity

```
public class User implements Serializable {

    private Long id;
    private String username;

    transient String otp;

    transient String sessionToken;
}
```

We don't want:

- OTP
- Session Token
- Temporary Data

to be stored or transmitted.

---

## JPA Perspective

Many developers confuse:

```
transient
```

with

```
@Transient
```

These are different.

---

### Java transient

```
transient String password;
```

Ignored during Java Serialization.

---

### JPA @Transient

```
@Transientprivate String fullName;
```

Ignored by Hibernate/JPA.

No column will be created.

---

Example:

```
@Entity
public class Employee {

    private String firstName;

    private String lastName;

    @Transient
    private String fullName;
}
```

Database Table:

```
employee
---------
first_name
last_name
```

No `full_name` column.

---

## Interview Answer

> The transient keyword is used to exclude a field from Java serialization. When an object is converted into a byte stream, transient fields are not persisted. In JPA, if we want to exclude a field from database mapping, we use @Transient annotation instead of the transient keyword.

# ==What is the purpose of @GeneratedValue in JPA?  What are the different strategies supported by @GeneratedValue?  Explain the difference between GenerationType.AUTO, IDENTITY, SEQUENCE, and TABLE.


## Problem: Who will generate the Primary Key?

Suppose we have a User table:

```
@Entity
public class User {

    @Id
    private Long id;

    private String name;
}
```

When we save:

```
User user = new User();
user.setName("Prashant");

userRepository.save(user);
```

What should be the value of `id`?

```
id = ?
```

Options:

1. Java Application generates it.
2. Database generates it.

Without a strategy, JPA doesn't know how to generate the ID.


# All Strategies

```
@GeneratedValue(strategy = GenerationType.AUTO)

@GeneratedValue(strategy = GenerationType.IDENTITY)

@GeneratedValue(strategy = GenerationType.SEQUENCE)

@GeneratedValue(strategy = GenerationType.TABLE)
```

Let's understand each deeply.

# Comparison Table

|Strategy|Who Generates ID|Performance|Database|
|---|---|---|---|
|AUTO|Hibernate decides|Depends|Any|
|IDENTITY|Database AUTO_INCREMENT|Medium|MySQL|
|SEQUENCE|Database Sequence|Best|PostgreSQL, Oracle|
|TABLE|Generator Table|Poor|Any|

---

### Interview Answer (2-Min Version)

`@GeneratedValue` is used with `@Id` to automatically generate primary key values for entities.

JPA supports four strategies:

1. **AUTO** – Hibernate chooses the appropriate strategy based on the database.
2. **IDENTITY** – Uses database auto-increment columns. Common in MySQL.
3. **SEQUENCE** – Uses database sequence objects. Common in PostgreSQL and Oracle. Supports efficient batch inserts.
4. **TABLE** – Uses a separate table to maintain IDs. Portable but slower due to additional queries and locking.


# ==How does GenerationType.AUTO decide which strategy to use?==

This is where many developers get confused.

`GenerationType.AUTO` does **not** generate IDs itself.

It simply tells Hibernate:

> "You choose the best ID generation strategy for the database I'm using."

---

### How Hibernate Decides

When the application starts:

```
Spring Boot
    ↓
Hibernate
    ↓
Database Connection
    ↓
Read Database Metadata
```

Hibernate checks:

```
spring.datasource.url
```

Example:

```
jdbc:mysql://localhost:3306/mydb
```

Hibernate knows:

```
Database = MySQL
```

or

```
jdbc:postgresql://localhost:5432/mydb
```

Hibernate knows:

```
Database = PostgreSQL
```

---

### Example 1: PostgreSQL

Configuration:

```
spring.datasource.url=jdbc:postgresql://localhost:5432/shopdb
```

Entity:

```
@Entity
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.AUTO)
    private Long id;
}
```

Hibernate detects:

```
PostgreSQL
```

PostgreSQL supports sequences very efficiently.

Therefore Hibernate usually chooses:

```
SEQUENCE
```

and creates something like:

```
create sequence user_seq;
```

Internally it behaves almost like:

```
@GeneratedValue(strategy = GenerationType.SEQUENCE)
```

---

### Example 2: MySQL

Configuration:

```
spring.datasource.url=jdbc:mysql://localhost:3306/shopdb
```

Hibernate detects:

```
MySQL
```

Historically MySQL didn't support database sequences like PostgreSQL.

So Hibernate commonly uses an identity-style mechanism.

Effectively:

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

and table column becomes:

```
id BIGINT AUTO_INCREMENT
```

---

### Why Senior Developers Often Avoid AUTO

Consider:

Today:

```
Database = PostgreSQL
```

AUTO chooses:

```
SEQUENCE
```

Later company migrates to:

```
MySQL
```

AUTO may switch to:

```
IDENTITY
```

Now performance characteristics change.

Batch inserts may behave differently.

Because of this, many teams explicitly write:

```
@GeneratedValue(strategy = GenerationType.SEQUENCE)
```

or

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

so the behavior is obvious.

---

### Interview Answer

**How does `GenerationType.AUTO` decide which strategy to use?**

> `AUTO` delegates the decision to the JPA provider (typically Hibernate). Hibernate examines the database dialect at startup and selects the most appropriate identifier generation strategy supported by that database. For example, PostgreSQL and Oracle typically use `SEQUENCE`, while MySQL commonly uses `IDENTITY`. The exact choice can vary depending on the Hibernate version and database capabilities. Therefore, many production applications prefer explicitly specifying `SEQUENCE` or `IDENTITY` instead of relying on `AUTO`.



# ==When would you use GenerationType.SEQUENCE over IDENTITY ? batch insert performance ? batch insert in postgres and mysql. (possibilities and best practice). is this the reason behind why postgres is write heavy and mysql is read heavy ?== 

Yes, **performance and batch insert** is the main reason to prefer `SEQUENCE` over `IDENTITY`, especially in **PostgreSQL + Hibernate**.

## 1. Core difference

### IDENTITY

Database generates ID **during INSERT**.

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Flow:

```
Hibernate: INSERT user
Database: generates id
Hibernate: waits for generated id
```

So Hibernate cannot know the ID before insert.

Result:

```
insert one row → wait
insert one row → wait
insert one row → wait
```

This hurts batching.

---

### SEQUENCE

Hibernate gets ID **before INSERT**.

```
@GeneratedValue(strategy = GenerationType.SEQUENCE)
private Long id;
```

Flow:

```
Hibernate: SELECT nextval('user_seq')
Database: gives id 101
Hibernate: INSERT user with id 101
```

Hibernate already knows IDs before inserting.

Result:

```
get ids first
then batch multiple inserts together
```

Better for write-heavy systems.

---

## 2. Why SEQUENCE is better for batch inserts

Suppose you save 1000 users.

### With IDENTITY

Hibernate usually has to do:

```
INSERT user 1 → get id
INSERT user 2 → get id
INSERT user 3 → get id
...
INSERT user 1000 → get id
```

Hard to batch efficiently.

---

### With SEQUENCE

Hibernate can do:

```
Get ids: 1 to 1000
Batch INSERT users together
```

Example:

```
insert into users (id, name) values (?, ?)
insert into users (id, name) values (?, ?)
insert into users (id, name) values (?, ?)
```

These can be sent in batches.

---

## 3. PostgreSQL best practice

For PostgreSQL, prefer:

```
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
@SequenceGenerator(
    name = "user_seq",
    sequenceName = "user_sequence",
    allocationSize = 50
)
private Long id;
```

Important part:

```
allocationSize = 50
```

This means Hibernate can reserve IDs in chunks.

Example:

```
Hibernate asks DB once
DB gives range 1-50
Hibernate uses those IDs in memory
```

This reduces database round trips.

Good for:

```
high insert volume
bulk import
orders
payments
logs
catalog ingestion
event tables
```

---

## 4. MySQL best practice

MySQL commonly uses:

```
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Because MySQL traditionally uses:

```
AUTO_INCREMENT
```

Example:

```
id BIGINT AUTO_INCREMENT PRIMARY KEY
```

For normal CRUD apps, this is fine.

But for huge batch inserts, `IDENTITY` is less efficient with Hibernate.

---

## 5. Can MySQL do batch inserts?

Yes, MySQL can do batch inserts at SQL level:

```
insert into users(name) values
('A'),
('B'),
('C');
```

But with JPA/Hibernate + `GenerationType.IDENTITY`, batching is limited because Hibernate needs generated IDs immediately.

So:

```
MySQL database supports batch insert
but Hibernate + IDENTITY makes batching harder
```

That is the important interview point.

---

## 6. Can PostgreSQL use IDENTITY?

Yes.

PostgreSQL supports identity columns:

```
id BIGINT GENERATED BY DEFAULT AS IDENTITY
```

And Hibernate can use:

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

But in Hibernate/JPA, for write-heavy apps, PostgreSQL `SEQUENCE` is usually preferred because it works better with batching.

---

## 7. Is this why PostgreSQL is write-heavy and MySQL is read-heavy?

Not exactly.

This ID generation difference is **one small reason**, not the full reason.

PostgreSQL is often preferred for complex/write-heavy systems because of:

```
strong ACID behavior
MVCC implementation
advanced locking
better concurrency for complex workloads
powerful indexing
JSONB
CTEs
window functions
partial indexes
transactional DDL
rich query planner
sequence support
```

MySQL is often used for read-heavy web apps because:

```
simple setup
fast primary-key reads
replication ecosystem
widely used with read replicas
good for simple OLTP workloads
easy horizontal read scaling
```

But saying:

```
Postgres = write-heavy
MySQL = read-heavy
```

is too simplistic.

Better interview answer:

> PostgreSQL is often chosen for complex transactional and write-heavy workloads because of its strong consistency, MVCC, advanced indexing, rich SQL features, and sequence-based ID generation. MySQL is often chosen for simpler high-read web workloads because it is easy to operate, performs very well for primary-key reads, and has strong replication support. But both databases can handle reads and writes well when designed properly.

---

## Final rule

Use this:

```
PostgreSQL + Hibernate + high inserts → SEQUENCE
MySQL + normal CRUD → IDENTITY
Legacy/portable DB → AUTO or TABLE rarely
Production code → avoid AUTO, be explicit
```

# ==What is CrudRepository and JpaRepository ?==

## Problem Before Spring Data JPA

Suppose you have a `User` entity.

```
@Entity
public class User {

    @Id
    private Long id;

    private String name;
    private String email;
}
```

Without Spring Data JPA, you would write all database operations manually.

```
@Repository
public class UserRepository {

    @PersistenceContext
    private EntityManager entityManager;

    public void save(User user) {
        entityManager.persist(user);
    }

    public User findById(Long id) {
        return entityManager.find(User.class, id);
    }

    public void delete(User user) {
        entityManager.remove(user);
    }
}
```

Imagine doing this for:

- User
- Product
- Order
- Employee
- Customer

You would write the same CRUD code again and again.

Spring Data JPA solves this problem.

---

## What is Repository?

he **Repository Layer** (also called the Data Access Layer) in **Spring Boot** ==manages database interactions, handling operations like saving, fetching, updating, and deleting records==

```
User user = repository.findById(1L);
```

instead of writing SQL manually.

---

## What is CrudRepository?

Spring provides an interface called:

```
CrudRepository
```

It already contains basic CRUD methods.

```
public interface CrudRepository<T, ID>
```

Where:

```
T  = Entity
ID = Primary Key Type
```

Example:

```
public interface UserRepository
        extends CrudRepository<User, Long> {
}
```

Now Spring automatically gives you:

```
save()
findById()
findAll()
delete()
deleteById()
existsById()
count()
```

without writing any implementation.

## What is JpaRepository?

`JpaRepository` is an advanced version of CrudRepository.

Hierarchy:

```
Repository      ↑CrudRepository      ↑PagingAndSortingRepository      ↑JpaRepository
```

So:

```
JpaRepository
```

already contains everything from:

- Repository
- CrudRepository
- PagingAndSortingRepository

plus extra JPA features.

---

### Using JpaRepository

```
public interface UserRepository
        extends JpaRepository<User, Long> {
}
```

### Real Production Example

Imagine an E-Commerce Application.

Entity:

```
@Entity
public class Product {
    @Id
    private Long id;

    private String name;
    private Double price;
}
```

Repository:

```
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
```

Service:

```
@Service
public class ProductService {

    @Autowired
    private ProductRepository repository;

    public Product create(Product product) {
        return repository.save(product);
    }

    public Product get(Long id) {
        return repository.findById(id)
                .orElseThrow();
    }

    public List<Product> getAll() {
        return repository.findAll();
    }

    public void delete(Long id) {
        repository.deleteById(id);
    }
}
```

No SQL.  
No implementation class.

Spring generates everything.

---

## Which One Should You Use?

### Interviews

> CrudRepository provides basic CRUD operations.

> JpaRepository extends PagingAndSortingRepository which extends CrudRepository.

> JpaRepository provides all CRUD features plus pagination, sorting, batch operations, flush
and other JPA-specific functionality.

> In modern Spring Boot applications, JpaRepository is generally preferred because it
includes all capabilities of CrudRepository along with additional enterprise-level features.

### Most Used Methods in Real Projects

If you're joining as a Java Backend Developer, you'll use these daily:

```
save()

saveAll()

findById()

findAll()

findAll(Pageable)

findAll(Sort)

count()

existsById()

findAllById()

saveAndFlush()

getReferenceById()

deleteAllInBatch()

flush()

Custom Queries:
findByEmail()
findByName()
existsByEmail()
```

# ==JPQL queries ? How do you use @Query annotation for custom JPQL queries ?==

##  What is JPQL?

**JPQL = Java Persistence Query Language**

It looks like SQL, but it works on **Entity class names and Java field names**, not table names and column names.

Suppose entity:

```
@Entity
@Table(name = "users")
public class User {

    @Id
    private Long id;

    private String name;

    private String email;

    private String status;
}
```

SQL uses table/column:

```
SELECT * FROM users WHERE email = 'abc@gmail.com';
```

JPQL uses entity/field:

```
SELECT u FROM User u WHERE u.email = :email
```

Important difference:

```
SQL  → table name, column name
JPQL → entity name, field name
```

---

## Why do we need custom JPQL queries?

Spring Data JPA can generate queries automatically:

```
User findByEmail(String email);
```

But sometimes method names become too long:

```
List<User> findByStatusAndNameContainingIgnoreCaseOrderByNameAsc(...)
```

For complex conditions, joins, projections, update queries, we use:

```
@Query
```


---

## Full Example

### Entity

```
@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    private String status;
    private Integer age;
}
```

### Repository

```
public interface UserRepository extends JpaRepository<User, Long> {

    @Query("SELECT u FROM User u WHERE u.email = :email")
    Optional<User> findByEmailCustom(String email);

    @Query("SELECT u FROM User u WHERE u.status = :status")
    List<User> findByStatusCustom(String status);

    @Query("SELECT u FROM User u WHERE u.age >= :age")
    List<User> findUsersOlderThan(Integer age);
}
```

### Service

```
@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public Optional<User> getUserByEmail(String email) {
        return userRepository.findByEmailCustom(email);
    }
}
```


---

## Named Parameter with `@Param`

Sometimes use `@Param` for clarity.

```
@Query("SELECT u FROM User u WHERE u.email = :email")
Optional<User> findByEmailCustom(@Param("email") String email);
```

Recommended for interviews and production.

---

## Multiple Parameters

```
@Query("""
       SELECT u
       FROM User u
       WHERE u.status = :status
       AND u.age >= :age
       """)
List<User> findActiveUsersAboveAge(
        @Param("status") String status,
        @Param("age") Integer age
);
```

Equivalent SQL:

```
SELECT *
FROM users
WHERE status = 'ACTIVE'
AND age >= 18;
```

---

## LIKE Query

```
@Query("SELECT u FROM User u WHERE u.name LIKE %:keyword%")
List<User> searchByName(@Param("keyword") String keyword);
```

SQL:

```
SELECT *
FROM users
WHERE name LIKE '%rah%';
```

Better version:

```
@Query("""
       SELECT u
       FROM User u
       WHERE LOWER(u.name) LIKE LOWER(CONCAT('%', :keyword, '%'))
       """)
List<User> searchByNameIgnoreCase(@Param("keyword") String keyword);
```

---

## IN Query

# ==What is the role of EntityManager in Spring Data JPA?==


**EntityManager is the core JPA interface that manages the lifecycle of entities and performs database operations.**

Think of it as:

> EntityManager = Bridge between Java Objects and Database Tables

When you save, update, delete, or fetch an entity, ultimately the work is performed through EntityManager.

---

### Real World Analogy

Suppose:

- Database = Warehouse
- Entity = Product
- EntityManager = Warehouse Manager

You don't directly enter the warehouse and move products.

Instead:

1. Tell the manager to add a product
2. Tell the manager to update a product
3. Tell the manager to remove a product

The manager handles everything.

Similarly:

```
entityManager.persist(user);
entityManager.merge(user);
entityManager.remove(user);
entityManager.find(User.class, 1);
```

EntityManager performs the actual database operations.

---

### Why do we need EntityManager?

Without JPA:

```
Connection conn = ...
PreparedStatement ps = ...
ResultSet rs = ...
```

Lots of boilerplate code.

With JPA:

```
entityManager.find(User.class, 1);
```

Much simpler.

---

## Main Responsibilities of EntityManager

### 1. Persist Entity

Save object into database.

```
User user = new User();
user.setName("Prashant");

entityManager.persist(user);
```

Generated SQL:

```
INSERT INTO users(name)
VALUES('Prashant');
```

---

### 2. Fetch Entity

```
User user =
    entityManager.find(User.class, 1L);
```

Generated SQL:

```
SELECT *
FROM users
WHERE id = 1;
```

---

### 3. Update Entity

```
user.setName("John");

entityManager.merge(user);
```

Generated SQL:

```
UPDATE users
SET name='John'
WHERE id=1;
```

---

### 4. Delete Entity

```
entityManager.remove(user);
```

Generated SQL:

```
DELETE FROM users
WHERE id=1;
```


# ==What is Persistence Context ?==

In the Java Persistence API (JPA), the **persistence context** is ==an in-memory staging area and first-level cache where entity instances are managed by an== `EntityManager`. It serves as a buffer between your Java application and the underlying relational database, ensuring that object state changes are tracked and accurately synchronized.

> Persistence Context is like a temporary memory/cache where Hibernate keeps entities before finally syncing changes with the database.

It is also called:

```
First Level Cache
```

Every `EntityManager` has one Persistence Context.


# ==Entity States==

EntityManager manages entity lifecycle.

An entity can be in 4 states.

### 1. Transient

Object exists in Java only.

```
User user = new User();
```

Not saved.

---

### 2. Managed

Entity is tracked by EntityManager.

```
entityManager.persist(user);
```

Now EntityManager watches changes.

---

### 3. Detached

EntityManager no longer tracks it.

```
entityManager.detach(user);
```

---

### 4. Removed

Marked for deletion.

```
entityManager.remove(user);
```

# ==Dirty Checking==

## Step 1: First Understand the Big Picture

Suppose we have:

```
User user = entityManager.find(User.class, 1L);
```

What happens?

```
Database
    ↓
SELECT * FROM users WHERE id=1
    ↓
User Object Created
    ↓
Stored inside Persistence Context
```

Now EntityManager starts managing this object.

```
Persistence Context

User(id=1,name="John")
```

This is called a **Managed Entity**.

---

## Question

Now suppose:

```
user.setName("Prashant");
```

You never wrote:

```
userRepository.save(user);
```

You never wrote:

```
entityManager.merge(user);
```

So how does Hibernate know something changed?

Answer:

```
Dirty Checking
```

---

## What is Dirty Checking?

Dirty Checking means:

> Hibernate automatically detects changes made to managed entities.

---

## Real Life Example

Suppose EntityManager keeps a photo of your entity.

Initial state:

```
User
id=1
name=John
```

Hibernate secretly stores:

```
Original Snapshot

id=1
name=John
```

Now you modify:

```
user.setName("Prashant");
```

Current state:

```
User
id=1
name=Prashant
```

Hibernate compares:

```
Snapshot      Current

John      vs  Prashant
```

Difference found.

```
Entity is Dirty
```

Meaning:

```
Entity Changed
```

This process is called:

```
Dirty Checking
```

---



```
@Transactional
public void updateUser() {

    User user =
        entityManager.find(User.class,1L);

    user.setName("Prashant");
}
```

Flow:

```
Database
   ↓
Fetch User
   ↓
Persistence Context
   ↓
Managed Entity
   ↓
Modify Name
   ↓
Dirty Checking detects change
   ↓
Flush
   ↓
Update SQL generated
   ↓
Commit
```

---

## Important [Interview Definition]

**Dirty Checking is a Hibernate mechanism that automatically detects changes made to managed entities inside the Persistence Context and synchronizes those changes with the database during flush/commit.**

---

## When Does Dirty Checking Work?

ONLY for:

```
Managed Entities
```

Example:

```
User user = entityManager.find(User.class,1L);
```

Managed.

Dirty checking works.

---

Example:

```
User user = new User();
user.setName("Prashant");
```

Not managed.

Dirty checking doesn't work.

Need:

```
entityManager.persist(user);
```

---

## Now Understand Flush

This is where most beginners get confused.

---

### What is Flush?

Flush means:

> Synchronize Persistence Context changes to the database.

Important:

```
Flush != Commit
```

Most people think they are same.

They are NOT.

---

### Real Life Analogy

Imagine writing answers in an exam.

```
Notebook = Persistence Context

Teacher's Register = Database
```

You write:

```
Answer 1
Answer 2
Answer 3
```

Still not submitted.

This is:

```
Persistence Context
```

Now you hand over notebook to teacher.

This is:

```
Flush
```

Teacher receives it.

But results not finalized yet.

---

### Example

```
@Transactional
public void updateUser() {

    User user =
        entityManager.find(User.class,1L);

    user.setName("Prashant");

    entityManager.flush();
}
```

What happens?

Dirty checking detects:

```
John → Prashant
```

Hibernate generates:

```
UPDATE users
SET name='Prashant'
WHERE id=1;
```

SQL executes immediately.

Database updated.

But transaction still open.

---

### Important Point

After Flush:

```
SQL executed
```

But

```
Transaction NOT committed yet
```

Rollback still possible.

---

### Example

```
@Transactional
public void updateUser() {

    User user =
        entityManager.find(User.class,1L);

    user.setName("Prashant");

    entityManager.flush();

    throw new RuntimeException();
}
```

What happens?

```
Flush executed
UPDATE fired
Exception occurred
Rollback happened
```

Final result:

```
Database unchanged
```

Because commit never happened.

---

### Then What is Commit?

Commit means:

> Permanently save transaction changes.

---

### Flow

```
Start Transaction
        ↓
Modify Entity
        ↓
Dirty Checking
        ↓
Flush
        ↓
Commit
        ↓
Changes Permanent
```

---

### Complete Example

Suppose DB:

```
id   name
1    John
```

Code:

```
@Transactional
public void updateUser() {

    User user =
        entityManager.find(User.class,1L);

    user.setName("Prashant");
}
```

---

#### Step 1

Fetch:

```
Persistence Context

User(1,"John")
```

Snapshot:

```
User(1,"John")
```

---

#### Step 2

Modify:

```
user.setName("Prashant");
```

Current:

```
User(1,"Prashant")
```

Snapshot:

```
User(1,"John")
```

---

#### Step 3

Dirty Checking

Hibernate compares:

```
John != Prashant
```

Entity is dirty.

---

#### Step 4

Flush

Hibernate generates:

```
UPDATE users
SET name='Prashant'
WHERE id=1;
```

SQL sent.

---

#### Step 5

Commit

Transaction committed.

Changes become permanent.

---

### Dirty Checking vs Save()

Many beginners ask:

```
@Transactional
public void updateUser() {

    User user =
       userRepository.findById(1L)
                     .orElseThrow();

    user.setName("Prashant");
}
```

Where is save()?

No save needed.

Because:

```
Managed Entity
    ↓
Dirty Checking
    ↓
Flush
    ↓
Commit
```

Hibernate automatically updates.

---

### When save() is Required?

New Entity.

```
User user = new User();
user.setName("Prashant");

userRepository.save(user);
```

Because:

```
Entity not managed yet
```

Need:

```
persist()
```

to start tracking.

---

## Interview Question

### Does Flush Commit Data?

Answer:

```
No.
Flush only synchronizes Persistence Context with database.

Commit permanently saves transaction changes.
```

---

### When does Dirty Checking happen?

Answer:

```
Dirty Checking happens before flush.

Hibernate compares the managed entity with its snapshot and generates UPDATE statements for changed fields.
```

---

### What is the relationship between Dirty Checking, Flush and Commit?

Answer:

```
Dirty Checking
      ↓
Hibernate detects changed entities

Flush
      ↓
Hibernate generates and executes SQL

Commit
      ↓
Database permanently saves transaction
```

### One-Line Memory Trick

```
Persistence Context = Working Area

Dirty Checking = Detect Changes

Flush = Send SQL to DB

Commit = Permanently Save Changes
```

Meaning:

> Don't load related entity now.
>

Only now.

## Interview Answer (2 Minutes)

> **FetchType determines when related entities are loaded from the database. `FetchType.EAGER` loads associated entities immediately when the parent entity is loaded, while `FetchType.LAZY` delays loading until the association is actually accessed. Hibernate implements LAZY loading using proxy objects. EAGER loading can cause unnecessary data fetching and performance issues, whereas LAZY loading improves memory usage and scalability. The default fetch type is LAZY for `@OneToMany` and `@ManyToMany`, and EAGER for `@ManyToOne` and `@OneToOne`. In production systems, LAZY is generally preferred, combined with DTOs, fetch joins, or entity graphs to avoid N+1 query problems and LazyInitializationException**.

@Entity

    private User user;

Database:

#### user

|id|name|
|---|---|
|1|Prashant|

#### orders

|id|item|user_id|
|---|---|---|
|101|Laptop|1|

```
User(1)
   |
   +---- Order(101)
   |
   +---- Order(102)
   |

From User side:

### What is [mappedBy] ?

#### Ownership

JPA calls this the **owning side**.

In JPA bidirectional relationships, ==the **owning side controls the database state** (manages the foreign key column or join table), while the **inverse side is a read-only mirror** used strictly for object navigation==

Owning side:

```
@ManyToOneUser user;
```

Inverse side:

```
@OneToMany(mappedBy = "user")
List<Order> orders;
```

The FK is stored in:

```
orders.user_id
```

so Order owns the relationship.

---

## What is FetchType?

Fetch type decides:

> When should related data be loaded?

Two options:

```
FetchType.EAGER
FetchType.LAZY
```

---

### EAGER

```
@OneToOne(fetch = FetchType.EAGER)
```

means:

> Load related entity immediately.

Example:

```
User user = userRepo.findById(1L);
```

Hibernate generates:

```
SELECT *
FROM user u
LEFT JOIN passport p
ON u.passport_id = p.id
WHERE u.id = 1;
```

User and Passport come together.

---

### LAZY

```
@OneToMany(fetch = FetchType.LAZY)
```

means:

> Don't load orders immediately.

```
User user = userRepo.findById(1L);
```

SQL:

```
SELECT * FROM user WHERE id = 1;
```

Only user loaded.

Later:

```
user.getOrders();
```

Then Hibernate fires:

```
SELECT *
FROM orders
WHERE user_id = 1;
```

This is lazy loading.

---

## Why is OneToMany default LAZY?

This is the most important question.

Imagine:

```
User user = userRepo.findById(1L);
```

User has:

```
10,000 orders
```

If OneToMany were EAGER:

```
SELECT *
FROM user
JOIN orders
```

Hibernate would immediately load:

```
1 User

10,000 Orders
```

even if you never use orders.

Huge memory waste.

---

Another example:

```
Customer
   -> Orders
      -> OrderItems
         -> Products
```

EAGER loading can explode into:

```
Customer
+ 100 Orders
+ 5000 OrderItems
+ 5000 Products
```

for a simple query.

Therefore:

```
@OneToMany
```

defaults to:

```
LAZY
```

to prevent loading huge collections.

---

## Why is ManyToOne default EAGER?

Consider:

```
Order order = orderRepo.findById(101L);
```

An order usually belongs to exactly one user.

Loading:

```
Order
+
User
```

is cheap.

The assumption of JPA designers was:

> If you're working with an Order, you'll probably need its User.

Therefore:

```
@ManyToOne
```

default:

```
EAGER
```


---

## Why is OneToOne default EAGER?

Consider:

```
User -> Passport
```

Only one related record.

Loading:

```
User + Passport
```

is usually cheap.

Therefore JPA chose:

```
@OneToOne
```

default:

```
EAGER
```

---

## Reality in Modern Applications

Most experienced Spring developers override defaults.

Instead of:

```
@ManyToOne
```

they write:

```
@ManyToOne(fetch = FetchType.LAZY)
```

and

```

because:

- Better performance
- Avoid unnecessary joins
- More control

Nowadays many teams prefer:

```
OneToOne -> LAZY
ManyToOne -> LAZY

```

and explicitly fetch data when needed using:

```
JOIN FETCH
@EntityGraph
DTO projections
```

# ==N+1 query problem? caused by FetchType.EAGER or lazy loading ?==

Most developers memorize:

> "N+1 problem happens because of lazy loading."

This is **only partially true**.

The real answer is:

> N+1 happens when JPA executes one query for parent entities and then executes additional queries for associated entities one by one.

It can happen with **LAZY** and sometimes even with **EAGER**.

Let's build intuition from scratch.

---

## Step 1: Real-world example

Imagine:

```
Order 
└── Customer
```

Database:

### Orders

|id|order_no|customer_id|
|---|---|---|
|1|O101|1|
|2|O102|2|
|3|O103|3|

### Customers

|id|name|
|---|---|
|1|John|
|2|Alice|
|3|Bob|

---

Suppose you want:

```
All Orders + Customer Name
```

Expected SQL:

```
SELECT *
FROM orders o
JOIN customers c
ON o.customer_id = c.id;
```

One query.

Life is good.

---

## Step 2: What JPA does by default

Entity:

```
@Entity
public class Order {

    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    private Customer customer;
}
```

Repository:

```
List<Order> orders = orderRepository.findAll();
```

---

Hibernate executes:

```
SELECT * FROM orders;
```

Only orders are loaded.

Result:

```
[
 Order(1),
 Order(2),
 Order(3)
]
```

Customer not loaded yet.

---

## Step 3: Lazy loading starts

Now:

```
for(Order order : orders){
    System.out.println(
        order.getCustomer().getName()
    );
}
```

First iteration:

```
order1.getCustomer()
```

Hibernate:

```
SELECT * FROM customers
WHERE id = 1;
```

---

Second iteration:

```
order2.getCustomer()
```

Hibernate:

```
SELECT * FROM customers
WHERE id = 2;
```

---

Third iteration:

```
SELECT * FROM customers
WHERE id = 3;
```

---

Total queries:

```
1 query for Orders

+
3 queries for Customers

=
4 queries
```

Formula:

```
1 + N
```

where N = number of parent records.

This is called:

## N+1 Problem


```
DB ---> All Orders + Customers
```

One trip.

JPA does:

```
DB ---> Orders

DB ---> Customer 1

DB ---> Customer 2

DB ---> Customer 3
```

Many trips.

Network calls increase.

Database load increases.

Performance drops.

---

### Example with 1000 Orders

```
List<Order> orders = orderRepository.findAll();
```

1000 orders.

Then:

```
orders.forEach(
 order -> order.getCustomer().getName()
);
```

Queries:

```
1 query for Orders

1000 queries for Customers

=
1001 queries
```

This is why N+1 is dangerous.

---

### Why does LAZY cause it?

Because LAZY means:

```
@ManyToOne(fetch = FetchType.LAZY)
```

Hibernate says:

```
Don't load customer now.
Load customer when someone asks.
```

So every access:

```
order.getCustomer()
```

may trigger a new query.

---

### Does EAGER solve N+1?

Most beginners think:

```
Lazy causes N+1
Therefore Eager fixes N+1
```

Wrong.

---

Let's see.

```
@ManyToOne(fetch = FetchType.EAGER)
private Customer customer;
```

Now:

```
List<Order> orders = orderRepository.findAll();
```

Developers expect:

```
SELECT * 
FROM orders o
JOIN customers c
```

But Hibernate is NOT required to do that.

It may do:

```
SELECT * FROM orders;
```

Then:

```
SELECT * FROM customers WHERE id=1;
SELECT * FROM customers WHERE id=2;
SELECT * FROM customers WHERE id=3;
```

Again:

```
1 + N
```

Still N+1.

---

## ==Important Interview Point==

`EAGER` means:

```
Associated entity must be loaded.
```

It does NOT mean:

```
Use SQL JOIN.
```

Huge difference.

---

## Then what actually fixes N+1?

Not EAGER.

Not LAZY.

The solution is:

```
Fetch association in same SQL query.
```

Using:

### JOIN FETCH

```
@Query("""
	SELECT o
	FROM Order o
	JOIN FETCH o.customer
	""")
List<Order> findAllWithCustomer();
```

SQL:

```
SELECT *
FROM orders o
JOIN customers c
ON o.customer_id = c.id;
```

One query.

Problem solved.

## How to identify N+1?

Enable Hibernate SQL logs.

```
spring.jpa.show-sql=true
logging.level.org.hibernate.SQL=DEBUG
```

If you see:

```
select * from orders

select * from customer where id=1

select * from customer where id=2

select * from customer where id=3
```

You have N+1.

---

## Interview Answer

**What is N+1 Query Problem?**

> N+1 query problem occurs when JPA first loads a collection of parent entities using one query and then loads each associated entity individually using additional queries. For N parent records, total queries become 1 + N, causing serious performance issues.

**Does it happen because of LAZY loading?**

> It commonly happens with LAZY loading because associations are fetched on demand. However, EAGER loading does not guarantee prevention of N+1 because Hibernate may still execute separate queries instead of using a SQL join.

**How do you solve it?**

> Use JOIN FETCH, Entity Graphs, DTO projections, batch fetching, or optimized custom queries so related entities are loaded in a single query.

### Golden Interview Line

> The root cause of N+1 is not LAZY or EAGER itself. The root cause is fetching related entities through multiple SQL queries instead of a single optimized query.
