
## How to handle caching with Spring boot ? @EnableCaching ? How does @Cacheable work in Spring Boot? What is the difference between @Cacheable, @CachePut and @CacheEvict?

Caching means storing frequently used data in fast storage so we do not calculate/fetch it again and again.

Example:

```
getProductById(101)
```

Without cache:

```
Request → Service → Database → Return product
Request → Service → Database → Return product
Request → Service → Database → Return product
```

With cache:

```
First request  → Database → Store result in cache
Second request → Return from cache
Third request  → Return from cache
```

So caching helps with:

```
Fast response
Less database load
Better scalability
Lower cost
```

---

### Where caching is useful?

Good use cases:

```
Product details
Category list
User profile
Country/state/city list
Configuration data
Expensive calculations
API response from third-party service
```

Bad use cases:

```
Highly changing data, live data, realtime data
```

### Spring Boot Caching Basics

Spring provides abstraction over different cache providers.

You write:

```
@Cacheable
```

Spring internally can use:

```
Internally, Spring uses the ConcurrentHashMap for its default, out-of-the-box caching.
```


For production, mostly:

```
Redis
```

### Enable caching

To use Spring caching, add:

```
@EnableCaching
```

Example:

```
@SpringBootApplication
@EnableCaching
public class ProductApplication {
    public static void main(String[] args) {
        SpringApplication.run(ProductApplication.class, args);
    }
}
```

#### What does `@EnableCaching` do?

Spring activates its "Simple" cache provider. and spring says:

```
Please scan my beans for caching annotations like:
@Cacheable
@CachePut
@CacheEvict
```

Without `@EnableCaching`, these annotations will not work.

####  Example without caching

```
@Service
public class ProductService {

    public Product getProductById(Long id) {
        System.out.println("Fetching product from DB...");
        return productRepository.findById(id).orElseThrow();
    }
}
```

Every call hits database.

```
getProductById(1) → DB
getProductById(1) → DB
getProductById(1) → DB
```

---

###  @Cacheable

**`@Cacheable`** is a method-level annotation used to **store the results of expensive operations** (like slow database queries or external API calls) in a cache. When the method is invoked again with the same parameters, Spring skips executing the method and instead returns the cached result directly.

Example:

```
@Cacheable(value = "products", key = "#id")
public Product getProductById(Long id) {
    System.out.println("Fetching product from DB...");
    return productRepository.findById(id).orElseThrow();
}
```

#### Flow

First call:

```
getProductById(1)
↓
Cache check: products::1 not found
↓
Method executes
↓
DB call happens
↓
Result stored in cache
```

Second call:

```
getProductById(1)
↓
Cache check: products::1 found
↓
Method does NOT execute
↓
Return cached product
```

Important point:

```
System.out.println("Fetching product from DB...");
```

will print only on first call.

---

#### Cache name and key

```
@Cacheable(value = "products", key = "#id")
```

Here:

```
products = cache name
#id      = cache key
```

Actual cache entry is like:

```
products::1 → Product object
products::2 → Product object
```

---

### @CachePut

The **`@CachePut`** annotation in Spring Boot is used to **update the cache with the latest method result every time the method is executed**. Unlike `@Cacheable`, it **never skips the method execution**; instead, it forces the method to run, updates the underlying database or repository, and then synchronizes that new data directly into the cache.

Example:

```
@CachePut(value = "products", key = "#id")
public Product updateProduct(Long id, ProductRequest request) {
    Product product = productRepository.findById(id).orElseThrow();

    product.setName(request.getName());
    product.setPrice(request.getPrice());

    return productRepository.save(product);
}
```

#### Flow

```
updateProduct(1)
↓
Method always executes
↓
DB update happens
↓
Updated product stored in cache
```

So after update, cache also has latest value.

---

### @CacheEvict

In Spring Boot, **cache eviction** removes stale or unused data from your application's cache. You can perform eviction declaratively using the **`@CacheEvict` annotation**, or programmatically using the **`CacheManager` API**

Example:

```
@CacheEvict(value = "products", key = "#id")
public void deleteProduct(Long id) {
    productRepository.deleteById(id);
}
```

#### Flow

```
deleteProduct(1)
↓
Delete from DB
↓
Remove products::1 from cache
```

Now next call:

```
getProductById(1)
```

will not return old cached data.

---

### Full production-style example

```
@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Cacheable(value = "products", key = "#id")
    public Product getProductById(Long id) {
        System.out.println("DB call for product id: " + id);
        return productRepository.findById(id).orElseThrow();
    }

    @CachePut(value = "products", key = "#id")
    public Product updateProduct(Long id, ProductRequest request) {
        Product product = productRepository.findById(id).orElseThrow();

        product.setName(request.getName());
        product.setPrice(request.getPrice());

        return productRepository.save(product);
    }

    @CacheEvict(value = "products", key = "#id")
    public void deleteProduct(Long id) {
        productRepository.deleteById(id);
    }
}
```

---

###  Important beginner mistake

Spring caching works through proxy.

That means this will work:

```
productService.getProductById(1);
```

But calling cached method from same class may not work:

```
public void someMethod() {
    getProductById(1); // self-invocation, cache may be bypassed
}
```

Why?

Because Spring applies caching using proxy object. Internal method call does not go through proxy.

---
### Final mental model

```
Read API    → @Cacheable
Update API  → @CachePut or @CacheEvict
Delete API  → @CacheEvict
```

Most common production pattern:

```
GET    /products/{id} → @Cacheable
PUT    /products/{id} → @CachePut
DELETE /products/{id} → @CacheEvict
```

## How do you implement conditional caching using unless and condition attributes in @Cacheable?

### Why do we need conditional caching?

**`condition` and** **`unless` are parameters used for conditional caching, determining whether a method's result should be fetched from or saved to a cache**.

The primary difference lies in the **timing of evaluation**: `condition` is checked _before_ the method executes based on arguments, while `unless` is checked _after_ the method executes based on the return value

Sometimes:
#### Case 1

Cache only premium products.

```
Product 1 → Premium
Product 2 → Normal
```

Cache:

```
Product 1 → YES
Product 2 → NO
```

---

#### Case 2

Don't cache null values.

```
Product Exists → Cache
Product Not Found → Don't Cache
```

---

#### Case 3

Cache only expensive API calls.

```
User data → Cache
Live stock price → Don't Cache
```

For such scenarios Spring provides:

```
conditionunless
```

---

### condition

`condition` is evaluated BEFORE method execution.

```
Condition true
↓
Caching logic applies

Condition false
↓
Ignore caching completely
↓
Method executes normally
```

---
#### Syntax

```
@Cacheable(
    value = "products",
    key = "#id",
    condition = "#id > 100"
)
```

---

### Example 1

Cache only products with id > 100

```
@Cacheable(
    value = "products",
    key = "#id",
    condition = "#id > 100"
)
public Product getProduct(Long id) {
    System.out.println("DB Call");
    return productRepository.findById(id).orElseThrow();
}
```

---

#### Call 1

```
getProduct(50)
```

Condition:

```
50 > 100
```

False

Result:

```
Cache ignored
DB called every time
```

---

#### Call 2

```
getProduct(150)
```

Condition:

```
150 > 100
```

True

Result:

```
Cache works normally
```

---

### Flow of condition

```
Request
↓
Evaluate condition
↓
True?
├─ Yes → Check Cache
└─ No  → Skip Cache Completely
```

---

### What can be used inside condition?

Method parameters.

Example:

```
condition = "#id > 100"
```

```
condition = "#country == 'IN'"
```

```
condition = "#includeCache == true"
```

Example:

```
@Cacheable(
        value="products",
        key="#id",
        condition="#useCache"
)
public Product getProduct(Long id, boolean useCache) {
    return repository.findById(id).orElseThrow();
}
```

---

### unless

This is where most people get confused.

---

#### Meaning

`unless` is evaluated AFTER method execution.

Spring first executes method.

Then checks returned result.

Then decides whether to cache.

---

```
@Cacheable(
    value = "products",
    key = "#id",
    unless = "#result == null"
)
```

---

#### Flow

```
Request
↓
Execute Method
↓
Get Result
↓
Evaluate unless
↓
False → Cache Result
True  → Don't Cache
```

---

#### Example 1

Do not cache null values.

```
@Cacheable(
    value = "products",
    key = "#id",
    unless = "#result == null"
)
public Product getProduct(Long id) {
    return productRepository.findById(id).orElse(null);
}
```

---

Product Found

```
Product(id=1)
```

Condition:

```
#result == null
```

False

Result:

```
Stored in Cache
```

---

Product Not Found

```
null
```

Condition:

```
#result == null
```

True

Result:

```
Do NOT cache
```

---

#### Why is this useful?

Imagine:

```
getProduct(999)
```

returns

```
null
```

If null gets cached:

```
products::999 → null
```

Later product gets created.

But cache still contains null.

Users won't see new data until cache expires.

So usually:

```
unless="#result == null"
```

is very common.

---

#### Example 2

Cache only premium products

```
@Cacheable(
    value = "products",
    key = "#id",
    unless = "!#result.isPremium()"
)
public Product getProduct(Long id) {
    return repository.findById(id).orElseThrow();
}
```

Suppose:

```
Product A → Premium
Product B → Normal
```

---

For Product A:

```
!true
```

False

```
Cache Product A
```

---

For Product B:

```
!false
```

True

```
Don't Cache Product B
```

---

#### Example 3

Cache only expensive products

```
@Cacheable(
        value="products",
        key="#id",
        unless="#result.price < 1000"
)
public Product getProduct(Long id) {
    return repository.findById(id).orElseThrow();
}
```

---

Product:

```
Price = 5000
```

Condition:

```
5000 < 1000
```

False

```
Cache it
```

---

Product:

```
Price = 500
```

Condition:

```
500 < 1000
```

True

```
Don't Cache
```

---

### Difference Between condition and unless

|Feature|condition|unless|
|---|---|---|
|Checked When?|Before method execution|After method execution|
|Access method parameters?|Yes|Yes|
|Access result?|No|Yes|
|Can prevent method execution?|No (prevents cache logic only)|No|
|Common Use|Decide if cache should participate|Decide if result should be stored|

---


---
### Using Both Together

Very common in production.

```
@Cacheable(
    value = "products",
    key = "#id",
    condition = "#id > 0",
    unless = "#result == null"
)
public Product getProduct(Long id) {
    return repository.findById(id).orElse(null);
}
```

Flow:

```
id > 0 ?
    No → Skip Cache

    Yes
       ↓
       Execute Method
       ↓
       Result null ?
            Yes → Don't Cache
            No  → Cache Result
```

---

### Interview Answer (2-3 lines)

> `condition` is evaluated before method execution and decides whether the caching mechanism should participate for a given invocation. `unless` is evaluated after method execution and decides whether the returned result should actually be stored in the cache. `condition` works on method arguments, while `unless` is commonly used with `#result`, such as preventing null values from being cached.

## What is Etags. what is the need ? How do you implement ETags and conditional GET with caching for REST APIs ?

**ETag = Entity Tag**

ETags and Spring Cache serve two completely different purposes in a web application: ETags handle client-side (HTTP) caching to save network bandwidth, while Spring Cache handles server-side application caching to reduce heavy computing or database strain.

Example response:

```
GET /products/101
```

Server response:

```
HTTP/1.1 200 OK
ETag: "product-101-v5"
Content-Type: application/json
```

Body:

```
{
  "id": 101,
  "name": "iPhone",
  "price": 70000
}
```

Here:

```
ETag: "product-101-v5"
```

means:

```
This is version 5 of product 101 response.
```

---

### Why do we need ETags?

Imagine product data does not change often.

Without ETag:

```
Client requests product
↓
Server sends full JSON response

Client requests same product again
↓
Server again sends full JSON response

Client requests again
↓
Server again sends full JSON response
```

Problem:

```
Unnecessary network usage
Unnecessary JSON serialization
More server load
Slower APIs
```

With ETag:

```
Client asks: Has product changed?
Server says: No, use your cached copy.
```

So instead of sending full response, server returns:

```
HTTP/1.1 304 Not Modified
```

No response body.

That saves:

```
Network bandwidth
Server processing
Client processing
API latency
```

## How does @Cacheable works internally? CacheInterceptor,  CacheManager,  Cache resolver? Cache lookup ?

### Internal Flow of `@Cacheable`

### 1. Spring creates proxy

When you write:

```
@EnableCaching
```

Spring enables cache AOP.

Your bean is wrapped with a proxy.

```
Controller
   ↓
Proxy object
   ↓
Actual service object
```

So when you call:

```
userService.getUserById(1)
```

you are not directly calling the real method.

You are calling the proxy first.

---

### 2. Proxy sends call to `CacheInterceptor`

Internally, Spring uses:

```
CacheInterceptor
```

`CacheInterceptor` is the main class that handles caching logic.

Flow:

```
Method call
   ↓
Proxy
   ↓
CacheInterceptor
   ↓
Check @Cacheable metadata
   ↓
Decide cache hit/miss
```

So `CacheInterceptor` decides:

```
Should I return cached value?
Or should I execute actual method?
```

---

### 3. Spring reads `@Cacheable` metadata

For this method:

```
@Cacheable(value = "users", key = "#id")
public User getUserById(Long id) {}
```

Spring reads:

```
cache name = users
key = #id
condition = optional
unless = optional
cacheManager = optional
cacheResolver = optional
```

Example:

```
@Cacheable(
    value = "users",
    key = "#id",
    condition = "#id > 0",
    unless = "#result == null"
)
```

---

### 4. CacheResolver decides which cache to use

`CacheResolver` decides:

```
Which cache should be checked?
```

Most of the time, you do not write `CacheResolver` manually.

Spring uses default resolver:

```
SimpleCacheResolver
```

This resolver uses the configured:

```
CacheManager
```

---

### 5. CacheManager gives actual Cache object

`CacheManager` manages caches.

Example:

```
CacheManager
   ↓
users cache
products cache
orders cache
```

If your annotation says:

```
@Cacheable(value = "users")
```

Then internally:

```
CacheManager.getCache("users")
```

Spring asks the cache manager:

```
Give me the cache named "users"
```

Depending on your setup, `CacheManager` may be:

```
ConcurrentMapCacheManager  // in-memory
RedisCacheManager          // Redis
CaffeineCacheManager       // Caffeine
EhCacheCacheManager        // Ehcache
```

Example with Redis:

```
CacheManager = RedisCacheManager
Cache = Redis cache named "users"
```

---

### 6. KeyGenerator creates cache key

Spring needs a unique key.

For this:

```
@Cacheable(value = "users", key = "#id")
public User getUserById(Long id)
```

Key is:

```
1
```

So final cache entry is like:

```
cache name: users
key: 1
value: User object
```

If you do not provide key:

```
@Cacheable("users")
public User getUserById(Long id)
```

Spring uses default key generator:

```
SimpleKeyGenerator
```

For one argument:

```
key = id
```

For multiple arguments:

```
getUser(String city, String role)
```

key becomes:

```
SimpleKey[city, role]
```

---

### 7. Cache lookup happens

Now Spring checks:

```
users cache contains key 1?
```

Internally:

```
cache.get(key)
```

Decision:

```
If value present → cache hit
If value absent  → cache miss
```

---

### 8. Decision based on presence

#### Case 1: Cache Hit

```
users::1 exists
```

Then Spring does this:

```
Return cached value
Do not execute actual method
```

So this method body is skipped:

```
public User getUserById(Long id) {
    System.out.println("DB call");
    return userRepository.findById(id).orElseThrow();
}
```

That is why second request is fast.

---

#### Case 2: Cache Miss

```
users::1 does not exist
```

Then Spring does this:

```
Execute actual method
Get result
Store result in cache
Return result
```

Flow:

```
Cache miss
   ↓
Actual method executes
   ↓
DB call happens
   ↓
Result comes
   ↓
Spring stores result in cache
   ↓
Return result
```

---

### Complete Internal Flow

```
Client calls getUserById(1)
        ↓
Spring proxy intercepts call
        ↓
CacheInterceptor starts
        ↓
Read @Cacheable metadata
        ↓
Resolve cache using CacheResolver
        ↓
CacheResolver uses CacheManager
        ↓
CacheManager returns "users" cache
        ↓
Generate key using KeyGenerator / SpEL
        ↓
Check cache.get(key)
        ↓
Is value present?
   ┌───────────────┬────────────────┐
   │ YES           │ NO             │
   │ Cache hit     │ Cache miss     │
   ↓               ↓
Return cached    Execute method
value            ↓
                 Store result in cache
                 ↓
                 Return result
```

# One-line interview answer

`@Cacheable` works using Spring AOP. Spring creates a proxy around the bean, and method calls are intercepted by `CacheInterceptor`. The interceptor reads cache metadata, resolves the cache through `CacheResolver` and `CacheManager`, generates a key, checks the cache, and if the value is present it returns it directly. If not present, it executes the method, stores the result in cache, and then returns it.

## How do you implement multi-level caching (in-memory + Redis)? When you will use it ? adv and distadvantage ?

### What is Multi-Level Cache?

Instead of one cache, we use multiple cache layers.

Usually:

```
L1 Cache
(Application Memory)

↓

L2 Cache
(Redis)

↓

Database
```

Flow becomes

```
Client

   │

   ▼

Application

   │

Check L1 Cache

   │

Found?
 /      \

Yes      No

 │        │

 ▼        ▼

Return    Check Redis (L2)

            │

          Found?

         /      \

       Yes      No

        │         │

        ▼         ▼

 Update L1      Database

        │

        ▼

Return Data
```

This is called **Hierarchical Cache** or **Multi-Level Cache**.

---

### Why not just use Redis?

Redis is fast.

But:

```
Application → Redis

# When should you use multi-level caching?

Use it when all of the following are true:

- **Read-heavy workload**: reads vastly outnumber writes (e.g., product catalog, user profiles, configuration).
- **Low-latency requirements**: every millisecond matters.
- **Horizontally scaled services**: multiple application instances share a common Redis cache.
- **Data can tolerate brief staleness**: a few seconds of stale data is acceptable, or you have a robust invalidation mechanism.

Avoid it when:

- Data changes very frequently (for example, rapidly changing stock prices).
- Strong consistency is required (every read must reflect the latest write).
- The application is small enough that the added complexity isn't justified.

### Interview summary (30-second answer)

> **Multi-level caching** uses multiple cache layers, typically an **L1 in-memory cache (such as Caffeine)** and an **L2 distributed cache (Redis)**. On each read, the application checks L1 first because it's the fastest. If L1 misses, it checks Redis. If Redis also misses, it loads the data from the database, then populates both Redis and L1. This approach minimizes latency, reduces Redis traffic, and greatly lowers database load. The main challenges are cache invalidation, maintaining consistency across application instances, and the added operational complexity. It is best suited for read-heavy workloads like product catalogs, user profiles, and application configuration.

### Part 2: Cache Stampede

#### Definition

A cache stampede happens when a **hot key expires**, causing many requests to simultaneously miss the cache and hit the database.

A **cache stampede** (or "thundering herd problem") is failure where concurrent requests simultaneously miss the cache and overwhelm the backend (e.g., a database) to regenerate the same data. `It happens when a popular cache key expires and a slow database query cannot compute fast enough to stop subsequent requests from firing identical queries.`

Hot Key -> `a specific piece of cached data that receives a disproportionate amount of traffic compared to other keys.`

---

### Spring Boot Production Architecture

```

          ▼              ▼              ▼

          │              │              │
          └────── Redis Cluster ────────┘
                    │

Flow:

1. Check L1 (Caffeine) if enabled.
2. Check Redis.
3. If Redis misses:
    - Acquire a distributed lock.
    - One instance loads from DB.
    - Update Redis (and L1 if present).
    - Other instances wait briefly or retry Redis.
4. Use randomized TTLs to avoid synchronized expirations.
5. Refresh critical hot data proactively where appropriate.

### Interview Answer (1 minute)

> In a clustered Spring Boot application, each instance has its own local memory, so an in-memory cache alone can lead to inconsistent data and duplicate database queries. A shared distributed cache like Redis is typically used so all instances access the same cached data.
> 
> Two common problems are **cache stampede** and **cache avalanche**. A cache stampede occurs when a hot key expires and many concurrent requests hit the database simultaneously. I would prevent it using a distributed mutex lock, refresh-ahead for hot keys, or request coalescing so only one request rebuilds the cache.
> 
> A cache avalanche occurs when many cache entries expire at the same time or the cache layer becomes unavailable, causing a surge of database traffic. To mitigate it, I would use randomized TTLs, stagger cache refreshes, multi-level caching (Caffeine + Redis), Redis high availability (Cluster or Sentinel), and protect the database with rate limiting or circuit breakers.
> 
> These techniques together make the caching layer resilient and scalable in production.

## mutex lock in cache stampede ? is this the same as distributed lock in redis ?

### Step 9: What if App1 crashes after acquiring the lock?

This is a common interview follow-up.

Suppose:

```
App1 acquires lock

↓

Before releasing it...

↓

💥 Crash
```

If the lock never expires:

```
App2 waits forever

App3 waits forever
```

The system is stuck.

To prevent this, Redis locks are created with a **TTL (lease time)**:

```
SET lock:product123 unique_value NX PX 10000
```

- `NX` → only create the lock if it doesn't already exist.
- `PX 10000` → automatically expire the lock after 10 seconds.

If App1 crashes, Redis deletes the lock automatically after the TTL, allowing another application to rebuild the cache.

---

### Step 10: Why use a unique lock value?

Another interview follow-up:

Imagine:

1. App1 acquires the lock.
2. App1 is slow (GC pause, network delay).
3. The 10-second TTL expires.
4. App2 acquires a **new** lock.
5. App1 wakes up and blindly executes `DEL lock:product123`.

Now App1 accidentally deletes **App2's** lock.

To prevent this, store a unique token (UUID) as the lock value:

```
SET lock:product123 8f3a... NX PX 10000
```

When releasing the lock:

- Read the value.
- Delete the lock **only if** the stored value matches your UUID (typically done atomically with a Lua script).

This ensures one application cannot delete another application's lock.

### Interview Summary

|Feature|Request Coalescing|Mutex / Distributed Lock|
|---|---|---|
|Purpose|Merge duplicate in-flight requests|Ensure only one worker rebuilds the cache|
|Scope|Usually within a single application instance|Across multiple application instances|
|Waiting behavior|Wait on the same Future/Promise|Wait for the lock to be released or retry|
|Database queries (single JVM)|1|1|
|Database queries (multiple JVMs)|One per JVM|One across the entire cluster|
|Common implementation|`ConcurrentHashMap + CompletableFuture`|Redis `SET key value NX PX`, ZooKeeper, etc.|

### A good interview answer

> "Request coalescing prevents duplicate work by detecting that a request for the same resource is already in progress. Instead of starting another database query, later requests wait for the first request's result and then reuse it. This is typically implemented using a shared `Future` or `Promise` within a single application instance. In a distributed system, request coalescing is often combined with a distributed lock so that only one application instance rebuilds the cache while all duplicate requests—both within and across instances—share the same result."

## how to combine Request coalescing and Distributed Lock ?

This is an excellent system design question because **companies like Google, Meta, Netflix, and Amazon commonly combine both techniques**.

The reason is simple:

- **Distributed Lock** prevents **multiple servers** from hitting the database.
- **Request Coalescing** prevents **multiple threads within the same server** from doing duplicate work.

Using only one of them still leaves unnecessary work.

### Java Pseudocode

```
public Product getProduct(Long id) {

    // 1. Check Redis
    Product product = redis.get(id);

    if (product != null)
        return product;

    // 2. Local Request Coalescing
    CompletableFuture<Product> future =
        loading.computeIfAbsent(id, key ->

            CompletableFuture.supplyAsync(() -> {

                // 3. Distributed Lock
                if (redis.tryLock(key)) {

                    try {

                        Product p = database.findById(key);

                        redis.set(key, p);

                        return p;

                    } finally {

                        redis.unlock(key);
                    }

                }

                // Someone else owns lock
                while (true) {

                    Product cached = redis.get(key);

                    if (cached != null)
                        return cached;

                    Thread.sleep(50);
                }

            })

        );

    return future.get();
}
```

Notice what this achieves:

- **Within one JVM**, `computeIfAbsent` ensures only one thread performs the loading logic.
- **Across all JVMs**, the Redis lock ensures only one server performs the database query.
- Every other thread simply waits for either:
    - the local `CompletableFuture` to complete, or
    - the cache to be populated by the lock owner.

- 20 application servers.

```

Redis Cache Updated
        │
        ▼
All waiting Futures complete
        │
        ▼

```

This combination minimizes **database load**, **Redis load**, and **CPU usage** on your application servers, which is why it's a common design in high-throughput distributed systems.
