### What is a Transaction?

**transaction** represents a single logical unit of work that ensures database operations are either fully completed or completely rolled back.

Simple example: **Bank money transfer**

```
Transfer ₹1000 from Account A to Account B

Step 1: Deduct ₹1000 from Account A
Step 2: Add ₹1000 to Account B
```

Both steps must succeed together.

If Step 1 succeeds but Step 2 fails, money disappears. That is a serious bug.

With transaction:

```
If everything is successful → COMMIT
If something fails → ROLLBACK
```

---

#### Commit
	Commit means permanently save the transaction changes into the database.

#### Rollback
	Rollback means undo all changes made inside the transaction. Database goes back to the previous safe state. 

#### After commit can we rollback, but how can we rollback in distributed systems ( saga pattern ) ?

In a single database, **you cannot rollback a transaction after it has been explicitly committed**; once `COMMIT` is executed, the changes are permanent and visible to other users.

However, in distributed systems using the **Saga Pattern**, "rolling back" does not mean erasing a database transaction. Instead, it uses **Compensating Transactions**

### How @Transactional works internally

#### The Proxy Mechanism

Every @Transactional behavior, bug, and gotcha traces back to one concept: **Spring uses proxies**. If you understand the proxy, you understand @Transactional.

#### What Spring Actually Does at Startup

When your Spring Boot application starts and finds a `@Service` class with `@Transactional` methods:
-  Spring creates your actual `OrderService` object
-  Spring generates a new class at runtime using **CGLIB bytecode generation**: `OrderService$$SpringCGLIB$$0`
-  This generated class **extends** your OrderService
-  It **overrides every method** and adds transaction interceptor logic
-  Spring registers the PROXY in the application context, not your original class
-  When you `@Autowired OrderService`, you get the proxy

```java
@Service
public class OrderService {

    @PostConstruct
    public void init() {
        System.out.println("My class: " + this.getClass().getName());
        // Output: com.app.OrderService$$SpringCGLIB$$0
        // NOT:    com.app.OrderService
    }
}
```


That `$$SpringCGLIB$$0` suffix is proof that you're never working with your actual class. It's always the proxy.

This Applies to More Than @Transactional

```
The same proxy mechanism powers `@Async`, `@Cacheable`, `@Retryable`, and `@Scheduled`. All of them use proxies. All of them have the same self-invocation problem. Understanding the proxy once means understanding all these annotations.
```


### Trap 1:  Self-Invocation (The #1 Spring Transaction Bug).

This is one of the most common Spring interview questions.

**Self-invocation** is a situation where one method in a Spring bean calls another method of the **same bean**.

Spring's `@Transactional` works using **AOP proxies**. The transaction starts only when the method is called **through the Spring proxy**.

When a method calls another method inside the same class using `this.method()`, the call **bypasses the proxy**, so the `@Transactional` annotation is ignored.

As a result, **no transaction is created**, even though the method is annotated with `@Transactional`.

---

#### Simple Example

```java
@Service
public class OrderService {

    public void placeOrder() {
        // Self-invocation
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        // Transaction will NOT start
    }
}
```

Here,

```
placeOrder()
      |
      | this.saveOrder()
      V
saveOrder()   ❌ Proxy is bypassed
               ❌ @Transactional ignored
```

---

#### Correct Approach

Call the transactional method through the Spring proxy.

```java
@Service
public class OrderService {

    @Autowired
    private OrderService orderService;

    public void placeOrder() {
        orderService.saveOrder();   // Goes through proxy
    }

    @Transactional
    public void saveOrder() {
        // Transaction starts
    }
}
```

Or, even better, move the transactional method to another service.

```java
@Service
public class OrderService {

    @Autowired
    private InventoryService inventoryService;  // Different bean = different proxy

    @Transactional
    public void placeOrder(Order order) {
        saveOrder(order);
        inventoryService.deductInventory(order);  // Goes through InventoryService's proxy
        sendNotification(order);
    }
}

@Service
public class InventoryService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void deductInventory(Order order) {
        // NOW this works! Called from a different bean = goes through proxy
        // REQUIRES_NEW creates an independent transaction
        inventoryRepository.deduct(order.getProductId(), order.getQuantity());
    }
}
```

#### One-line interview definition

> **Self-invocation occurs when a method inside a Spring bean calls another method of the same bean. Since the call bypasses the Spring AOP proxy, annotations like `@Transactional` are ignored, and no transaction is started.**

### Trap 2:  @Transactional(readOnly = true) Doesn't Prevent Writes.



#### Sets Hibernate FlushMode to MANUAL

Normally, Hibernate takes a snapshot of every entity you load. At commit time, it compares the current state with the snapshot (dirty checking) to detect changes. This costs CPU and memory.

`readOnly = true` tells Hibernate to set `FlushMode.MANUAL`. This means:

- No dirty checking happens
- No automatic flush at commit time
- Setter changes via dirty checking are **silently ignored**
- No UPDATE fired. No exception. No warning.

```
This Is Actually Worse Than Updating

Your setter call looks like it worked. Your code compiles. Your tests pass. But the data never changes in the database. Silent data loss is harder to debug than a wrong update.
```


#### 2. Sets JDBC Connection to Read-Only

Spring calls `connection.setReadOnly(true)` on the JDBC connection. But the behavior depends entirely on your database:

|Database|Behavior with readOnly = true|Safe?|
|---|---|---|
|**PostgreSQL**|Throws exception if you try to write via explicit save()/flush()|Yes|
|**MySQL**|Writes succeed silently. No error.|No|
|**H2 (Test DB)**|Writes succeed. Test passes.|No|

The Dangerous Combination

H2 in tests + MySQL in production + readOnly = true. Your tests pass because H2 allows writes. Production allows writes silently on MySQL. You only discover the bug when PostgreSQL throws an exception, or worse, when your data is silently stale.

#### Short Interview Answer (30–60 seconds)

> `@Transactional(readOnly = true)` is a performance optimization hint, not a write blocker. It signals that the transaction is intended for reads, but it does not guarantee that write operations are prevented.

However, it **does not prevent write operations**. If you call `save()`, `delete()`, or execute an update query inside a read-only transaction, the behavior depends on the JPA provider and the database. Some databases may reject it, but many allow it.



### Trap 3:  Catching Exceptions Inside @Transactional

### Short Interview Answer (30–60 seconds)

By default, Spring **rolls back a transaction only if an unchecked exception (`RuntimeException` or `Error`) is thrown out of the `@Transactional` method**.

If you **catch the exception inside the method and don't rethrow it**, Spring thinks the method completed successfully and **commits the transaction**.

So, even though an error occurred, the data may still be saved to the database.

**The Dangerous Code**

```java
@Transactional
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);   // succeeds, deducts money
    try {
        accountRepository.credit(toId, amount);  // fails
    } catch (Exception e) {
        log.error("Credit failed", e);
        // You "handled" it
    }
}
```

// Result: Money debited but never credited. Money disappeared.

### Three Fixes

#### Fix 1: Don't Catch Inside @Transactional (Recommended)

```java
@Transactional
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);
    accountRepository.credit(toId, amount);
    // Let exceptions propagate to the proxy
    // Handle them in @RestControllerAdvice
}
```

#### Fix 2: Re-throw After Logging

```java
@Transactional
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);
    try {
        accountRepository.credit(toId, amount);
    } catch (Exception e) {
        log.error("Credit failed for transfer {} -> {}", fromId, toId, e);
        throw e;  // Re-throw so proxy sees it and rolls back
    }
}
```

#### Fix 3: Manually Mark Rollback

```java
@Transactional
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);
    try {
        accountRepository.credit(toId, amount);
    } catch (Exception e) {
        log.error("Credit failed", e);
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        // Transaction will rollback even though exception was caught
    }
}
```



### Trap 4:  @Transactional Holding Connections Hostage

#### Short Interview Answer (30–60 seconds)

A `@Transactional` method **holds a database connection for the entire duration of the transaction**.

If you perform **slow operations** inside the transaction—such as calling an external API, sending an email, or processing a large file—the database connection remains occupied even though it's not being used.

This can exhaust the connection pool and reduce application performance.

```java
@Transactional
public void processOrder(Order order) {
    orderRepository.save(order);           // 2ms — needs DB connection
    paymentClient.charge(order);           // 3 seconds — external API call
    emailService.sendConfirmation(order);  // 2 seconds — SMTP call
    auditRepository.logEvent(order);       // 2ms — needs DB connection
}

// Connection borrowed at method START
// Connection held for 5+ SECONDS
// Only 4ms of actual DB work
```


HikariCP default pool size is 10. The connection is borrowed when the `@Transactional` method starts and returned when it ends. Not when the query finishes — when the METHOD finishes.

10 concurrent requests × 5 seconds each = pool empty. Request #11 waits 30 seconds and times out.

#### The Fix: Keep Transactions Short

```java
public void processOrder(Order order) {
    // Transactional — DB operations only
    saveOrderTransactional(order);

    // Non-transactional — external calls
    paymentClient.charge(order);
    emailService.sendConfirmation(order);

    // Transactional — DB operations only
    logAuditTransactional(order);
}

@Transactional
public void saveOrderTransactional(Order order) {
    orderRepository.save(order);  // Borrows connection for 2ms, returns immediately
}

@Transactional
public void logAuditTransactional(Order order) {
    auditRepository.logEvent(order);  // Borrows connection for 2ms, returns immediately
}
```


### Important: Put `@Transactional` on Service Layer

Usually, we put transaction logic in the **service layer**, not controller or repository.


### @Transactaion in checked exception

> **By default, Spring rolls back transactions only for `RuntimeException` and `Error`. Checked exceptions do not trigger rollback unless you specify `rollbackFor` in `@Transactional`.**

Spring **automatically rolls back only for**:
- `RuntimeException`
- `Error`

If a checked exception is thrown, Spring **commits the transaction** unless you explicitly configure rollback.

---

```java
@Transactional
public void createOrder() throws IOException {

    orderRepository.save(order);

    throw new IOException("File upload failed");
}
```

The order is still saved because `IOException` is a checked exception.

---

#### How to Roll Back for Checked Exceptions

Use the `rollbackFor` attribute.

```java
@Transactional(rollbackFor = IOException.class)
public void createOrder() throws IOException {

    orderRepository.save(order);

    throw new IOException("File upload failed");
}
```

Now Spring rolls back the transaction.

```
Transaction Starts
       |
Save Order
       |
IOException
       |
rollbackFor matches
       |
✅ Transaction ROLLED BACK
```

---

#### Interview Question

**Q: Why doesn't Spring roll back for checked exceptions by default?**

Checked exceptions usually represent **recoverable or expected business conditions** (e.g., `IOException`, `SQLException`), whereas unchecked exceptions typically indicate programming or system failures. Therefore, Spring's default behaviour is to roll back only for unchecked exceptions.

---


```java
// This commits even though PaymentException is thrown!

@Transactional
public void processPayment(Payment p) throws PaymentException {
    deductBalance(p);
    throw new PaymentException("Gateway timeout");  // checked exception
    // Proxy sees checked exception → COMMITS → balance is deducted
}

// Fix: explicitly tell Spring to rollback on all exceptions
@Transactional(rollbackFor = Exception.class)
public void processPayment(Payment p) throws PaymentException {
    deductBalance(p);
    throw new PaymentException("Gateway timeout");
    // Now it rolls back on ANY exception
}
```

Avoid:

```java
@Transactional

}
```

Use public service methods.

### Transaction propagation -

`Transaction Propagation` defines **what should happen if a transactional method calls another transactional method**.

The two most important propagation types asked in interviews are:
1. **REQUIRED (Default)**
2. **REQUIRES_NEW**

---

#### Propagation.REQUIRED (Default)

> **"If there's already a transaction, join it; otherwise create a new one. All operations share the same transaction, so if one fails, everything rolls back."**

This is the default propagation mode.

```java
@Transactional
```

is equivalent to

```java
@Transactional(propagation = Propagation.REQUIRED)
```

---

#### Example

Suppose you're buying a laptop.

- Save Order
- Reduce Inventory
- Deduct Payment

All three should succeed together.
If payment fails...
	Everything should roll back.

----

**OrderService**

```java
@Service
public class OrderService {

    @Autowired
    PaymentService paymentService;

    @Transactional
    public void placeOrder() {

        orderRepository.save(order);
        paymentService.makePayment();
        System.out.println("Order completed");
    }
}
```


**PaymentService**

```java
@Service
public class PaymentService {

    @Transactional
    public void makePayment() {

        paymentRepository.save(payment);
        throw new RuntimeException("Payment Failed");
    }
}
```

#### Flow

```
Existing Transaction?

YES
↓

Join It

NO
↓

Create New Transaction
```


---

#### Propagation.REQUIRES_NEW

> **"Always start a new transaction by suspending the current one. The new transaction commits or rolls back independently, regardless of what happens to the outer transaction."**

---

#### Example

Suppose an order fails, but you still want to save an audit log.

Audit logs should never disappear.

---

**AuditService**

```java
@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAudit(String message) {

        auditRepository.save(new Audit(message));
    }
}
```


**OrderService**

```java
@Service
public class OrderService {

    @Autowired
    AuditService auditService;

    @Transactional
    public void placeOrder() {

        orderRepository.save(order);

        auditService.saveAudit("Order Created");

        throw new RuntimeException("Order Failed");
    }
}
```


#### Flow

```
Transaction T1

Order Save

↓

Suspend


-------------------------

Transaction T2

Audit Save

Commit

-------------------------

Resume T1

↓

Failure

↓

Rollback T1
```

### Why do we need `@Modifying`?

`@Modifying` tells Spring Data JPA that the query **changes data** (INSERT, UPDATE, DELETE) instead of just reading it.

Without `@Modifying`, Spring assumes the query is a `SELECT` and throws an exception.


```java
@Modifying
@Query("UPDATE Employee e SET e.salary = :salary WHERE e.id = :id")
int updateSalary(Long id, Double salary);
```

#### Interview Answer (30 seconds)

> "`@Modifying` is used with `@Query` when executing UPDATE, DELETE, or INSERT statements. It tells Spring Data JPA that the query modifies the database instead of returning data. Without it, Spring treats the query as a SELECT and fails."


### In production, the **best practice** is:
- ✅ `@Modifying` → **Repository**
- ✅ `@Transactional` → **Service** (preferred)

You usually **do not** put `@Transactional` on the repository method unless there's a very specific reason.

**Repository**

```java
@Repository
public interface EmployeeRepository extends JpaRepository<Employee, Long> {

    @Modifying
    @Query("""
        UPDATE Employee e
        SET e.salary = :salary
        WHERE e.id = :id
    """)
    int updateSalary(Long id, Double salary);
}
```


**Service (Recommended)**

```java
@Service
public class EmployeeService {

    @Autowired
    private EmployeeRepository repository;

    @Transactional
    public void updateEmployeeSalary(Long id, Double salary) {

        int rows = repository.updateSalary(id, salary);

        if (rows == 0) {
            throw new RuntimeException("Employee not found");
        }
    }
}
```

#### Can we put `@Transactional` in Repository?

Yes, it works:

```java
@Modifying
@Transactional
@Query("UPDATE Employee e SET e.salary = :salary WHERE e.id = :id")
int updateSalary(Long id, Double salary);
```

But this is **not the recommended approach** because the repository should only handle data access, while the service should manage business logic and transaction boundaries.


#### @Transactional(readOnly=true) + @Modifying ?

`@Transactional(readOnly = true)` and `@Modifying` **should not be used together** for the same operation.

##### Why?

- `@Transactional(readOnly = true)` → Tells Spring **this transaction will only read data**.
- `@Modifying` → Tells Spring **this query will modify data (UPDATE/DELETE/INSERT)**.

These two intentions conflict.

---

**❌ Wrong**

```java
@Transactional(readOnly = true)
@Modifying
@Query("UPDATE Employee e SET e.salary = :salary WHERE e.id = :id")
int updateSalary(Long id, Double salary);
```

The transaction is marked read-only, but you're trying to update the database.

**✅ Correct (Read Operation)**

```java
@Transactional(readOnly = true)
public Employee getEmployee(Long id) {
    return repository.findById(id).orElseThrow();
}
```
