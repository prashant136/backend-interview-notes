## What is a Transaction?

A **transaction** is a group of database operations that should happen as **one single unit**.

Simple example: **Bank money transfer**

```
Transfer ₹1000 from Account A to Account B

Step 1: Deduct ₹1000 from Account A
Step 2: Add ₹1000 to Account B
```

Both steps must succeed together.

If Step 1 succeeds but Step 2 fails, money disappears. That is a serious bug.

So we need:

```
Either:
  both operations succeed

Or:
  both operations fail
```

This is called **all-or-nothing behavior**.

---

## Why do we need transactions?

Without transaction:

```
accountA.setBalance(accountA.getBalance() - 1000);
accountRepository.save(accountA);

// app crashes here

accountB.setBalance(accountB.getBalance() + 1000);
accountRepository.save(accountB);
```

Problem:

```
Account A money deducted
Account B money not added
Data becomes inconsistent
```

With transaction:

```
If everything is successful → COMMIT
If something fails → ROLLBACK
```

---

##  Commit and Rollback

### Commit

**Commit means permanently save the transaction changes into the database.**

Example:

```
Transaction starts
Deduct money from Account A
Add money to Account B
Everything successful
Commit
```

After commit, changes are saved permanently.

---

### Rollback

**Rollback means undo all changes made inside the transaction.**

Example:

```
Transaction starts
Deduct money from Account A
Add money to Account B
Error occurs
Rollback
```

Database goes back to the previous safe state.

---

## Simple real-world example

Imagine an e-commerce order system.

When user places an order:

```
1. Save order
2. Reduce product stock
3. Save payment details
4. Generate invoice
```

If payment fails, should we still reduce stock?

No.

So this whole operation should be transactional.

```
If payment succeeds:
    save order
    reduce stock
    save payment
    commit

If payment fails:
    rollback everything
```

## What is `@Transactional` in Spring Boot?

`@Transactional` tells Spring:

> Start a database transaction before this method runs.  
> If the method completes successfully, commit the transaction.  
> If the method throws an exception, rollback the transaction.

Example:

```
@Service
public class BankService {

    private final AccountRepository accountRepository;

    public BankService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Transactional
    public void transferMoney(Long fromAccountId, Long toAccountId, BigDecimal amount) {

        Account fromAccount = accountRepository.findById(fromAccountId)
                .orElseThrow(() -> new RuntimeException("From account not found"));

        Account toAccount = accountRepository.findById(toAccountId)
                .orElseThrow(() -> new RuntimeException("To account not found"));

        fromAccount.setBalance(fromAccount.getBalance().subtract(amount));
        toAccount.setBalance(toAccount.getBalance().add(amount));

        accountRepository.save(fromAccount);

        if (true) {
            throw new RuntimeException("Something failed");
        }

        accountRepository.save(toAccount);
    }
}
```

Because of `@Transactional`, if the exception occurs:

```
fromAccount update will also be rolled back
toAccount will not be updated
```

So database remains safe.

---

## How `@Transactional` works internally

Very simple flow:

```
Client calls service method
        ↓
Spring proxy intercepts the call
        ↓
Transaction starts
        ↓
Service method runs
        ↓
Repository/database operations happen
        ↓
If success → commit
If exception → rollback
```

Behind the scenes, Spring uses a **Transaction Manager**.

For JPA/Hibernate, commonly:

```
JpaTransactionManager
```

The transaction manager manages:

```
Database connection
Transaction start
Commit
Rollback
EntityManager / Hibernate session
```

---

## Important: Put `@Transactional` on Service Layer

Usually, we put transaction logic in the **service layer**, not controller or repository.

Good:

```
@Service
public class OrderService {

    @Transactional
    public void placeOrder() {
        // business logic
        // multiple DB operations
    }
}
```

Avoid this:

```
@RestController
public class OrderController {

    @Transactional
    @PostMapping("/orders")
    public void placeOrder() {
        // not ideal
    }
}
```

Why service layer?

Because service layer contains business flow:

```
create order
update stock
save payment
send notification
```

Transaction should cover business operation, not just one SQL query.

---

## Default rollback behavior

By default, Spring rolls back for:

```
RuntimeException
Error
```

Example:

```
throw new RuntimeException("Payment failed");
```

This will rollback.

But Spring does **not rollback by default** for checked exceptions.

Example:

```
throw new IOException("File error");
```

This may not rollback unless you mention:

```
@Transactional(rollbackFor = Exception.class)
public void placeOrder() throws Exception {
    // logic
}
```

Interview point:

> By default, `@Transactional` rolls back on unchecked exceptions like `RuntimeException`, but not on checked exceptions unless we configure `rollbackFor`.

## Example with rollback

```
@Transactional
public void createOrder(CreateOrderRequest request) {

    Order order = new Order();
    order.setUserId(request.getUserId());
    order.setStatus("CREATED");
    orderRepository.save(order);

    Product product = productRepository.findById(request.getProductId())
            .orElseThrow(() -> new RuntimeException("Product not found"));

    if (product.getStock() < request.getQuantity()) {
        throw new RuntimeException("Insufficient stock");
    }

    product.setStock(product.getStock() - request.getQuantity());
    productRepository.save(product);

    Payment payment = new Payment();
    payment.setOrderId(order.getId());
    payment.setAmount(request.getAmount());
    paymentRepository.save(payment);
}
```

If stock is not available:

```
Order save → rollback
Product update → rollback
Payment save → rollback
```

Nothing is permanently saved.

# What happens if you catch the exception?

Important mistake:

```
@Transactional
public void placeOrder() {
    try {
        orderRepository.save(order);
        throw new RuntimeException("Payment failed");
    } catch (Exception e) {
        System.out.println("Exception handled");
    }
}
```

Here, the exception is caught.

So Spring thinks:

```
Method completed successfully
Commit transaction
```

So transaction may commit.

Correct way:

```
@Transactional
public void placeOrder() {
    try {
        orderRepository.save(order);
        throw new RuntimeException("Payment failed");
    } catch (Exception e) {
        throw e;
    }
}
```

Or:

```
@Transactional
public void placeOrder() {
    try {
        orderRepository.save(order);
        throw new RuntimeException("Payment failed");
    } catch (Exception e) {
        throw new RuntimeException("Order failed", e);
    }
}
```

Interview point:

> If we catch and suppress the exception inside a transactional method, Spring may commit because it does not know an error happened.

# Common concurrency problems

## 1. Dirty Read

Transaction A updates data but does not commit.

Transaction B reads that uncommitted data.

Then Transaction A rolls back.

Now Transaction B read fake data.

Example:

```
A changes balance from ₹1000 to ₹500 but not committedB reads ₹500A rolls backActual balance is still ₹1000
```

This is dirty read.

---

## 2. Non-repeatable Read

Transaction A reads same row two times.

Between those reads, Transaction B updates and commits that row.

Transaction A sees different values.

Example:

```
A reads balance = ₹1000B updates balance = ₹700 and commitsA reads balance again = ₹700
```

Same transaction, same row, different result.

---

## 3. Phantom Read

Transaction A runs a query.

Transaction B inserts new matching rows and commits.

Transaction A runs same query again and sees extra rows.

Example:

```
A checks: SELECT * FROM orders WHERE amount > 1000Result: 5 rowsB inserts new order with amount 2000 and commitsA runs same query againResult: 6 rows
```

New row appeared like a phantom.

---

# Isolation levels

## 1. `READ_UNCOMMITTED`

```
@Transactional(isolation = Isolation.READ_UNCOMMITTED)
```

Can read uncommitted data.

Fast but unsafe.

Usually not used in real-world business systems.

---

## 2. `READ_COMMITTED`

```
@Transactional(isolation = Isolation.READ_COMMITTED)
```

Can read only committed data.

Prevents dirty reads.

But non-repeatable reads and phantom reads may still happen.

Common default in many databases, including PostgreSQL.

Use case:

```
Most normal business applications
```

---

## 3. `REPEATABLE_READ`

```
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

If you read the same row multiple times in one transaction, value remains consistent.

Prevents:

```
Dirty readNon-repeatable read
```

Use case:

```
Financial calculationsInventory checksReports needing consistent row data
```

---

## 4. `SERIALIZABLE`

```
@Transactional(isolation = Isolation.SERIALIZABLE)
```

Highest isolation.

Transactions behave as if they run one by one.

Prevents:

```
Dirty readNon-repeatable readPhantom read
```

But performance is slower.

Use case:

```
Critical financial systemsHigh-value inventory updateBooking systems
```

Example:

```
@Transactional(isolation = Isolation.SERIALIZABLE)public void bookSeat(Long seatId) {    Seat seat = seatRepository.findById(seatId)            .orElseThrow(() -> new RuntimeException("Seat not found"));    if (seat.isBooked()) {        throw new RuntimeException("Seat already booked");    }    seat.setBooked(true);    seatRepository.save(seat);}
```

---

# Isolation interview summary

|Isolation Level|Dirty Read|Non-repeatable Read|Phantom Read|Performance|
|---|---|---|---|---|
|`READ_UNCOMMITTED`|Possible|Possible|Possible|Fastest|
|`READ_COMMITTED`|Prevented|Possible|Possible|Good|
|`REPEATABLE_READ`|Prevented|Prevented|Depends on DB|Medium|
|`SERIALIZABLE`|Prevented|Prevented|Prevented|Slowest|

Interview answer:

> Isolation defines how one transaction is isolated from other concurrent transactions. Higher isolation gives better consistency but lower performance.

## `@Transactional(readOnly = true)`

For read operations:

```
@Transactional(readOnly = true)
public List<Product> getProducts() {
    return productRepository.findAll();
}
```

This tells Spring/Hibernate:

```
This method is only reading data.
No need to track changes heavily.
Can optimize performance.
```

Use for query methods.

Example:

```
@Service
public class ProductService {

    @Transactional(readOnly = true)
    public Product getProduct(Long id) {
        return productRepository.findById(id)
                .orElseThrow(() -> new RuntimeException("Product not found"));
    }
}
```

# Full example: Order placement

```
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;
    private final PaymentRepository paymentRepository;

    public OrderService(OrderRepository orderRepository,
                        ProductRepository productRepository,
                        PaymentRepository paymentRepository) {
        this.orderRepository = orderRepository;
        this.productRepository = productRepository;
        this.paymentRepository = paymentRepository;
    }

    @Transactional
    public void placeOrder(Long productId, int quantity, BigDecimal amount) {

        Product product = productRepository.findById(productId)
                .orElseThrow(() -> new RuntimeException("Product not found"));

        if (product.getStock() < quantity) {
            throw new RuntimeException("Insufficient stock");
        }

        product.setStock(product.getStock() - quantity);
        productRepository.save(product);

        Order order = new Order();
        order.setProductId(productId);
        order.setQuantity(quantity);
        order.setStatus("CREATED");
        orderRepository.save(order);

        Payment payment = new Payment();
        payment.setOrderId(order.getId());
        payment.setAmount(amount);
        payment.setStatus("SUCCESS");
        paymentRepository.save(payment);
    }
}
```

If any line fails:

```
product stock update rollback
order save rollback
payment save rollback
```

## 20. Bad practice: External API inside transaction

Avoid this:

```
@Transactional
public void placeOrder() {
    orderRepository.save(order);

    paymentGateway.callPaymentApi(); // slow external call

    productRepository.save(product);
}
```

Problem:

```
DB transaction stays open while waiting for external API.
This can lock database rows for longer time.
Performance issue.
```

Better approach:

```
1. Save order as PENDING
2. Call payment gateway
3. Update order status
```

Or use async/event-driven design.

## 21. Common mistakes with `@Transactional`

### Mistake 1: Calling method inside same class

```
@Service
public class OrderService {

    public void placeOrder() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        // transaction may not work here
    }
}
```

Why?

Because Spring uses proxy.

The transaction starts when method is called from outside the Spring bean through proxy.

Self-call inside same class bypasses proxy.

Better:

```
@Service
public class OrderService {

    private final OrderTransactionService orderTransactionService;

    public OrderService(OrderTransactionService orderTransactionService) {
        this.orderTransactionService = orderTransactionService;
    }

    public void placeOrder() {
        orderTransactionService.saveOrder();
    }
}
```

```
@Service
public class OrderTransactionService {

    @Transactional
    public void saveOrder() {
        // transaction works
    }
}
```

---

### Mistake 2: Using `@Transactional` on private method

Avoid:

```
@Transactional
private void saveOrder() {
}
```

Usually, it will not work as expected because proxy-based transaction management works on externally called methods.

Use public service methods.

---

### Mistake 3: Swallowing exception

Avoid:

```
@Transactional
public void placeOrder() {
    try {
        orderRepository.save(order);
        throw new RuntimeException("Failed");
    } catch (Exception e) {
        // swallowed
    }
}
```

Spring may commit because method completed normally.

---

### Mistake 4: Expecting rollback for checked exception

```
@Transactional
public void importFile() throws IOException {
    throw new IOException("File failed");
}
```

May not rollback by default.

Use:

```
@Transactional(rollbackFor = IOException.class)
public void importFile() throws IOException {
    throw new IOException("File failed");
}
```

Or:

```
@Transactional(rollbackFor = Exception.class)
public void importFile() throws Exception {
}
```

##  Interview-ready answer for `@Transactional`

You can say:

> `@Transactional` is used to manage database transactions declaratively in Spring. When a method annotated with `@Transactional` is called, Spring creates or joins a transaction before method execution. If the method completes successfully, Spring commits the transaction. If the method throws a runtime exception, Spring rolls back the transaction. It helps maintain data consistency in operations involving multiple database changes, like order creation, payment, and inventory update.

Then add:

> It works using Spring AOP proxy and a transaction manager such as `JpaTransactionManager`. We usually place it on service layer methods because service methods represent business use cases.

---

## Interview-ready answer for Commit and Rollback

> Commit means making all changes inside a transaction permanent in the database. Rollback means undoing all changes made inside the transaction when an error occurs. This ensures all-or-nothing behavior and keeps the database consistent.

---

## Interview-ready answer for Propagation

> Propagation defines how transactions behave when one transactional method calls another transactional method. The default is `REQUIRED`, which means join the existing transaction if present, otherwise create a new one. `REQUIRES_NEW` always creates a separate transaction, commonly used for audit logs where we want the log to be saved even if the main business transaction fails.

---

## Interview-ready answer for Isolation

> Isolation defines how visible one transaction’s changes are to other concurrent transactions. It helps prevent concurrency problems like dirty reads, non-repeatable reads, and phantom reads. Higher isolation improves consistency but can reduce performance. Common isolation levels are `READ_COMMITTED`, `REPEATABLE_READ`, and `SERIALIZABLE`.

---

## Final mental model

Remember this:

```
Transaction = All or nothing
Commit = Save permanently
Rollback = Undo changes
Propagation = What happens when transactions call other transactions
Isolation = How transactions behave when many users access data at same time
@Transactional = Spring annotation that starts, commits, or rolls back transaction automatically
```

For real projects:

```
Use @Transactional on service layer

Use readOnly = true for read methods

Use REQUIRED for normal business flows

Use REQUIRES_NEW for audit logs

Avoid long external API calls inside transaction

Do not swallow exceptions

Be careful with checked exceptions
```



# Transaction propagation -

**Propagation means:**

> When one transactional method calls another transactional method, Spring needs to decide whether the second method should use the same transaction, create a new transaction, or run without transaction.

## 1. Propagation.REQUIRED

This is the **default propagation**.

```
@Transactional(propagation = Propagation.REQUIRED)
```

or simply:

```
@Transactional
```

### Meaning

```
If transaction already exists:
    join the same transaction

If no transaction exists:
    create a new transaction
```

### Real-world use case

Normal business flow:

```
Place order
Reduce stock
Save payment
```

All should succeed together or fail together.

---

### Example

```
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final PaymentService paymentService;

    public OrderService(OrderRepository orderRepository,
                        PaymentService paymentService) {
        this.orderRepository = orderRepository;
        this.paymentService = paymentService;
    }

    @Transactional
    public void placeOrder() {

        Order order = new Order();
        order.setStatus("CREATED");
        orderRepository.save(order);

        paymentService.makePayment();

        System.out.println("Order placed successfully");
    }
}
```

```
@Service
public class PaymentService {

    private final PaymentRepository paymentRepository;

    public PaymentService(PaymentRepository paymentRepository) {
        this.paymentRepository = paymentRepository;
    }

    @Transactional(propagation = Propagation.REQUIRED)
    public void makePayment() {

        Payment payment = new Payment();
        payment.setStatus("SUCCESS");
        paymentRepository.save(payment);

        throw new RuntimeException("Payment failed after save");
    }
}
```

### What happens?

```
placeOrder() starts transaction
        ↓
orderRepository.save(order)
        ↓
makePayment() joins same transaction
        ↓
paymentRepository.save(payment)
        ↓
RuntimeException occurs
        ↓
Entire transaction rollback
```

Result:

```
Order rollback
Payment rollback
```

So `REQUIRED` means both methods are part of **one single transaction**.

---

## 2. Propagation.REQUIRES_NEW

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
```

### Meaning

```
Always create a new transaction.

If an old transaction already exists:
    pause the old transaction
    start a new transaction
```

### Real-world use case

Very useful for **audit logs**.

Example:

```
Order failed
Main transaction rollback
But failure log should still be saved
```

If audit log uses the same transaction, it will also rollback.

So we use `REQUIRES_NEW`.

---

### Example

```
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final AuditService auditService;

    public OrderService(OrderRepository orderRepository,
                        AuditService auditService) {
        this.orderRepository = orderRepository;
        this.auditService = auditService;
    }

    @Transactional
    public void placeOrder() {

        try {
            Order order = new Order();
            order.setStatus("CREATED");
            orderRepository.save(order);

            throw new RuntimeException("Payment failed");

        } catch (Exception e) {
            auditService.saveAuditLog("Order failed because payment failed");

            throw e;
        }
    }
}
```

```
@Service
public class AuditService {

    private final AuditLogRepository auditLogRepository;

    public AuditService(AuditLogRepository auditLogRepository) {
        this.auditLogRepository = auditLogRepository;
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAuditLog(String message) {

        AuditLog log = new AuditLog();
        log.setMessage(message);
        auditLogRepository.save(log);
    }
}
```

### What happens?

```
placeOrder() starts Transaction-1
        ↓
order saved
        ↓
exception occurs
        ↓
saveAuditLog() starts Transaction-2
        ↓
audit log saved
        ↓
Transaction-2 commits
        ↓
exception re-thrown
        ↓
Transaction-1 rollback
```

Result:

```
Order rollback
Audit log commit
```

This is the main difference between `REQUIRED` and `REQUIRES_NEW`.

---

## 3. Propagation.MANDATORY

```
@Transactional(propagation = Propagation.MANDATORY)
```

### Meaning

```
Transaction must already exist.

If transaction exists:
    join it

If no transaction exists:
    throw exception
```

So this method says:

> ==I must run inside an existing transaction. Do not call me alone.==

### Real-world use case

Use when a method should **never run alone**.

Example:

```
updateStock() should only run inside placeOrder()
```

You do not want someone to call `updateStock()` independently without a full order transaction.

---

### Example

```
@Service
public class OrderService {

    private final ProductService productService;
    private final OrderRepository orderRepository;

    public OrderService(ProductService productService,
                        OrderRepository orderRepository) {
        this.productService = productService;
        this.orderRepository = orderRepository;
    }

    @Transactional
    public void placeOrder() {

        Order order = new Order();
        order.setStatus("CREATED");
        orderRepository.save(order);

        productService.reduceStock(1L, 2);
    }
}
```

```
@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public void reduceStock(Long productId, int quantity) {

        Product product = productRepository.findById(productId)
                .orElseThrow(() -> new RuntimeException("Product not found"));

        product.setStock(product.getStock() - quantity);
        productRepository.save(product);
    }
}
```

### Case 1: Called from transactional method

```
@Transactional
public void placeOrder() {
    productService.reduceStock(1L, 2);
}
```

Works fine because transaction already exists.

### Case 2: Called directly without transaction

```
public void test() {
    productService.reduceStock(1L, 2);
}
```

Fails because no transaction exists.

Spring throws exception similar to:

```
No existing transaction found for transaction marked with propagation 'mandatory'
```

---

## 4. Propagation.SUPPORTS

```
@Transactional(propagation = Propagation.SUPPORTS)
```

### Meaning

```
If transaction exists:
    join it

If no transaction exists:
    run without transaction
```

So this method says:

> ==I can work inside a transaction, but I can also work without one.==
### Real-world use case

Useful for read-only helper methods.

Example:

```
getProductDetails()
checkUserExists()
calculateDiscount()
```

These methods can work with or without transaction.

---

## Example

```
@Service
public class ProductQueryService {

    private final ProductRepository productRepository;

    public ProductQueryService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional(propagation = Propagation.SUPPORTS, readOnly = true)
    public Product getProduct(Long productId) {

        return productRepository.findById(productId)
                .orElseThrow(() -> new RuntimeException("Product not found"));
    }
}
```

### Case 1: Called inside transaction

```
@Transactional
public void placeOrder() {
    Product product = productQueryService.getProduct(1L);
}
```

Then `getProduct()` joins existing transaction.

### Case 2: Called without transaction

```
public Product getProductDetails() {
    return productQueryService.getProduct(1L);
}
```

Then it runs without transaction.

So `SUPPORTS` is flexible.

---

## 5. Propagation.NOT_SUPPORTED

```
@Transactional(propagation = Propagation.NOT_SUPPORTED)
```

### Meaning

```
Always run without transaction.

If transaction exists:
    pause the current transaction
    run method without transaction
    resume old transaction after method completes
```

### Real-world use case

Use this for slow work that should not keep DB transaction open.

Example:

```
Calling external payment API
Calling third-party service
Sending email
Uploading file
Generating report
```

You usually do not want to hold database locks while calling slow external services.

---

### Example

```
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final ExternalPaymentService externalPaymentService;

    public OrderService(OrderRepository orderRepository,
                        ExternalPaymentService externalPaymentService) {
        this.orderRepository = orderRepository;
        this.externalPaymentService = externalPaymentService;
    }

    @Transactional
    public void placeOrder() {

        Order order = new Order();
        order.setStatus("PENDING");
        orderRepository.save(order);

        externalPaymentService.callPaymentGateway();

        order.setStatus("CONFIRMED");
        orderRepository.save(order);
    }
}
```

```
@Service
public class ExternalPaymentService {

    @Transactional(propagation = Propagation.NOT_SUPPORTED)
    public void callPaymentGateway() {

        System.out.println("Calling external payment API...");
        
        // slow external API call
    }
}
```

### What happens?

```
placeOrder() starts transaction
        ↓
order saved as PENDING
        ↓
callPaymentGateway() called
        ↓
current transaction is paused
        ↓
payment API call runs without transaction
        ↓
transaction resumes
        ↓
order updated as CONFIRMED
        ↓
commit
```

This avoids keeping DB transaction open during slow external API call.

---

## 6. Propagation.NEVER

```
@Transactional(propagation = Propagation.NEVER)
```

### Meaning

```
Method must run without transaction.

If transaction exists:
    throw exception
```

### Real-world use case

Rarely used.

Use it when a method should strictly never be called inside a transaction.

Example:

```
Non-transactional reporting
External system operation
Legacy system call
```

---

### Example

```
@Service
public class ReportService {

    @Transactional(propagation = Propagation.NEVER)
    public void generateLargeReport() {

        System.out.println("Generating report without transaction");
    }
}
```

### Case 1: Called without transaction

```
public void downloadReport() {
    reportService.generateLargeReport();
}
```

Works fine.

### Case 2: Called inside transaction

```
@Transactional
public void placeOrder() {
    reportService.generateLargeReport();
}
```

Fails because transaction already exists.

Spring throws exception similar to:

```
Existing transaction found for transaction marked with propagation 'never'
```

---

## 7. Propagation.NESTED

```
@Transactional(propagation = Propagation.NESTED)
```

### Meaning

```
Runs inside existing transaction,
but creates a savepoint.
```

A savepoint means:

```
Rollback only inner part,
not the full outer transaction.
```

### Real-world use case

Suppose you are importing a file with many records.

```
Import file
Save row 1
Save row 2
Save row 3 fails
Save row 4
```

You may want:

```
Failed row rollback
But full import continues
```

This is where `NESTED` can be useful.

Note: `NESTED` depends on database and transaction manager support.

---

### Example

```
@Service
public class ImportService {

    private final UserRepository userRepository;
    private final RowImportService rowImportService;

    public ImportService(UserRepository userRepository,
                         RowImportService rowImportService) {
        this.userRepository = userRepository;
        this.rowImportService = rowImportService;
    }

    @Transactional
    public void importUsers(List<String> names) {

        for (String name : names) {
            try {
                rowImportService.importSingleUser(name);
            } catch (Exception e) {
                System.out.println("Skipping failed user: " + name);
            }
        }
    }
}
```

```
@Service
public class RowImportService {

    private final UserRepository userRepository;

    public RowImportService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Transactional(propagation = Propagation.NESTED)
    public void importSingleUser(String name) {

        User user = new User();
        user.setName(name);
        userRepository.save(user);

        if (name.equals("bad-user")) {
            throw new RuntimeException("Invalid user");
        }
    }
}
```

### Input

```
["Amit", "Rahul", "bad-user", "Neha"]
```

### What happens?

```
Outer transaction starts
        ↓
Amit saved
        ↓
Rahul saved
        ↓
bad-user save starts nested transaction
        ↓
error occurs
        ↓
rollback to savepoint
        ↓
bad-user rollback only
        ↓
Neha saved
        ↓
outer transaction commits
```

Result:

```
Amit saved
Rahul saved
bad-user not saved
Neha saved
```

## Interview explanation

You can answer like this:

> Transaction propagation defines how a transactional method behaves when it is called inside another transactional method. The default propagation is `REQUIRED`, which means join the existing transaction or create a new one if none exists. `REQUIRES_NEW` always creates a separate transaction and suspends the existing one. It is useful for audit logging because the audit log can commit even if the main transaction rolls back. `MANDATORY` requires an existing transaction, otherwise it throws an exception. `NESTED` creates a savepoint inside the existing transaction, so the inner operation can rollback without rolling back the full outer transaction.


## Real-world order example summary

Imagine this flow:

```
placeOrder()
    save order
    reduce stock
    make payment
    save audit log
    call external notification API
```

Good transaction design:

```
@Transactional(propagation = Propagation.REQUIRED)
public void placeOrder() {
    // main order transaction
}
```

```
@Transactional(propagation = Propagation.MANDATORY)
public void reduceStock() {
    // must be called inside order transaction
}
```

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void saveAuditLog() {
    // should commit separately even if order fails
}
```

```
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void callExternalApi() {
    // should not hold DB transaction while calling external system
}
```

## One very important Spring Boot point

Propagation works properly when the method is called through a **Spring bean proxy**.

Good:

```
@Service
public class OrderService {

    private final AuditService auditService;

    public OrderService(AuditService auditService) {
        this.auditService = auditService;
    }

    @Transactional
    public void placeOrder() {
        auditService.saveAuditLog();
    }
}
```

Here, `AuditService` is another Spring bean, so propagation works.

Problem case:

```
@Service
public class OrderService {

    @Transactional
    public void placeOrder() {
        saveAuditLog();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAuditLog() {
        // may not create new transaction
    }
}
```

This is called **self-invocation**.

Because the method is called inside the same class, Spring proxy may be bypassed, so `REQUIRES_NEW` may not work as expected.

Best practice:

```
Keep separate transactional methods in separate service classes.
```

# Why do we need @Modifying?

By default, Spring Data JPA assumes that every `@Query` is a **SELECT query**.

Example:

```
@Query("SELECT e FROM Employee e")
List<Employee> findAllEmployees();
```

This works because it returns data.

---

But what if you want to execute:

```
UPDATE employee
SET salary = 50000
WHERE id = 1;
```

or

```
DELETE FROM employee
WHERE id = 1;
```

These queries do not return entities.

For such queries, Spring Data JPA needs to know:

> "This query modifies database data."

That's why we use `@Modifying`.

---

### Example Without @Modifying

```
@Query("UPDATE Employee e SET e.salary = :salary WHERE e.id = :id")
void updateSalary(Long id, Double salary);
```

Error:

```
QueryExecutionRequestException:
Not supported for DML operations
```

Because JPA thinks it's a SELECT query.

---

### Example With @Modifying

```
@Modifying
@Query("""
       UPDATE Employee e
       SET e.salary = :salary
       WHERE e.id = :id
       """)
int updateSalary(Long id, Double salary);
```

Now Spring understands:

```
This is UPDATE query.
Execute it as DML.
```

Return value:

```
int
```

represents affected rows.

Example:

```
int rows = repository.updateSalary(1L, 70000.0);
```

Result:

```
rows = 1
```

---

## What Queries Need @Modifying?

### UPDATE

```
@Modifying
@Query("UPDATE Employee e SET e.salary=:salary WHERE e.id=:id")
```

---

### DELETE

```
@Modifying
@Query("DELETE FROM Employee e WHERE e.id=:id")
```

---

### INSERT (Native Query)

JPQL doesn't support INSERT.

Use native query.

```
@Modifying
@Query(
 value = """
 INSERT INTO employee(name,salary)
 VALUES(:name,:salary)
 """,
 nativeQuery = true)
int insertEmployee(String name, Double salary);
```

# question: I have @Transactional annotation on Service class's method and @Modifying annotation on the method in the Repository class. Does method with @Transactional annotation applies to the method in the Repository with annotation @Modifying? what about @Transactional( readOnly = true ) with @Modifying ?

Excellent question. This goes into how Spring transaction propagation works internally.

## Case 1: @Transactional on Service + @Modifying on Repository

```
@Service
public class EmployeeService {

    @Transactional
    public void updateEmployee(Long id) {
        employeeRepository.updateSalary(id, 100000.0);
    }
}
```

Repository:

```
@Repository
public interface EmployeeRepository extends JpaRepository<Employee, Long> {

    @Modifying
    @Query("""
           UPDATE Employee e
           SET e.salary = :salary
           WHERE e.id = :id
           """)
    int updateSalary(Long id, Double salary);
}
```

### What happens?

```
Client
  ↓
Service Method
@Transactional
  ↓
Transaction Starts
  ↓
Repository Method
@Modifying
  ↓
UPDATE Query Executes
  ↓
Transaction Commits
```

Yes, the repository method participates in the transaction started by the service method.

The repository method does **not need its own @Transactional**.

This is actually the preferred production approach:

```
Service Layer
   → Transaction Boundary

Repository Layer
   → Database Access
```


---

## Case 2: Repository has @Modifying only

```
@Modifying
@Query(...)
int updateSalary(...);
```

and

```
public void updateEmployee() {
    repository.updateSalary(...);
}
```

(no transaction anywhere)

Result:

```
TransactionRequiredException
```

or provider-specific errors.

Because UPDATE/DELETE require a transaction.

---

## Case 3: @Transactional(readOnly=true) + @Modifying

```
@Transactional(readOnly = true)
public void updateEmployee() {
    repository.updateSalary(...);
}
```

Repository:

```
@Modifying
@Query(...)
int updateSalary(...);
```

#### This is WRONG.

You are saying:

```
Transaction is READ ONLY
```

but inside you're doing:

```
UPDATE
DELETE
INSERT
```

which modifies data.

---

## Why does readOnly=true exist?

For query optimization.

```
@Transactional(readOnly = true)
public Employee getEmployee(Long id) {
    return repository.findById(id).orElseThrow();
}
```

Benefits:

- No dirty checking
- Reduced flushing
- Better performance
- Intent is clear

Used for:

```
SELECT
SELECT
SELECT
```

Not for:

```
INSERT
UPDATE
DELETE
```

---

## What if Repository Method Has Its Own Transaction?

Example:

```
@Service
public class EmployeeService {

    @Transactional
    public void updateEmployee() {
        repository.updateSalary();
    }
}
```

Repository:

```
@Transactional
@Modifying
@Query(...)
int updateSalary();
```

Result:

```
Only ONE transaction exists.
```

Default propagation is:

```
Propagation.REQUIRED
```

Meaning:

```
Join existing transaction if present,
otherwise create a new one.
```

## Production Best Practice

### Service Layer

```
@Service
public class EmployeeService {

    @Transactional
    public void updateSalary(Long id, Double salary) {
        repository.updateSalary(id, salary);
    }
}
```

### Repository Layer

```
@Modifying(clearAutomatically = true)
@Query("""
       UPDATE Employee e
       SET e.salary=:salary
       WHERE e.id=:id
       """)
int updateSalary(Long id, Double salary);
```

Keep transaction management at the service layer.

---

## Interview Answer

>**Yes.** If a service method is annotated with `@Transactional`, any repository method called from it (including one annotated with `@Modifying`) participates in the same transaction. The repository method does not need its own `@Transactional` annotation unless you want special propagation behavior.

>**No**, `@Transactional(readOnly = true)` should not be used with `@Modifying` queries. A read-only transaction is intended for SELECT operations and may fail or behave unexpectedly when executing UPDATE, DELETE, or INSERT statements. Use a normal read-write transaction for modifying queries.

# ==How do you implement auditing in Spring Data JPA (@CreatedDate, @LastModifiedDate)?==

## What is Auditing in Spring?

**Auditing means automatically tracking “who created/updated data” and “when data was created/updated”.**

In real-world applications, almost every table needs audit information.

Example: `products` table

|id|name|price|created_at|updated_at|
|---|---|---|---|---|
|1|iPhone 15|75000|2026-06-15 10:00|2026-06-15 12:30|

So later we can know:

> This product was created at 10:00 and updated at 12:30.

In production apps, auditing is useful for:

- debugging issues
- tracking data changes
- compliance
- admin panels
- finding who changed something
- showing “created on” and “last updated on” in UI

---

## Without Auditing: Manual Approach

Normally, you may write:

```
product.setCreatedAt(LocalDateTime.now());
product.setUpdatedAt(LocalDateTime.now());
productRepository.save(product);
```

And during update:

```
product.setUpdatedAt(LocalDateTime.now());
productRepository.save(product);
```

Problem?

You have to repeat this everywhere.

In a large application, this becomes messy.

Spring Data JPA auditing solves this automatically.

---

## Spring Data JPA Auditing

Spring Data JPA provides annotations:

```
@CreatedDate
@LastModifiedDate
```

These automatically fill values when entity is saved or updated.

|Annotation|Meaning|
|---|---|
|`@CreatedDate`|fills creation time when row is first inserted|
|`@LastModifiedDate`|fills update time whenever row is updated|
|`@CreatedBy`|stores who created it|
|`@LastModifiedBy`|stores who last updated it|

---

## Real-World Use Case

Suppose you are building an **e-commerce product management system**.

Admin can create/update products.

When a product is added:

```
createdAt = current time
updatedAt = current time
```

When product price/name changes:

```
createdAt = same old value
updatedAt = new current time
```

---

### Step 1: Enable Auditing

In your main Spring Boot class:

```
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.data.jpa.repository.config.EnableJpaAuditing;

@SpringBootApplication
@EnableJpaAuditing
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

Important line:

```
@EnableJpaAuditing
```

This tells Spring:

> Please enable automatic auditing for JPA entities.

### Step 2: Create Entity

```
package com.example.demo.product;

import jakarta.persistence.*;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

import java.math.BigDecimal;
import java.time.LocalDateTime;

@Entity
@EntityListeners(AuditingEntityListener.class)
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private BigDecimal price;

    @CreatedDate
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;

    public Product() {
    }

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
    }

    // getters and setters
}
```

Important parts:

```
@EntityListeners(AuditingEntityListener.class)
```

This allows Spring Data JPA to listen to entity save/update events.

```
@CreatedDate
private LocalDateTime createdAt;
```

Automatically set on insert.

```
@LastModifiedDate
private LocalDateTime updatedAt;
```

Automatically set on insert and update.

```
updatable = false
```

This means `createdAt` should not change after insert.

}

### Step 4: Service

```
package com.example.demo.product;

import org.springframework.stereotype.Service;

import java.math.BigDecimal;

@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    public Product createProduct(String name, BigDecimal price) {
        Product product = new Product(name, price);
        return productRepository.save(product);
    }

    public Product updatePrice(Long productId, BigDecimal newPrice) {
        Product product = productRepository.findById(productId)
                .orElseThrow(() -> new RuntimeException("Product not found"));

        product.setPrice(newPrice);

        return productRepository.save(product);
    }
}
```

updatedAt

## Best Practice: Base Auditable Class

In production, we do not repeat auditing fields in every entity.

Instead, create a base class.

```
package com.example.demo.common;

import jakarta.persistence.Column;
import jakarta.persistence.EntityListeners;
import jakarta.persistence.MappedSuperclass;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

import java.time.LocalDateTime;

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseAuditableEntity {

    @CreatedDate
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;

    public LocalDateTime getCreatedAt() {
        return createdAt;
    }

    public LocalDateTime getUpdatedAt() {
        return updatedAt;
    }
}
```

Now entity becomes cleaner:

```
package com.example.demo.product;

import com.example.demo.common.BaseAuditableEntity;
import jakarta.persistence.*;

import java.math.BigDecimal;

@Entity
@Table(name = "products")
public class Product extends BaseAuditableEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private BigDecimal price;

    public Product() {
    }

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
    }

    // getters and setters
}
```

This is production-style.

# ==How do you handle optimistic and pessimistic locking in Spring Data JPA?==


This is a very important Spring Data JPA interview topic because it solves **concurrent update problems**.

Before learning Optimistic and Pessimistic Locking, understand the problem first.

## Problem: Lost Update

Imagine an e-commerce application.

Product:

```
Product
-------
id = 1
name = iPhone
stock = 10
```

Two users order the same product at the same time.

### User A

Reads stock = 10

### User B

Reads stock = 10

Now both reduce stock by 1.

### User A

```
UPDATE product SET stock = 9 WHERE id = 1;
```

### User B

```
UPDATE product SET stock = 9 WHERE id = 1;
```

Final stock:

```
9
```

Expected:

```
8
```

One update is lost.

This is called:

### Lost Update Problem

Locking is used to prevent this.

---

### Types of Locking in JPA

There are two major strategies:

```
1. Optimistic Locking
2. Pessimistic Locking
```

---

## 1. Optimistic Locking

### Intuition

Assume:

```
Conflicts are rare.
```

Let everyone read and update freely.

When saving:

```
Check if someone modified the record meanwhile.
```

If yes:

```
Fail the transaction.
```

Think:

```
Trust first.
Verify later.
```

This is Optimistic Locking.

---

### Real Life Example

Google Docs.

Two people open a document.

Both can edit.

When saving:

```
System checks whether document changed.
```

If conflict:

```
Refresh and try again.
```

---

### How JPA Implements Optimistic Locking

Using:

```
@Version
```

Example:

```
@Entity
public class Product {

    @Id
    private Long id;

    private String name;

    private Integer stock;

    @Version
    private Long version;
}
```

Database:

```
id | name   | stock | version
--------------------------------
1  | iPhone | 10    | 1
```

---

### What Happens Internally

User A reads:

```
stock=10
version=1
```

User B reads:

```
stock=10
version=1
```

---

#### User A Saves

JPA executes:

```
UPDATE product
SET stock = 9,
    version = 2
WHERE id = 1
AND version = 1;
```

Success.

Database:

```
stock=9
version=2
```

---

#### User B Saves

JPA executes:

```
UPDATE product
SET stock = 9,
    version = 2
WHERE id = 1
AND version = 1;
```

But database version is:

```
2
```

Not:

```
1
```

Rows affected:

```
0
```

JPA throws:

```
OptimisticLockException
```

or

```
ObjectOptimisticLockingFailureException
```

(Spring)

---

### Spring Boot Example

#### Entity

```
@Entity
public class Product {

    @Id
    private Long id;

    private Integer stock;

    @Version
    private Long version;
}
```

---

#### Service

```
@Transactional
public void updateStock(Long id) {

    Product product = repository.findById(id)
                                .orElseThrow();

    product.setStock(product.getStock() - 1);
}
```

No extra code required.

Just:

```
@Version
```

---

#### Handling Exception

```
try {

    service.updateStock(1L);

} catch (ObjectOptimisticLockingFailureException ex) {

    // retry
}
```

Many production systems:

```
Retry 3 times
Then fail
```

---

#### When to Use Optimistic Locking

Good for:

#### E-commerce Product Update

```
Rare conflicts
Many reads
Few writes
```

#### User Profile Update

```
Mostly reads
Occasional updates
```

#### Banking Statements

```
Read-heavy
```

---

### Advantages

No database lock.

```
High performance
High scalability
```

Suitable for:

```
Microservices
Cloud applications
```

---

### Disadvantages

If conflicts happen often:

```
Many retries
Poor user experience
```

---

## 2. Pessimistic Locking

### Intuition

Assume:

```
Conflicts WILL happen.
```

So:

```
Lock row immediately.
```

Others must wait.

Think:

```
Reserve first.Work later.
```

---

### Real Life Example

Bank Locker.

If someone enters locker room:

```
Others wait outside.
```

Nobody else can access it.

---

### ==JPA Pessimistic Lock Types - { Lock modes }

#### PESSIMISTIC_READ

```
LockModeType.PESSIMISTIC_READ
```

Other transactions can read.

Cannot update.

---

#### PESSIMISTIC_WRITE

```
LockModeType.PESSIMISTIC_WRITE
```

Most commonly used.

Others cannot:

```
Read (depends on DB)
Write
```

Must wait.

---

### PESSIMISTIC_FORCE_INCREMENT

Used rarely.

Like:

```
Lock + increment version
```

---

### Spring Data JPA Example

#### Repository:

```
@Repository
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Product findByIdForUpdate(Long id);
}
```

---

#### Service

```
@Transactional
public void updateStock(Long id) {

    Product product =
            repository.findByIdForUpdate(id);

    product.setStock(product.getStock() - 1);
}
```

---

#### Internal SQL

Hibernate generates something like:

```
SELECT *
FROM product
WHERE id = 1
FOR UPDATE;
```

Important:

```
FOR UPDATE
```

This locks the row.

---

### Example Flow

#### Transaction A

```
SELECT * FROM product
FOR UPDATE;
```

Row locked.

---

#### Transaction B

```
SELECT * FROM product
FOR UPDATE;
```

Blocked.

Waits.

---

#### Transaction A

```
COMMIT;
```

Lock released.

---

#### Transaction B

Continues.

---

### Real Production Use Cases

#### Banking Money Transfer

```
Account A
Account B
```

Money must never be corrupted.

Use:

```
Pessimistic Locking
```

Example:

```

```

Must be serialized.

---

#### Ticket Booking

Suppose:

```
1 seat left
```

100 users try booking.

Use:

```

```

Otherwise:

```
Overselling
```

may happen.

---

#### Inventory Reservation

```
Flash Sale

```

Heavy concurrent writes.

Often:

```
Pessimistic Locking
```

or distributed locking.

### Optimistic vs Pessimistic

|Feature|Optimistic|Pessimistic|
|---|---|---|
|Lock row immediately|No|Yes|
|Performance|High|Lower|
|Scalability|High|Lower|
|Read-heavy systems|Excellent|Not ideal|
|Write-heavy systems|Not ideal|Better|

|DB lock required|No|Yes|
|Common in microservices|Yes|Less|

## Interview Answer (2 Minutes)

> "Optimistic locking assumes conflicts are rare. We use `@Version` in the entity. JPA adds the version value in the update query and throws `OptimisticLockException` if another transaction has already modified the row. It provides better performance and is suitable for read-heavy applications."

> "Pessimistic locking assumes conflicts are likely. We use `@Lock(LockModeType.PESSIMISTIC_WRITE)` which generates SQL like `SELECT ... FOR UPDATE`. The row is locked immediately and other transactions must wait. It is commonly used in banking, ticket booking, and inventory reservation where data consistency is more important than throughput."


## 1. `@Version`

`@Version` is used for **Optimistic Locking**.

It means:

```
I will not lock the row while reading.
But before updating, I will check if someone changed it.
```

Entity:

```
@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Integer stock;

    @Version
    private Long version;
}
```

Database:

```
id | name   | stock | version
1  | iPhone | 10    | 0
```

When update happens, Hibernate runs something like:

```
UPDATE product
SET stock = 9, version = 1
WHERE id = 1 AND version = 0;
```

If another transaction already changed version to `1`, this update fails and Spring throws:

```
ObjectOptimisticLockingFailureException
```

---

## 2. `@Lock`

`@Lock` is used in Spring Data JPA repository for **Pessimistic Locking**.

Example:

```
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Optional<Product> findByIdForUpdate(@Param("id") Long id);
```

Hibernate generates SQL like:

```
SELECT *
FROM product
WHERE id = 1
FOR UPDATE;
```

This means:

```
Lock this row until transaction commits.
Other transactions must wait.
```

---

## 3. `@Transactional`

`@Transactional` starts and manages a database transaction.

Very important:

```
@Transactional
public void decreaseStock(Long productId) {
    Product product = repository.findByIdForUpdate(productId).orElseThrow();
    product.setStock(product.getStock() - 1);
}
```

Without `@Transactional`, pessimistic lock is almost useless because the lock is released immediately after query execution.

With `@Transactional`:

```
START TRANSACTION
SELECT ... FOR UPDATE
UPDATE product
COMMIT
```

The lock stays active until `COMMIT`.

## Full Example: Product Stock Booking

### Use Case

Product has only limited stock.

Two users place order at same time.

We want to avoid:

```
stock going negative
wrong stock value
overselling
```

---

### Entity

```
package com.example.demo.product;

import jakarta.persistence.*;

@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Integer stock;

    @Version
    private Long version;

    public Product() {
    }

    public Product(String name, Integer stock) {
        this.name = name;
        this.stock = stock;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public Integer getStock() {
        return stock;
    }

    public Long getVersion() {
        return version;
    }

    public void decreaseStock(int quantity) {
        if (stock < quantity) {
            throw new RuntimeException("Insufficient stock");
        }
        this.stock = this.stock - quantity;
    }
}
```

---

### Repository

```
package com.example.demo.product;

import jakarta.persistence.LockModeType;
import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;

import java.util.Optional;

public interface ProductRepository extends JpaRepository<Product, Long> {

    // Optimistic locking
    @Lock(LockModeType.OPTIMISTIC)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdWithOptimisticLock(@Param("id") Long id);

    // Pessimistic locking
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdWithPessimisticWriteLock(@Param("id") Long id);
}
```

---

### Service: Optimistic Locking

```
package com.example.demo.product;

import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class ProductOptimisticService {

    private final ProductRepository productRepository;

    public ProductOptimisticService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional
    public void orderProduct(Long productId, int quantity) {
        Product product = productRepository.findByIdWithOptimisticLock(productId)
                .orElseThrow(() -> new RuntimeException("Product not found"));

        product.decreaseStock(quantity);

        // No need to call save manually.
        // Hibernate dirty checking will update entity during transaction commit.
    }

    public void orderProductWithRetry(Long productId, int quantity) {
        int maxRetries = 3;

        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            try {
                orderProduct(productId, quantity);
                return;
            } catch (ObjectOptimisticLockingFailureException ex) {
                if (attempt == maxRetries) {
                    throw ex;
                }
            }
        }
    }
}
```

Important:

```
Optimistic locking does not block other users.
If conflict happens, one transaction succeeds and another fails.
Then we retry or return error.
```

---

### Service: Pessimistic Locking

```
package com.example.demo.product;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class ProductPessimisticService {

    private final ProductRepository productRepository;

    public ProductPessimisticService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional
    public void orderProduct(Long productId, int quantity) {
        Product product = productRepository.findByIdWithPessimisticWriteLock(productId)
                .orElseThrow(() -> new RuntimeException("Product not found"));

        product.decreaseStock(quantity);

        // Lock is released only when transaction commits.
    }
}
```

Internal SQL:

```
BEGIN;

SELECT *
FROM product
WHERE id = 1
FOR UPDATE;

UPDATE product
SET stock = 9
WHERE id = 1;

COMMIT;
```

### Which One Should You Use?

#### Use Optimistic Locking when:

```
Many reads
Few writes
Conflicts are rare
Performance is important
```

Examples:

```
User profile update
Product description update
Blog post update
Customer details update
```

---

#### Use Pessimistic Locking when:

```
Many concurrent writes
Conflict chance is high
Data correctness is critical
```

Examples:

```
Bank account balance
Wallet balance
Ticket booking
Hotel room booking
Inventory stock update during sale
```

---

### Interview Answer

You can say:

> In Spring Data JPA, optimistic locking is handled using `@Version`. JPA adds a version column to the update query. If another transaction has already modified the same row, the version mismatch causes an `OptimisticLockException` or Spring’s `ObjectOptimisticLockingFailureException`.

> Pessimistic locking is handled using `@Lock` with lock modes like `PESSIMISTIC_WRITE`. It usually generates SQL like `SELECT ... FOR UPDATE`, which locks the database row until the transaction commits. For this to work correctly, the service method must be annotated with `@Transactional`.

> I would use optimistic locking for read-heavy systems and pessimistic locking for high-contention use cases like wallet balance, ticket booking, or inventory reservation.
