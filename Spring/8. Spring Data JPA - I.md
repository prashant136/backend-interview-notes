
### JDBC

Before learning Spring Data JPA, Hibernate, etc., you must understand JDBC because everything ultimately talks to the database through JDBC.

Think of JDBC as:

> "A bridge between Java application and Database."

Without JDBC, Java cannot directly talk to PostgreSQL, MySQL, Oracle, etc.

---

### What is JDBC ?

**JDBC = Java Database Connectivity**

`a standard Java API that enables Java applications to connect and interact with relational databases.`

It is a Java API that allows Java applications to:

- Connect to database
- Execute SQL queries
- Retrieve data
- Update data
- Delete data

---

Without JDBC:

```
Database-specific code
```

For PostgreSQL:

```
postgres code
```

For MySQL:

```
mysql code
```

For Oracle:

```
oracle code
```

Very difficult.


### What is Spring JDBC and connection pool HikariCP.

**Spring JDBC** is a core module within the Spring Framework that simplifies low-level database operations by eliminating repetitive boilerplate code. It provides a clean, abstract API layer over standard Java Database Connectivity (JDBC) while giving developers direct control over writing plain SQL queries.

-----
### What is Connection Pool?

A connection pool maintains already-open database connections.

A connection pool is a cache of reusable, pre-established database connections. Instead of opening and closing a new connection for every single client request—which is resource-intensive and slow—an application borrows an idle connection from the pool, uses it, and returns it for others to use.

An **idle connection** -> database connection is open but doing nothing.

---

##### With Pool

Startup:

```
Create 10 connections
```

Store them:

```
Pool

C1
C2
C3
...
C10
```

Request comes:

```
Borrow C1
```

Query executes.

Return:

```
C1 back to pool
```

No new creation.

Very fast.

---

### What is HikariCP?

HikariCP is the most popular JDBC connection pool.

**HikariCP** is a zero-overhead, ultra-fast JDBC connection pool. It is the default connection pooling framework integrated into **Spring Boot**. Instead of creating and destroying database connections for every query, HikariCP maintains a reusable pool of ready-to-use connections to minimize latency and scale performance.

---


#### Why HikariCP?

Answer:

> Creating database connections is expensive. HikariCP maintains a pool of reusable connections, reducing connection creation overhead and improving application performance and scalability.

### ORM?

**ORM** (Object-Relational Mapping) is a programming technique that lets you interact with a relational database using your preferred object-oriented programming (OOP) language, instead of writing raw SQL queries. It acts as a bridge, converting data between incompatible type systems in code and databases.

Example - Hibernate

#### Benefits?

- Caching support
- Increased Productivity
- Database Independence
- Built-in Security

#### Drawbacks?

- Performance Overhead
- N+1 query problem

- Steeper learning curve

### JPA / Spring Data JPA

JPA (Java Persistence API) is a standard specification for object-relational mapping (ORM) in Java, while **Spring Data JPA** is a framework that builds an abstraction layer on top of JPA to dramatically reduce boilerplate data-access code.

To put it simply: JPA defines the standard rules and interfaces, an ORM provider like **Hibernate** implements those rules, and **Spring Data JPA** wraps around them to make database operations fast and clean.

## Use of transient Keyword ?

The `transient` keyword tells Java:

> "Do not serialize this field."

Serialization means converting an object into a byte stream so that it can be stored in a file, sent over a network, cached in Redis, etc.

Serialization and Deserialization are important Java mechanisms used to convert objects into a byte stream and reconstruct them back into objects. Together, they enable object persistence, data transfer, and communication between different systems while preserving an object's state.

- Serialization converts an object into a byte stream for storage or transmission.
- Deserialization converts the byte stream back into the original Java object.

When you mark a field as `transient`, you instruct the Java Virtual Machine (JVM) to ignore it, meaning its value will not be saved when the object is converted into a byte stream.


Why Use `transient`?

- **Security:** Prevents sensitive data—like passwords, authentication tokens, or payment details—from being written to disk or sent over a network.

---


```java
import java.io.Serializable;

public class Employee implements Serializable {

    private int id;
    private String name;

    transient String password; // won't be serialized

    public Employee(int id, String name, String password) {
        this.id = id;
        this.name = name;
        this.password = password;
    }
}
```


Password also gets stored.

---
#### With transient

```
transient String password;
```

Serialized data:

```

name=Prashant
```

Password is ignored.

Ignored during Java Serialization.

## What is the purpose of @GeneratedValue in JPA?  What are the different strategies supported by @GeneratedValue?  Explain the difference between GenerationType.AUTO, IDENTITY, SEQUENCE, and TABLE.






## Problem: Who will generate the Primary Key?

Suppose we have a User table:

```
@Entity
public class User {

    @Id
    private Long id;

    private String name;
}
```

When we save:

```
User user = new User();
user.setName("Prashant");

userRepository.save(user);
```

What should be the value of `id`?

```
id = ?
```

Options:

1. Java Application generates it.
2. Database generates it.

Without a strategy, JPA doesn't know how to generate the ID.


# All Strategies

```
@GeneratedValue(strategy = GenerationType.AUTO)

@GeneratedValue(strategy = GenerationType.IDENTITY)

@GeneratedValue(strategy = GenerationType.SEQUENCE)

@GeneratedValue(strategy = GenerationType.TABLE)
```

Let's understand each deeply.

# Comparison Table

|Strategy|Who Generates ID|Performance|Database|
|---|---|---|---|
|AUTO|Hibernate decides|Depends|Any|
|IDENTITY|Database AUTO_INCREMENT|Medium|MySQL|
|SEQUENCE|Database Sequence|Best|PostgreSQL, Oracle|
|TABLE|Generator Table|Poor|Any|

---

### Interview Answer (2-Min Version)

`@GeneratedValue` is used with `@Id` to automatically generate primary key values for entities.

JPA supports four strategies:

1. **AUTO** – Hibernate chooses the appropriate strategy based on the database.
2. **IDENTITY** – Uses database auto-increment columns. Common in MySQL.
3. **SEQUENCE** – Uses database sequence objects. Common in PostgreSQL and Oracle. Supports efficient batch inserts.
4. **TABLE** – Uses a separate table to maintain IDs. Portable but slower due to additional queries and locking.


# ==How does GenerationType.AUTO decide which strategy to use?==

This is where many developers get confused.

`GenerationType.AUTO` does **not** generate IDs itself.

It simply tells Hibernate:

> "You choose the best ID generation strategy for the database I'm using."

---

### How Hibernate Decides

When the application starts:

```
Spring Boot
    ↓
Hibernate
    ↓
Database Connection
    ↓
Read Database Metadata
```

Hibernate checks:

```
spring.datasource.url
```

Example:

```
jdbc:mysql://localhost:3306/mydb
```

Hibernate knows:

```
Database = MySQL
```

or

```
jdbc:postgresql://localhost:5432/mydb
```

Hibernate knows:

```
Database = PostgreSQL
```

---

### Example 1: PostgreSQL

Configuration:

```
spring.datasource.url=jdbc:postgresql://localhost:5432/shopdb
```

Entity:

```
@Entity
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.AUTO)
    private Long id;
}
```

Hibernate detects:

```
PostgreSQL
```

PostgreSQL supports sequences very efficiently.

Therefore Hibernate usually chooses:

```
SEQUENCE
```

and creates something like:

```
create sequence user_seq;
```

Internally it behaves almost like:

```
@GeneratedValue(strategy = GenerationType.SEQUENCE)
```

---

### Example 2: MySQL

Configuration:

```
spring.datasource.url=jdbc:mysql://localhost:3306/shopdb
```

Hibernate detects:

```
MySQL
```

Historically MySQL didn't support database sequences like PostgreSQL.

So Hibernate commonly uses an identity-style mechanism.

Effectively:

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

and table column becomes:

```
id BIGINT AUTO_INCREMENT
```

---

### Why Senior Developers Often Avoid AUTO

Consider:

Today:

```
Database = PostgreSQL
```

AUTO chooses:

```
SEQUENCE
```

Later company migrates to:

```
MySQL
```

AUTO may switch to:

```
IDENTITY
```

Now performance characteristics change.

Batch inserts may behave differently.

Because of this, many teams explicitly write:

```
@GeneratedValue(strategy = GenerationType.SEQUENCE)
```

or

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

so the behavior is obvious.

---

### Interview Answer

**How does `GenerationType.AUTO` decide which strategy to use?**

> `AUTO` delegates the decision to the JPA provider (typically Hibernate). Hibernate examines the database dialect at startup and selects the most appropriate identifier generation strategy supported by that database. For example, PostgreSQL and Oracle typically use `SEQUENCE`, while MySQL commonly uses `IDENTITY`. The exact choice can vary depending on the Hibernate version and database capabilities. Therefore, many production applications prefer explicitly specifying `SEQUENCE` or `IDENTITY` instead of relying on `AUTO`.



# ==When would you use GenerationType.SEQUENCE over IDENTITY ? batch insert performance ? batch insert in postgres and mysql. (possibilities and best practice). is this the reason behind why postgres is write heavy and mysql is read heavy ?== 

Yes, **performance and batch insert** is the main reason to prefer `SEQUENCE` over `IDENTITY`, especially in **PostgreSQL + Hibernate**.

## 1. Core difference

### IDENTITY

Database generates ID **during INSERT**.

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Flow:

```
Hibernate: INSERT user
Database: generates id
Hibernate: waits for generated id
```

So Hibernate cannot know the ID before insert.

Result:

```
insert one row → wait
insert one row → wait
insert one row → wait
```

This hurts batching.

---

### SEQUENCE

Hibernate gets ID **before INSERT**.

```
@GeneratedValue(strategy = GenerationType.SEQUENCE)
private Long id;
```

Flow:

```
Hibernate: SELECT nextval('user_seq')
Database: gives id 101
Hibernate: INSERT user with id 101
```

Hibernate already knows IDs before inserting.

Result:

```
get ids first
then batch multiple inserts together
```

Better for write-heavy systems.

---

## 2. Why SEQUENCE is better for batch inserts

Suppose you save 1000 users.

### With IDENTITY

Hibernate usually has to do:

```
INSERT user 1 → get id
INSERT user 2 → get id
INSERT user 3 → get id
...
INSERT user 1000 → get id
```

Hard to batch efficiently.

---

### With SEQUENCE

Hibernate can do:

```
Get ids: 1 to 1000
Batch INSERT users together
```

Example:

```
insert into users (id, name) values (?, ?)
insert into users (id, name) values (?, ?)
insert into users (id, name) values (?, ?)
```

These can be sent in batches.

---

## 3. PostgreSQL best practice

For PostgreSQL, prefer:

```
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
@SequenceGenerator(
    name = "user_seq",
    sequenceName = "user_sequence",
    allocationSize = 50
)
private Long id;
```

Important part:

```
allocationSize = 50
```

This means Hibernate can reserve IDs in chunks.

Example:

```
Hibernate asks DB once
DB gives range 1-50
Hibernate uses those IDs in memory
```

This reduces database round trips.

Good for:

```
high insert volume
bulk import
orders
payments
logs
catalog ingestion
event tables
```

---

## 4. MySQL best practice

MySQL commonly uses:

```
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Because MySQL traditionally uses:

```
AUTO_INCREMENT
```

Example:

```
id BIGINT AUTO_INCREMENT PRIMARY KEY
```

For normal CRUD apps, this is fine.

But for huge batch inserts, `IDENTITY` is less efficient with Hibernate.

---

## 5. Can MySQL do batch inserts?

Yes, MySQL can do batch inserts at SQL level:

```
insert into users(name) values
('A'),
('B'),
('C');
```

But with JPA/Hibernate + `GenerationType.IDENTITY`, batching is limited because Hibernate needs generated IDs immediately.

So:

```
MySQL database supports batch insert
but Hibernate + IDENTITY makes batching harder
```

That is the important interview point.

---

## 6. Can PostgreSQL use IDENTITY?

Yes.

PostgreSQL supports identity columns:

```
id BIGINT GENERATED BY DEFAULT AS IDENTITY
```

And Hibernate can use:

```
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

But in Hibernate/JPA, for write-heavy apps, PostgreSQL `SEQUENCE` is usually preferred because it works better with batching.

---

## 7. Is this why PostgreSQL is write-heavy and MySQL is read-heavy?

Not exactly.

This ID generation difference is **one small reason**, not the full reason.

PostgreSQL is often preferred for complex/write-heavy systems because of:

```
strong ACID behavior
MVCC implementation
advanced locking
better concurrency for complex workloads
powerful indexing
JSONB
CTEs
window functions
partial indexes
transactional DDL
rich query planner
sequence support
```

MySQL is often used for read-heavy web apps because:

```
simple setup
fast primary-key reads
replication ecosystem
widely used with read replicas
good for simple OLTP workloads
easy horizontal read scaling
```

But saying:

```
Postgres = write-heavy
MySQL = read-heavy
```

is too simplistic.

Better interview answer:

> PostgreSQL is often chosen for complex transactional and write-heavy workloads because of its strong consistency, MVCC, advanced indexing, rich SQL features, and sequence-based ID generation. MySQL is often chosen for simpler high-read web workloads because it is easy to operate, performs very well for primary-key reads, and has strong replication support. But both databases can handle reads and writes well when designed properly.

---

## Final rule

Use this:

```
PostgreSQL + Hibernate + high inserts → SEQUENCE
MySQL + normal CRUD → IDENTITY
Legacy/portable DB → AUTO or TABLE rarely
Production code → avoid AUTO, be explicit
```

## What is CrudRepository and JpaRepository ?

### What is Repository?

The **Repository Layer** (also called the Data Access Layer) in **Spring Boot** manages database interactions, handling operations like saving, fetching, updating, and deleting records.

---

### CrudRepository?

Spring provides an interface called:

```
CrudRepository
```

`CrudRepository` provides only the most basic, lightweight CRUD (Create, Read, Update, Delete) methods.

```
public interface CrudRepository<T, ID>

T  = Entity
ID = Primary Key Type
```


```
public interface UserRepository
        extends CrudRepository<User, Long> {
}
```

Now Spring automatically gives you:

```
save()
findById()
findAll()
delete()
deleteById()
existsById()
count()
```


### JpaRepository?

`JpaRepository` extends `CrudRepository` (via `PagingAndSortingRepository`) to add JPA-specific features like pagination, sorting, batch operations, and persistence context management (e.g., `flush()`, `saveAndFlush()`.

---

### Using JpaRepository

```
public interface UserRepository
        extends JpaRepository<User, Long> {
}
```

---

### Which One Should You Use?

#### Interviews

> CrudRepository provides basic CRUD operations.

> JpaRepository extends PagingAndSortingRepository which extends CrudRepository.

> JpaRepository provides all CRUD features plus pagination, sorting, batch operations, flush
and other JPA-specific functionality.

> In modern Spring Boot applications, JpaRepository is generally preferred because it
includes all capabilities of CrudRepository along with additional enterprise-level features.

## How do you use @Query annotation for custom JPQL queries ?


**JPQL = Java Persistence Query Language**

It looks like SQL, but it works on **Entity class names and Java field names**, not table names and column names.

Suppose entity:

```java
@Entity
@Table(name = "users")
public class User {

    @Id
    private Long id;

    private String name;

    private String email;

    private String status;
}
```

SQL uses table/column:

```java
SELECT * FROM users WHERE email = 'abc@gmail.com';
```

JPQL uses entity/field:

```java
SELECT u FROM User u WHERE u.email = :email
```

Important difference:

```
SQL  → table name, column name
JPQL → entity name, field name
```

---

### Why do we need custom JPQL queries?

Spring Data JPA can generate queries automatically:

```java
User findByEmail(String email);
```

But sometimes method names become too long:

```java
List<User> findByStatusAndNameContainingIgnoreCaseOrderByNameAsc(...)
```

For complex conditions, joins, projections, update queries, we use:

```java
@Query
```


---
### Example
#### Entity

```java
@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
```

## What is the role of EntityManager in Spring Data JPA?

> **EntityManager is the core JPA interface responsible for managing the lifecycle of entities (objects) and communicating with the database.**

Think of it as:

> **EntityManager = Manager between your Java objects and the database.**

Spring Data JPA repositories (`JpaRepository`) internally use `EntityManager`.

---

### Main Responsibilities

#### 1. Persist (Insert)

```java
entityManager.persist(product);
```

Equivalent SQL

```sql
INSERT INTO product ...
```

---

#### 2. Find (Read)

```java
Product product = entityManager.find(Product.class, 1L);
```

Equivalent SQL

```sql
SELECT * FROM product WHERE id = 1;
```

---

#### 3. Update

```java
product.setPrice(50000);
```

No SQL is executed immediately.

When the transaction commits,

```sql
UPDATE product
SET price = 50000
WHERE id = 1;
```

This happens automatically because of **Dirty Checking**.

---

#### 4. Delete

```java
entityManager.remove(product);
```

Equivalent SQL

```sql
DELETE FROM product WHERE id = 1;
```

---

#### 5. Execute Queries

```java
entityManager.createQuery(
    "SELECT s FROM Student s"
);
```

Native SQL

```java
entityManager.createNativeQuery(
    "SELECT * FROM student"
);
```

-----
### Why do we rarely use it directly?

Because Spring Data JPA provides `JpaRepository`.

Instead of writing

```java
entityManager.persist(product);
```

we simply write

```java
repository.save(product);
```


---

#### A simple interview answer is:

> **EntityManager is the core JPA interface that manages the lifecycle of entities. It acts as a bridge between the Java application and the database. Spring Data JPA repositories internally use EntityManager to perform operations like persist, find, update, remove, and execute JPQL/native queries.**

---

### Easy Memory Trick

**EntityManager = CRUD + Entity Lifecycle + Persistence Context**


### Persistence Context ?

> **Persistence Context is a temporary memory where EntityManager keeps the entities it is working with.**

---

#### Why is it useful?

- ✅ Tracks entity changes (**Dirty Checking**)
- ✅ Avoids duplicate database queries (**First-Level Cache**)
- ✅ Synchronizes changes to the database on commit

---

#### Interview Answer (20 seconds)

> **Persistence Context is the first-level cache managed by the `EntityManager`. It stores and tracks entities during a transaction. Any changes made to managed entities are automatically detected and synchronized with the database when the transaction commits.**

-----------------
### Dirty Checking ?

> **Dirty Checking is a JPA feature where the `EntityManager` automatically detects changes made to managed entities and updates the database when the transaction commits.**

Or even simpler:

> **Modify the object → JPA automatically updates the database.**

---

### When does Dirty Checking work?

✅ Inside a transaction (`@Transactional`)

✅ Entity must be **managed** (loaded by the `EntityManager`)

If the entity is detached, Dirty Checking won't happen.

---

### Interview Answer (20 seconds)

> **Dirty Checking is a JPA mechanism where the `EntityManager` automatically detects changes made to managed entities inside the Persistence Context. When the transaction commits, it generates the required `UPDATE` statement automatically, so we don't need to call `update()` or `save()` for every modification.**

---

#### Flushing -

> **Flushing** in Hibernate is the process of synchronizing the in-memory state of the persistence context (the first-level cache) with the underlying database. When a flush occurs, Hibernate translates pending entity changes (inserts, updates, deletes) into SQL statements and executes them against the database.
**flushing is not the same as committing**. A flush executes SQL commands, but the changes remain uncommitted and can still be rolled back unless the transaction is officially committed.
#### Easy Memory Trick

```
Load Entity
      ↓
Modify Object
      ↓
Dirty Checking
      ↓
Automatic UPDATE
```

### One-line memory aid

> **Dirty Checking = JPA automatically detects changes to managed entities and updates the database at transaction commit.**

### What is [mappedBy] ?

#### Ownership

JPA calls this the **owning side**.

In JPA bidirectional relationships, ==the **owning side controls the database state** (manages the foreign key column or join table), while the **inverse side is a read-only mirror** used strictly for object navigation==

Owning side:

```
@ManyToOneUser user;
```

Inverse side:

```
@OneToMany(mappedBy = "user")
List<Order> orders;
```

The FK is stored in:

```
orders.user_id
```

so Order owns the relationship.

## What is FetchType?

Fetch type decides:

> When should related data be loaded?

Two options:

```
FetchType.EAGER
FetchType.LAZY
```

---

### EAGER

```
@OneToOne(fetch = FetchType.EAGER)
```

means:

> Load related entity immediately.

Example:

```
User user = userRepo.findById(1L);
```

Hibernate generates:

```
SELECT *
FROM user u
LEFT JOIN passport p
ON u.passport_id = p.id
WHERE u.id = 1;
```

User and Passport come together.

---

### LAZY

```
@OneToMany(fetch = FetchType.LAZY)
```

means:

> Don't load orders immediately.

```
User user = userRepo.findById(1L);
```

SQL:

```
SELECT * FROM user WHERE id = 1;
```

Only user loaded.

Later:

```
user.getOrders();
```

Then Hibernate fires:

```
SELECT *
FROM orders
WHERE user_id = 1;
```

This is lazy loading.

---

## Why is OneToMany default LAZY?

This is the most important question.

Imagine:

```
User user = userRepo.findById(1L);
```

User has:

```
10,000 orders
```

If OneToMany were EAGER:

```
SELECT *
FROM user
JOIN orders
```

Hibernate would immediately load:

```
1 User

10,000 Orders
```

even if you never use orders.

Huge memory waste.

---

Another example:

```
Customer
   -> Orders
      -> OrderItems
         -> Products
```

EAGER loading can explode into:

```
Customer
+ 100 Orders
+ 5000 OrderItems
+ 5000 Products
```

for a simple query.

Therefore:

```
@OneToMany
```

defaults to:

```
LAZY
```

to prevent loading huge collections.

---

## Why is ManyToOne default EAGER?

Consider:

```
Order order = orderRepo.findById(101L);
```

An order usually belongs to exactly one user.

Loading:

```
Order
+
User
```

is cheap.

The assumption of JPA designers was:

> If you're working with an Order, you'll probably need its User.

Therefore:

```
@ManyToOne
```

default:

```
EAGER
```


---

## Why is OneToOne default EAGER?

Consider:

```
User -> Passport
```

Only one related record.

Loading:

```
User + Passport
```

is usually cheap.

Therefore JPA chose:

```
@OneToOne
```

default:

```
EAGER
```

---

## Reality in Modern Applications

Most experienced Spring developers override defaults.

Instead of:

```
@ManyToOne
```

they write:

```
@ManyToOne(fetch = FetchType.LAZY)
```

and

```
@OneToOne(fetch = FetchType.LAZY)
```

because:

- Better performance
- Avoid unnecessary joins
- More control

Nowadays many teams prefer:

```
OneToOne -> LAZY
ManyToOne -> LAZY
OneToMany -> LAZY
```

and explicitly fetch data when needed using:

```
JOIN FETCH
@EntityGraph
DTO projections
```

| Annotation   | Meaning    | FK Stored In            | Default Fetch |
| ------------ | ---------- | ----------------------- | ------------- |
| `@OneToOne`  | One ↔ One  | Either table            | EAGER         |
| `@ManyToOne` | Many → One | Many side table         | EAGER         |
| `@OneToMany` | One → Many | FK exists in Many table | LAZY          |

## Explain the difference between FetchType.LAZY and FetchType.EAGER ?

This is another frequently asked Spring Boot interview question.

---

### What is Fetch Type?

> **Fetch Type decides when JPA loads related entities from the database.**

There are two types:

- `FetchType.LAZY`
- `FetchType.EAGER`

---

### 1. FetchType.LAZY (Load only when needed)

> **Related data is NOT loaded immediately. It is loaded only when you access it.**

#### Example

Customer → Orders

```java
@Entity
class Customer {

    @OneToMany(mappedBy = "customer", fetch = FetchType.LAZY)
    List<Order> orders;
}
```

Suppose you execute:

```java
Customer customer = repository.findById(1L).get();
```

JPA executes:

```sql
SELECT * FROM customer WHERE id = 1;
```

Orders are **not fetched**.

Only when you do:

```java
customer.getOrders();
```

JPA executes another query:

```sql
SELECT * FROM orders WHERE customer_id = 1;
```

#### Real-world Analogy

Think of **Netflix**.

When you open the app, it **doesn't download every movie**.

It downloads a movie **only when you click Play**.

That's **LAZY loading**.

---

### 2. FetchType.EAGER (Load immediately)

> **Related data is loaded immediately along with the main entity.**

```java
@Entity
class Customer {

    @OneToMany(mappedBy = "customer", fetch = FetchType.EAGER)
    List<Order> orders;
}
```

Now:

```java
Customer customer = repository.findById(1L).get();
```

JPA loads:

```sql
SELECT * FROM customer WHERE id = 1;

SELECT * FROM orders WHERE customer_id = 1;
```

(or it may use a JOIN depending on the provider and query)

Even if you never call:

```java
customer.getOrders();
```

the orders are already loaded.

#### Real-world Analogy

Imagine ordering a **burger**.

With **EAGER**, the restaurant automatically gives you:

- Burger
- Fries
- Coke

Even if you only wanted the burger.

---

### Which one should we use?

✅ **Prefer `LAZY`** in most real-world applications because it avoids loading unnecessary data and improves performance.

Use **`EAGER`** only when you know the related entity is **always required**.

---

### Interview Answer (20 seconds)

> **`FetchType.LAZY` loads related entities only when they are accessed, which improves performance by avoiding unnecessary database queries. `FetchType.EAGER` loads related entities immediately along with the parent entity. In most real-world applications, `LAZY` is preferred because it reduces memory usage and improves performance, while `EAGER` should be used only when the related data is always needed.**

---

### Memory Trick

```
LAZY  = Load Later 📦

EAGER = Load Everything Immediately 🚚
```

**One-line memory aid:**

- **LAZY** → _"Load when I ask."_
- **EAGER** → _"Load everything now."_

------------

## 🚩 N+1 query problem? caused by FetchType.EAGER or lazy loading ?

Excellent interview question. Many candidates get this wrong.

### Short Answer

> **The N+1 Query Problem is NOT caused by `LAZY` or `EAGER` themselves.**
> 
> It is caused by **how entities are fetched**.

However:

- `LAZY` commonly leads to N+1 if you access the child entities in a loop.
- `EAGER` can also cause N+1 depending on the query and JPA provider.

So **both can suffer from N+1**.

---

#### Example

Suppose:

```
Customer 1 -----> Many Orders
```

There are **3 customers**.

---

### Using LAZY

```java
List<Customer> customers = customerRepository.findAll();

for (Customer customer : customers) {
    System.out.println(customer.getOrders().size());
}
```


```sql
-- Query 1
SELECT * FROM customer;

-- Query 2
SELECT * FROM orders WHERE customer_id = 1;

-- Query 3
SELECT * FROM orders WHERE customer_id = 2;

-- Query 4
SELECT * FROM orders WHERE customer_id = 3;
```

Total:

```
1 + 3 = 4 queries
```

This is the **N+1 problem**.

---

### What about EAGER?

```java
@OneToMany(fetch = FetchType.EAGER)
private List<Order> orders;
```

Now,

```java
customerRepository.findAll();
```

Many people think this solves N+1.

**Not necessarily.**

JPA may still execute:

```sql
SELECT * FROM customer;

SELECT * FROM orders WHERE customer_id = 1;

SELECT * FROM orders WHERE customer_id = 2;

SELECT * FROM orders WHERE customer_id = 3;
```

Some providers may use joins in certain cases, but **EAGER is not a guarantee that only one SQL query will be used**.

---

### How do we actually solve N+1?

- Fetch Join
- @EntityGraph
- projections

---

### Interview Answer (30 seconds)

> **The N+1 query problem occurs when JPA executes one query to fetch parent entities and then executes one additional query for each parent to fetch related entities. It is commonly seen with `LAZY` loading when relationships are accessed in a loop, but it can also happen with `EAGER` loading depending on how the query is executed. The recommended solution is to use `JOIN FETCH`, `@EntityGraph`, or projections to fetch the required data efficiently.**

---

### Important Interview Point

❌ **Wrong:** "`LAZY` causes the N+1 problem."

✅ **Correct:** "The N+1 problem is caused by the fetching strategy used in the query. It is more commonly observed with `LAZY`, but `EAGER` can also produce N+1. The proper fix is to optimize the query (for example, with `JOIN FETCH`), not simply change the fetch type."

## Use of @modifying and @Transactional ?

In Spring Data JPA, **`@Modifying` and `@Transactional` are used together whenever you write a custom JPQL or SQL query that changes data** (using `INSERT`, `UPDATE`, or `DELETE`) instead of just reading it.


**Why it is needed**: Without `@Modifying`, Spring will try to execute your update query as a select query, which triggers an `InvalidDataAccessApiUsageException`.

**Why it is needed**: If your query fails halfway through, `@Transactional` ensures the database rolls back to its original state, preventing data corruption. Without it on a modifying query, you will get a `TransactionRequiredException`.

```java
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.transaction.annotation.Transactional;

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Transactional // 1. Creates the transaction boundary
    @Modifying    // 2. Tells Spring this is an UPDATE/DELETE query
    @Query("UPDATE Product p SET p.price = :newPrice WHERE p.category = :category")
    int updatePriceByCategory(String category, double newPrice);
}
```


## How do you implement auditing in Spring Data JPA (@CreatedDate, @LastModifiedDate) ?

**Auditing** means automatically tracking **who created/updated** a record and **when** it happened.

Instead of writing code every time we save an entity, Spring Data JPA does it automatically.

Example:

|id|name|createdAt|updatedAt|
|---|---|---|---|
|1|Laptop|10 Jul 2026 10:00|15 Jul 2026 09:30|


#### 1. `@CreatedDate`

Automatically sets the timestamp **only when the entity is inserted**.

```
@CreatedDate
private LocalDateTime createdAt;
```

Example:

```
INSERT Product
createdAt = 2026-07-10 10:00
```

Later updates won't change it.

---

#### 2. `@LastModifiedDate`

Automatically updates the timestamp **whenever the entity is updated**.

```
@LastModifiedDate
private LocalDateTime updatedAt;
```

Example:

```
Update Product
updatedAt = 2026-07-15 09:30
```

---

### How to Enable Auditing?

#### Step 1: Enable JPA Auditing

```java
@SpringBootApplication
@EnableJpaAuditing

}
```

---

#### Step 2: Add Entity Listener

```java
@Entity
@EntityListeners(AuditingEntityListener.class)
public class Product {
```

---

#### Step 3: Add Auditing Fields

```java
@Entity
@EntityListeners(AuditingEntityListener.class)
public class Product {

    @Id
    private Long id;

    private String name;

    @CreatedDate
    private LocalDateTime createdAt;

```

## How do you handle optimistic and pessimistic locking in Spring Data JPA?

#### Why do we need locking?

Suppose two users try to update the same database row at the same time.

Example:

- Product stock = **10**
- User A buys 3.
- User B buys 4.

Without locking, both read **10**, and one update overwrites the other (**Lost Update Problem**).

Locking prevents this.

---

### 1. Optimistic Locking

> **"I trust conflicts are rare. Let everyone work. If conflict happens, reject one."**

Nobody locks the row while reading.

When updating, JPA checks whether someone else has already modified it.

---

#### Real-life analogy

Think of **Google Docs**.

Two people edit the same document.

When you save:

- If nobody changed it → Save succeeds.
- If someone already changed it → You get a conflict and need to refresh.

No one blocks anyone.

---

#### How Spring Data JPA implements it

Simply add a version field.

```java
@Entity
public class Product {

    @Id
    private Long id;

    private int stock;

    @Version
    private Long version;
}
```

Suppose DB contains:

```
Stock = 10
Version = 5
```

User A reads:

```
Stock = 10
Version = 5
```

User B also reads:

```
Stock = 10
Version = 5
```

User A updates.

DB becomes

```
Stock = 7
Version = 6
```

Now User B tries to update.

JPA executes something like

```sql
UPDATE product
SET stock=?, version=7
WHERE id=1 AND version=5;
```

No row matches version 5 anymore.

JPA throws

```java
OptimisticLockException
```

---

#### When to use

- Mostly reads
- Very few write conflicts
- High concurrency

Examples:

- User profile
- Product details
- Blog posts
- E-commerce product information

---

### [ Interview one-liner ]

> Optimistic locking doesn't lock the row. It uses a `@Version` field to detect concurrent updates and throws an `OptimisticLockException` if another transaction modified the data first.

---

### 2. Pessimistic Locking

> **"I don't trust anyone. Lock the row immediately."**

As soon as one transaction reads the row, it locks it.

Other transactions must wait.

---

#### Real-life analogy

Think of an **ATM**.

When you're withdrawing cash:

- The ATM locks your account.
- Another ATM cannot update the balance until you're done.

Everyone waits.

---

### Spring Data JPA

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Product findByIdForUpdate(Long id);
```

Now:

User A

```
Read row
↓
Row locked
↓
Update
↓
Commit
↓
Lock released
```

User B

```
Read row
↓
Wait...
↓
Lock released
↓
Continue
```

---

#### When to use

When conflicts are common and correctness is critical.

Examples:

- Bank account balance
- Wallet
- Inventory deduction during checkout
- Seat booking
- Payment processing

---

### [ Interview one-liner ]

> Pessimistic locking locks the database row immediately using `PESSIMISTIC_WRITE`, preventing other transactions from modifying it until the current transaction commits or rolls back.

---

### Quick Comparison

|Optimistic Locking|Pessimistic Locking|
|---|---|
|No row lock|Row is locked|
|Uses `@Version`|Uses `@Lock(PESSIMISTIC_WRITE)`|
|Conflict detected during update|Conflict prevented from happening|
|Better performance|Lower concurrency|
|Best when conflicts are rare|Best when conflicts are frequent|

----------------

### Example of optimistic and pessimistic locking in Spring Data JPA ?

Let's use the **same real-world example (Product Inventory)** for both approaches. This makes it much easier to remember during interviews.

---

### 1. Optimistic Locking Example (`@Version`)

#### Scenario

Suppose an e-commerce website has **1 iPhone left**.
Two users try to buy it at almost the same time.
Instead of locking the row, we allow both to read it.

When saving, JPA checks the **version**.
If another transaction has already updated it, the second transaction fails.

---

#### Entity

```java
@Entity
public class Product {

    @Id
    private Long id;

    private String name;

    private int stock;

    // JPA automatically increments this after every successful update.
    @Version
    private Long version;

    // getters & setters
}
```

#### Repository

```java
public interface ProductRepository extends JpaRepository<Product, Long> {
}
```

#### Service

```java
@Service
public class ProductService {

    @Autowired
    private ProductRepository repository;

    @Transactional
    public void purchase(Long productId) {

        // Read Product
        Product product = repository.findById(productId)
                .orElseThrow();

        // Business Logic
        if (product.getStock() <= 0) {
            throw new RuntimeException("Out of Stock");
        }

        product.setStock(product.getStock() - 1);

        // save() is optional because Transactional automatically flushes
        // JPA checks version before updating.
        repository.save(product);
    }
}
```

---

### What happens internally ?

Initial DB

| Stock | Version |
| ----- | ------- |
| 1     | 5       |

---

#### User A

```
Read Stock = 1
Version = 5
```

---

#### User B

```
Read Stock = 1
Version = 5
```

---

### User A saves

```sql
UPDATE product
SET stock = 0,
    version = 6
WHERE id = 1
AND version = 5;
```

Success ✅

---

### User B saves

```sql
UPDATE product
SET stock = 0,
    version = 6
WHERE id = 1
AND version = 5;
```

No row matches Version 5 anymore.

JPA throws

```java
OptimisticLockException
```

---

#### Interview Point

> Nobody was blocked.
> 
> JPA detected another transaction had already modified the row using the `@Version` column.

---

### 2. Pessimistic Locking Example

##### Scenario

Suppose this is a **bank account**.
Balance = ₹10,000
Two ATMs try to withdraw money simultaneously.

Here, we cannot allow concurrent updates.
So we lock the row immediately.

---

#### Repository

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    // Lock the row as soon as it is read.
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Product findProductForUpdate(Long id);
}
```

#### Service

```java
@Service
public class ProductService {

    @Autowired
    private ProductRepository repository;

    @Transactional
    public void purchase(Long id) {

        // Database row gets locked here.
        Product product = repository.findProductForUpdate(id);

        if (product.getStock() <= 0) {
            throw new RuntimeException("Out of Stock");
        }

        product.setStock(product.getStock() - 1);

        repository.save(product);

        // Lock is released only after transaction commits.
    }
}
```

---

### What happens internally?

#### User A

```
BEGIN TRANSACTION

Read Product

🔒 Database locks the row

Stock = 5

Update Stock = 4

COMMIT

Unlock row
```

---

#### User B

```
BEGIN TRANSACTION

Try to read Product

❌ Wait...

(User A still holds lock)

After User A commits

Row unlocked

Now User B continues
```

---

#### SQL generated

```sql
SELECT *
FROM product
WHERE id = 1
FOR UPDATE;
```

`FOR UPDATE` tells the database to lock the selected row until the transaction completes.

---

### Which one is used more?

#### Optimistic Locking (Most common)

Used for:

- User Profile
- Product Details
- Blog
- Orders
- Employee Records

Reason:

- Read operations are much more frequent than conflicting writes.
- Higher concurrency and better performance.

---

#### Pessimistic Locking

Used for:

- Bank balance
- Wallet
- Seat booking
- Payment processing
- Inventory deduction during checkout (when overselling must be prevented)

Reason:

- Data correctness is more important than throughput.
- Conflicts are expected or cannot be tolerated.

# Interview Cheat Sheet

|Optimistic Locking|Pessimistic Locking|
|---|---|
|`@Version`|`@Lock(PESSIMISTIC_WRITE)`|
|No lock while reading|Row locked immediately|
|Detects conflict during update|Prevents conflict from happening|
|Throws `OptimisticLockException`|Other transactions wait until lock is released|
|Best when conflicts are rare|Best when conflicts are common or correctness is critical|

### Easy way to remember

- **Optimistic** = _"Trust everyone; if a conflict happens, reject the later update."_
- **Pessimistic** = _"Don't trust anyone; lock first, then update."_

### PESSIMISTIC_READ ?

>A shared lock (often called a read lock) is a concurrency control mechanism that allows multiple transactions or processes to read a resource simultaneously but prevents any process from modifying it. While a shared lock is active, other read locks can be granted, but no exclusive (write) locks can be acquired until all shared locks are released.

> An exclusive lock (also known as a write lock) is a concurrency control mechanism that grants a single process or transaction sole access to a resource, prohibiting all other processes from reading or writing to it until the lock is released.

#### First understand what `PESSIMISTIC_READ` does

It acquires a **shared lock**.

- ✅ Multiple transactions can read the same row.
- ❌ No transaction can update the row until all read locks are released (database behavior varies slightly by vendor, but this is the general idea).

Imagine a **library reference book**.

Many students can sit and **read** the book.

But nobody is allowed to **write notes inside the book** until everyone finishes reading.

```
Reader A  ----\
               \
Reader B -------> Shared Read Lock
               /
Reader C -----/

Writer D
   |
   | waits...
   |
Readers finish
   |
Writer updates
```

---

### Example: PESSIMISTIC_READ

Repository

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_READ)
    @Query("select p from Product p where p.id=:id")
    Product findProduct(Long id);
}
```

Service

```java
@Transactional
public Product viewProduct(Long id) {

    // Shared read lock
    Product product = repository.findProduct(id);

    // simulate long processing
    Thread.sleep(10000);

    return product;
}
```

---

Suppose

```
Stock = 10
```

#### User A

```
Read Product

🔒 Shared Read Lock

Processing...
```

#### User B

```
Read Product

🔒 Another Shared Read Lock

Processing...
```

#### User C wants to update stock

```
Update Product

❌ Wait...

Readers still holding lock
```

Only after A and B finish can User C update.

---

### Why not always use PESSIMISTIC_READ?

Imagine an Amazon product page.

```
100,000 users
```

All open the same product.

With `PESSIMISTIC_READ`

```
100,000 read locks

↓

Seller wants to update price

↓

Cannot update

↓

Must wait until every read transaction ends
```

Terrible performance.

---

With `@Version`

```
100,000 users read

↓

Seller updates immediately

↓

Version changes

↓

Only conflicting updates fail
```

No waiting. Much faster.
