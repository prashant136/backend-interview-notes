
**Question 1: IOC? Purpose and benefits of IOC container in Spring ? DI ? types? explain to the interviewer ?**

**1. IoC — Inversion of Control**

**Definition:**  
IoC ka matlab hai **object banane aur manage karne ka control Spring ko de dena**, instead of khud `new` se object banana.

```
// Without IoC
UserService service = new UserService();
```

Spring mein:

```
@Autowired
UserService service;
```

👉 **Simple line:** _“Spring manages the creation and lifecycle of objects.”_


**2. IoC Container**

IoC Container woh **Spring ka component hai jo objects (Beans) ko create, configure aur manage karta hai.**

**Purpose/Benefits:**

- Object creation Spring handle karta hai
- Dependencies automatically provide karta hai
- Loose coupling
- Object lifecycle manage karta hai


```
ApplicationContext context = ...;

UserService service =
    context.getBean(UserService.class);
```

👉 Interview line:  
**“IoC Container manages Spring Beans and their dependencies and lifecycle.”**


**3. DI — Dependency Injection**

DI, IoC ko achieve karne ka **main mechanism** hai.

**Definition:**  
Ek object ki dependency ko **bahar se provide karna** instead of object khud create kare.

```
class UserService {
    private UserRepository repo;

    UserService(UserRepository repo) {
        this.repo = repo;
    }
}
```

Spring `UserRepository` ko `UserService` mein inject karega.

---

**4. Types of DI**

Constructor Injection -

```
@Service
class UserService {

    private final UserRepository repo;

    UserService(UserRepository repo) {
        this.repo = repo;
    }
}

// Dependency constructor ke through milti hai.
// Spring object banate time UserRepository pass karega.
```

**Interview:**

> “In constructor injection, dependencies are provided through the class constructor.”


Setter Injection -

```
@Service
class UserService {

    private UserRepository repo;

    @Autowired
    void setRepo(UserRepository repo) {
        this.repo = repo;
    }
}

// Dependency setter method ke through milti hai.
// Spring pehle object banata hai, phir setter call karke dependency deta hai.
// Use: Jab dependency optional/changeable ho.
```


Field Injection -

```
@Service
class UserService {

    @Autowired
    private UserRepository repo;
}

// Dependency directly field mein inject hoti hai.
```

Yahan constructor/setter ki zarurat nahi.

Why Field Injection is NOT Recommended ?

- Main reason:  (Dependencies hidden) => Dependency hidden ho jaati hai. Dekhne se immediately pata nahi chalta ki UserService ko UserRepository required dependency hai. jo Constructor mein clearly dikhta hai.

- final use nahi kar sakte easily. dependency immutable nhi bana sakte.
- unit testing becomes harder.
- Object fully initialized nahi hota constructor ke time.

Interview:

> **“There are three types of DI: Constructor, Setter and Field injection. Constructor injection is generally preferred because dependencies are explicit, can be made final, and make unit testing easier. Field injection is not recommended because dependencies are hidden and testing becomes harder.”**

**Shortcut yaad rakho:**  
Constructor = required dependency ✅
Setter = optional dependency
Field = easy but generally avoid ❌

Ek line mein relation:

**IoC = Control Spring ko dena**  
**DI = Spring se dependency inject karwana**  
**IoC Container = Jo ye objects/dependencies manage karta hai**

Autowiring is the process by which Spring automatically injects dependencies (beans) into a class without manual configuration.

@Service

**What if we implement same interface in two classes and we have to inject one of the class using autowiring ?**

Matlab:

```java
interface PaymentService {
    void pay();
}

// Ab 2 classes same interface implement kar rahi hain:

@Service
class StripePayment implements PaymentService {
    public void pay() {}
}

@Service
class RazorpayPayment implements PaymentService {
    public void pay() {}
}
```

Ab tum likhte ho:

```
@Autowired
private PaymentService paymentService;
```

Problem kya hai?
Spring ke paas **2 beans** hain:

```
PaymentService
     ↓
 ┌───────────────┐
 ↓               ↓
Stripe        Razorpay
```

Spring confuse ho jayega:

> "Bhai, Stripe inject karu ya Razorpay?" 😵

Isliye **`NoUniqueBeanDefinitionException`** aa sakta hai.


**Isko solve kaise karte hain?**

Option 1 — `@Qualifier` ✅

```
@Autowired
@Qualifier("stripePayment")
private PaymentService paymentService;

// Ab Spring ko clear hai: StripePayment inject karo.
```

Option 2 — `@Primary`

```
@Service
@Primary
class StripePayment implements PaymentService {
}

Ab agar multiple implementations hain, Spring StripePayment ko default maanega.
```


Interview mein short answer:

> If multiple classes implement the same interface, Spring gets confused because multiple beans match the dependency. We can resolve this using `@Qualifier` to explicitly select a bean, or `@Primary` to mark one bean as the default.

Bas is question ka core yehi hai:

Same interface → multiple implementations → Spring confused → `@Qualifier` / `@Primary`

**Question 3: @Configuration? @Bean ?**

@Configuration kya hai?

`@Configuration` batata hai ki **ye class Spring ke liye configuration class hai**, jahan hum beans define kar sakte hain.

```
@Configuration
public class AppConfig {

}

// Es class ke andar meri Spring configuration hai.
```

@Bean kya hai?

`@Bean` batata hai ki **es method ke return object ko Spring Bean ke roop mein manage karo.**

```
@Configuration
class AppConfig {

    @Bean
    UserService userService() {
        return new UserService();
    }
}
```

Interview mein bolna:

> `@Configuration` marks a class as a source of Spring bean definitions, and `@Bean` tells Spring to manage the object returned by that method as a bean.

**@Autowired vs @Inject** ?

> Both `@Autowired` and `@Inject` are used for dependency injection. `@Autowired` is Spring-specific, while `@Inject` is a standard dependency-injection annotation from Jakarta. In a Spring application, `@Autowired` is commonly used.

Maven Dependency Resolution kya hai?

> **Maven dependency resolution ka matlab hai Maven decide karta hai ki project mein agar same library ki multiple versions aa rahi hain, toh kaunsi version use karni hai.**

Generally Maven **nearest dependency** ko choose karta hai.

```
Project
 ├── A
 │    └── X v1
 │
 └── B
      └── C
           └── X v2
```

Yahan `X v1` project ke closer hai, toh **v1 select** ho sakta hai.

Agar same level/distance par conflict ho, Maven **first declaration** ko choose karta hai.

### Interview mein:

> **“Maven dependency resolution is the process Maven uses to determine which version of a dependency should be included when multiple versions are present. Maven generally uses the nearest dependency, and if there is a tie, the first declared dependency wins.”**

Bas yaad rakho:

**Multiple versions → Maven resolves conflict → nearest wins → tie mein first declared wins.**

☯️ mvn dependency: tree -> isko baad me smajhte hai.

Question: disable a specific auto-configuration class? Why we might need this ?

We disable specific auto-configurations when the default configuration provided by Spring Boot is not suitable, such as when we don't need a feature, want custom configuration, or want to avoid unnecessary initialization like database or security setups. Examples - Disable web if creating cli/batching app, security - we want JWT but spring gives us login page etc.

iska matlab ye hai.

Lekin project mein database dependency accidentally available hai, aur Spring `DataSource` configure karne ki try kar raha hai.

Tum disable kar sakte ho:

```

)
```

But tum apna **JWT-based authentication** implement karna chahte ho. toh tum default security auto-configuration ko exclude/customize kar sakte ho, depending on the setup:

    exclude = SecurityAutoConfiguration.class

Question: How do you handle exceptions in Spring Boot applications? 
I handle errors by creating a special Global Exception class with @RestControllerAdvice.
-> This class has methods marked with @ExceptionHandler that deal with different types of errors.
-> These methods help make sure that when something goes wrong, my application responds in a helpful way, like sending a clear error message or a specific error code.

**Custom Exception -**

Pehle apni exception banate hain:

```
public class UserNotFoundException extends RuntimeException {

    public UserNotFoundException(String msg) {
        super(msg);
    }
}
```

Ab kahin bhi:

```
throw new UserNotFoundException("User not found");
```

kar sakte ho.

 `@RestControllerAdvice`

Ab ek **central/global exception handler** banate hain:

```
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<String> handle(UserNotFoundException ex) {

        return new ResponseEntity<>(
            ex.getMessage(),
            HttpStatus.NOT_FOUND
        );
    }
}
```

Iska matlab:

> **“Agar application mein `UserNotFoundException` aaye, toh is method ko execute karo.”**

## CommandLineRunner & ApplicationRunner in spring boot ?

`CommandLineRunner` and `ApplicationRunner` are **Spring Boot startup hooks**. They allow you to execute code **once after the Spring Boot application has started** and all beans have been created.

### Why do we need them?

Suppose your Spring Boot application starts.

Startup sequence:

```
main()
    ↓
SpringApplication.run()
    ↓
Create ApplicationContext
    ↓
Create Beans
    ↓
Dependency Injection
    ↓
Application Ready
    ↓
Run CommandLineRunner/ApplicationRunner
```

Sometimes after the application starts, you want to:

- Load default data
- Create admin user
- Warm up cache
- Connect to external systems
- Print startup information
- Schedule some background work

Instead of putting this code inside `main()`, Spring Boot provides these interfaces.

---

### 1. CommandLineRunner

It is an interface.

```java
public interface CommandLineRunner {
    void run(String... args) throws Exception;
}
```

Spring automatically calls the `run()` method after startup.

---

### Example

```java
@Component
public class StartupRunner implements CommandLineRunner {

    @Override
    public void run(String... args) {

        System.out.println("Application Started!");

        for (String arg : args) {
            System.out.println(arg);
        }
    }
}
```

Output

```
Application Started!
hello
world
```

Run

```
java -jar app.jar hello world
```

The arguments become

```
args[0] = hello
args[1] = world
```


---

Insert initial records.

public class DataLoader implements CommandLineRunner {

}

### Why is ApplicationRunner better?

Because parsing command-line arguments yourself can be cumbersome.

With `CommandLineRunner`:

```
String[] args
```

You manually check

```
args[0]

args[1]

args[2]
```

With `ApplicationRunner`

```
args.getOptionValues("name")
```

Much cleaner.

---

### Difference

|Feature|CommandLineRunner|ApplicationRunner|
|---|---|---|
|Parameter|`String... args`|`ApplicationArguments`|
|Parses options|❌ No|✅ Yes|
|Access named arguments|❌|✅|
|Access non-option args|Manual|Built-in|
|Simplicity|Very simple|More powerful|

### Multiple Runners

You can have many runners.

```
@Component
class Runner1 implements CommandLineRunner
```

```
@Component
class Runner2 implements CommandLineRunner
```

Spring executes both.

To control order

```
@Component
@Order(1)
class Runner1 implements CommandLineRunner
```

```
@Component
@Order(2)
class Runner2 implements CommandLineRunner
```

Execution

```
Runner1

↓

Runner2
```

---

### Can we mix both?

Yes.

```
@Component
class RunnerA implements CommandLineRunner
```

```
@Component
class RunnerB implements ApplicationRunner
```

Spring executes both after startup.

### Interview Questions

#### Q1. When is `CommandLineRunner` executed?

**Answer:** After the Spring Boot application context has been created, all beans are initialized, and dependency injection is complete.

---

#### Q2. Can there be multiple `CommandLineRunner` beans?

**Answer:** Yes. Spring executes all of them. Use `@Order` or implement `Ordered` to control execution order.

---

#### Q3. What is the difference between `CommandLineRunner` and `ApplicationRunner`?

**Answer:** `CommandLineRunner` receives raw `String... args`, while `ApplicationRunner` receives an `ApplicationArguments` object that provides convenient methods to access option (`--key=value`) and non-option arguments.

---

#### Q4. Which one should you prefer?

**Answer:** If you only need the raw command-line arguments, `CommandLineRunner` is sufficient. If you need structured access to named command-line options, `ApplicationRunner` is generally the better choice.

## What is Logger in Spring ?

**Logging** means recording information about what your application is doing while it is running.

Instead of:

```
System.out.println("User created");
```

we write:

```
log.info("User created");
```

The log can be written to:

- Console
- File
- Database (rare)
- Cloud logging systems (AWS CloudWatch, ELK, Splunk, Datadog, etc.)

Example:

```
2026-07-22 10:15:23 INFO  UserService : User created successfully
2026-07-22 10:15:24 ERROR PaymentService : Payment failed
```

---

#### Why not use `System.out.println()`?

Imagine a production application serving **10,000 requests per second**.

Using:

```
System.out.println("Request received");
```

Problems:

- No timestamp
- No log level
- Can't disable logs selectively
- Difficult to search
- Cannot write to files easily
- Poor performance for large-scale applications

A logging framework solves these problems.

---

### Creating a Logger

Without Lombok:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class UserService {

    private static final Logger log =
            LoggerFactory.getLogger(UserService.class);

}
```

This creates one logger for the class.

---

#### Why `static final`?

```
private static final Logger log =
        LoggerFactory.getLogger(UserService.class);
```

static means Only one logger object per class. Not one per object.

and final -> Nobody can replace it later.

Good for memory.

#### Why `UserService.class`?

```
LoggerFactory.getLogger(UserService.class)
```

> "These logs belong to UserService."

---
### [ Do we need to define logger in every class? ]

#### Yes.

Usually every class has its own logger.

```java
Controller

private static final Logger log = ...
```

```java
Service

private static final Logger log = ...
```

```java
Repository

private static final Logger log = ...
```

This helps identify exactly which class produced the log.

---

### Can we define one global logger?

Technically yes.

```java
public class LoggerUtil {

    public static final Logger log =
            LoggerFactory.getLogger(LoggerUtil.class);

}
```

Then:

```
LoggerUtil.log.info("Hello");
```

But this is **not recommended**.

Why?

Every log will show:

```
LoggerUtil
```

instead of

```
UserService

OrderService

PaymentController
```

You lose the actual source of the log.

---

### Best Practice (Without Lombok)

Every class should have:

```java
private static final Logger log =
        LoggerFactory.getLogger(CurrentClass.class);
```

---

### Best Practice (With Lombok)

Most Spring Boot projects use Lombok.

```java
@Slf4j
@Service
public class UserService {

    public void createUser() {

        log.info("User Created");
    }

}
```

### `Log Levels`

### 1. TRACE

Most detailed logging.

Example:

```
log.trace("Entering method createUser()");
```

Used for:

- Every method call
- Variable values
- SQL parameters
- Internal framework behavior

Usually disabled in production.

---

### 2. DEBUG

Developer logs.

Example:

```
log.debug("Request received: {}", request);
```

Useful during development.

Example:

```
log.debug("User ID = {}", userId);
```

Production:

Usually OFF.

---

### 3. INFO ⭐ (Most Common)

Normal business events.

Example:

```
log.info("Application Started");
```

```
log.info("User registered successfully");
```

```
log.info("Order Created");
```

These logs are usually enabled in production.

---

### 4. WARN

Something unexpected happened, but the application can continue.

Example:

```
log.warn("User profile image missing, using default image");
```

Another:

```
log.warn("Redis unavailable. Falling back to database.");
```

No crash.

Just a warning.

---

### 5. ERROR

A serious problem occurred.

Example:

```
try {

    paymentService.pay();

}
catch(Exception e){

    log.error("Payment Failed", e);

}
```

Output:

```
ERROR PaymentService : Payment Failed

StackTrace...
```

---

### Logging an Exception

Bad:

```
log.error(e.getMessage());
```

Good:

```
log.error("Payment failed", e);
```

This logs:

- Message
- Stack trace
- Exception type

---

### Placeholder Logging

Don't do this:

```
log.info("User ID = " + id);
```

Use:

```
log.info("User ID = {}", id);
```

Multiple values:

```
log.info("User {} created order {}", userId, orderId);
```

SLF4J formats the message efficiently.

---

### Setting Log Levels

In `application.properties`:

```
logging.level.root=INFO
```

Specific package:

```
logging.level.com.example.service=DEBUG
```

Specific class:

```
logging.level.com.example.UserService=TRACE
```

---

### Typical Production Logging

```
log.info("User {} logged in", userId);

log.debug("JWT Token = {}", token);

log.warn("Retrying payment");

log.error("Payment failed", exception);
```

|Log Level|When to Use|Production?|
|---|---|---|
|`TRACE`|Very fine-grained execution details|Rarely enabled|
|`DEBUG`|Developer troubleshooting|Usually disabled|
|`INFO`|Normal business events and application lifecycle|✅ Common|
|`WARN`|Recoverable or unexpected situations|✅ Common|
|`ERROR`|Failures and exceptions|✅ Common|

## @Value and @ConfigurationProperties ?

#### @Value -

It allows you to read configuration data from sources like `application.properties`, environment variables, or system properties without hardcoding values in your Java code.

```java
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

@Component
public class DatabaseConfig {

    // 1. Hardcoded Literal Injection
    @Value("MyApplication")
    private String appName;

    // 2. Property File Injection (${property.name})
    @Value("${db.url}")
    private String databaseUrl;

    // 3. Property Injection with a Default Value (${property.name:default_value})
    @Value("${db.timeout:5000}")
    private int timeout;
}
```

#### ConfigurationProperties -

The **`@ConfigurationProperties`** annotation in Spring and Spring Boot is used to bind external configuration properties (like those in `application.properties` or `application.yml`) into a **strongly-typed Java object**.

Unlike the individual field injection of `@Value`, it allows you to group related configuration properties into a single bean.

```
app:
  security:
    enabled: true
    token-timeout: 3600
    roles: [ADMIN, USER]

```


```java
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.context.annotation.Configuration;
import java.util.List;

@Configuration
@ConfigurationProperties(prefix = "app.security")
public class SecurityProperties {

    private boolean enabled;
    private int tokenTimeout; // Maps from token-timeout
    private List<String> roles;

    // Getters and Setters are required unless using records
    public boolean isEnabled() { return enabled; }
    public void setEnabled(boolean enabled) { this.enabled = enabled; }

    public int getTokenTimeout() { return tokenTimeout; }
    public void setTokenTimeout(int tokenTimeout) { this.tokenTimeout = tokenTimeout; }

    public List<String> getRoles() { return roles; }
    public void setRoles(List<String> roles) { this.roles = roles; }
}

```


## @PostConstruct and @PreDestroy ?

These are lifecycle annotations in Spring.
- **`@PostConstruct`** → Runs **once after the bean is created and all dependencies are injected**.
- **`@PreDestroy`** → Runs **just before the Spring bean is destroyed** (for example, when the application shuts down).

---

### Syntax of `@PostConstruct`

```java
import jakarta.annotation.PostConstruct;
import org.springframework.stereotype.Service;

@Service
public class EmailService {

    @PostConstruct
    public void init() {
        System.out.println("Initializing EmailService...");
    }
}
```

**Execution flow:**

```
Bean Created
      ↓
Dependencies Injected
      ↓
@PostConstruct executes
      ↓
Bean Ready to Use
```

**Common use cases:**

- Load configuration
- Initialize caches
- Create database connections
- Preload data

---

### Syntax of `@PreDestroy`

```java
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Service;

@Service
public class EmailService {

    @PreDestroy
    public void cleanup() {
        System.out.println("Closing resources...");
    }
}
```

**Execution flow:**

```
Application Shutdown
        ↓
@PreDestroy executes
        ↓
Bean Destroyed
```

**Common use cases:**

- Close database connections
- Stop background threads
- Close file streams
- Release resources
